# R-0001: Deterministic simulation in Rust: build on an existing runtime or write our own

- Task: T-0003
- Used by: arfc-0005 section 9 (first open question), ADR on the `alloy-sim` foundation

## Answer

No surveyed option meets ARFC 0005 sections 3.2 and 3.3 as it stands. `turmoil` is the closest but it drives real `tokio` and cannot control task scheduling, so 3.2.2 fails; it also lacks several 3.3 faults and measured far outside the 3.2.3 time budget. `madsim` controls scheduling, time and randomness but its disk and network models are thin and it needs a `--cfg madsim` build plus `[patch]` git dependencies. `shuttle` is a concurrency tester with no network, disk, or virtual clock. Because ARFC 0005 puts everything behind five seams that we own, only an executor, a timer wheel, and the models are needed, and those are the part the libraries do not give us. Recommendation: write `alloy-sim` in-house, borrowing designs (not dependencies) from `madsim` and `turmoil`.

## What the sources say

### turmoil 0.7.2

- License MIT; latest release 2026-04-24, 26 releases since 2022; last commit 2026-11-12; repository `tokio-rs/turmoil`, not archived [1][2][3].
- Direct code: no `unsafe` in `src/` (grep count 0); 40 unique crates in the normal dependency tree across all targets (includes `tokio`, `rand` 0.9, `indexmap`, `bytes`, proc-macros, Windows crates) [4][5]. Advisories: not checked (`cargo audit` and `cargo deny` not installed in this environment).
- Model: each host is its own `tokio` current-thread `Runtime` with `start_paused(true)` plus a `LocalSet`; the simulator calls `block_on(local.run_until(sleep(tick)))` on each host in turn [6]. Hosts and a client run in one OS thread [6][7].
- Scheduling: task order inside a host is whatever `tokio`'s current-thread scheduler does. The seed only reaches `tokio` through `tokio_unstable` `rng_seed` (affects `select!` branch order), and `enable_random_order` shuffles which host ticks first [6][8]. There is no hook to choose the next runnable task.
- Time: `tokio` paused time; tick length configurable via `Builder::tick_duration` [8]. A comment in `rt.rs` says each host runtime "may have a different sense of now which simulates clock skew"; no skew or step API was found in `src/` (grep for "skew" finds only that comment) [6].
- Network: simulated `turmoil::net` types "mirror `tokio::net`" (TCP, UDP); the docs state turmoil "is not yet opinionated on how to structure your application code to swap in simulated types" [7]. Faults: random drop (`fail_rate`), `repair_rate`, per-link latency min/max and curve, `partition`, one-way partition, `hold`/`release` of in-flight messages [8][9]. A grep of `src/` for duplicate, corrupt, MTU finds no network fault of those kinds (only TCP internals) [6].
- Disk: feature `unstable-fs`. Per-host in-memory filesystem; unsynced writes and never-synced files are lost on `crash()`; options for sync probability, capacity (full disk), I/O error probability, silent read corruption probability, `block_size` for torn writes, direct I/O alignment, I/O latency, page cache [10].
- Crash/restart: `Sim::crash` and `Sim::bounce` drop and rebuild the host's `tokio` runtime; they are called between simulator steps, so a crash lands on a tick boundary [6][9]. Host software is a factory closure that is re-run on bounce [6].
- Nothing in the sources mentions randomness or `std::time` interception; host code that calls `std::time::Instant`, `SystemTime`, `getrandom`, or std `HashMap` still sees the real world [6][7]. Unknown whether this was ever intended (see Unknown).
- Source size: `src/` is 7,666 lines of Rust [4].

### madsim 0.2.34

- License Apache-2.0; latest release 2025-10-11, 46 releases; last commit 2026-02-16 (a `tonic` and `etcd-client` bump); not archived [1][2][11].
- Direct code: 35 `unsafe` occurrences in `src/` (rand 6, task 11, time 9, std-mode network 9) [4]. 86 unique crates in the normal tree including proc-macros, builds identical with or without `--cfg madsim` (cargo tree) [5]. Advisories not checked.
- Model: a `tokio`-like runtime (`madsim::runtime`) written from scratch, selected at build time by `RUSTFLAGS="--cfg madsim"`; applications rename `tokio` to `madsim-tokio` (and `tonic`, `etcd-client`, `rdkafka`, `aws-sdk-s3` likewise) and may need git `[patch.crates-io]` entries for `quanta`, `getrandom`, `tokio-retry`, `tokio-postgres`, `tokio-stream` [12].
- Scheduling: ready tasks are picked at random using the global seeded RNG (`try_recv_random`) [13]. Nodes can be killed, restarted, paused, sent Ctrl-C; a task can be restarted on panic [14].
- Time: virtual clock owned by the runtime, `advance_to_next_event` jumps time when nothing is runnable [15]. It overrides libc `clock_gettime` and `gettimeofday` via `#[no_mangle]` so `std::time::Instant` and `SystemTime` return simulated time inside the runtime [16].
- Randomness: overrides libc `getrandom` and `getentropy` and seeds std's `HashMap` random state, so `rand`, `HashMap` order, and similar become seed-driven; `Runtime::check_determinism` runs a scenario twice and compares RNG-call logs, panicking with "non-determinism detected at <time>" [17][14].
- Platform: the override code has `compile_error!("unsupported os")` for platforms other than Linux and macOS [17].
- Network: `Config` has two fields, `packet_loss_rate` and `send_latency` range; node and link "clog" (partition) with direction; IP assignment per node [18]. No duplication, corruption, MTU, or reorder (beyond latency variance) option in `Config` [18].
- Disk: `FsSim::power_fail` has the body `// TODO` and does nothing; files are an in-memory `Vec<u8>` per path with `read_at`, `write_all_at`, `set_len`; no sync, torn-write, error, or full-disk concept in `sim/fs.rs` [19].
- Source size: `src/sim` is 6,127 lines [4].

### shuttle 0.9.10

- License Apache-2.0; 0.9.10 released 2026-11-05, 31 releases, roughly weekly in Oct-Nov 2026; last commit 2026-11-11; not archived [1][2][20].
- Direct code: 3 `unsafe` lines in the `shuttle` crate itself; the engine lives in `shuttle-engine` and `shuttle-std` whose `unsafe` was not counted. 46 unique crates in the normal tree (includes `corosensei` stack switching, `bitvec`, `rand` 0.8) [4][5]. Advisories not checked.
- Purpose: "randomized concurrency testing" of threaded or async code; a `check_random(f, iterations)` runs the closure many times under a scheduler that picks which thread or task runs next, from a seed, with PCT and other schedulers; passing is not a proof [21].
- Application code swaps `std::sync`, `std::thread` for `shuttle::sync`, `shuttle::thread`; `shuttle::rand` replaces `rand` 0.8 with a replayable generator [21][22]. Wrappers exist for `tokio`, `parking_lot`, `dashmap`, `lazy_static`, `async_stream`, `rand`, collections [23].
- `shuttle-tokio` (1.0.0, depends on `tokio` 1.54.1): `fs`, `net`, `io` "simply forwarded to tokio... will not work if one actually tries to use it under Shuttle"; a task is modeled as a thread; no time model beyond "a very simple built in time model", `start_paused` unsupported; `sync::broadcast` unimplemented [24][5].
- No network, disk, crash, or virtual clock facilities were found in `shuttle` 0.9.10 `src/` (files: future, lazy_static, rand, scheduler, sync, thread) [4].

### Requirement table (ARFC 0005 sections 3.2, 3.3)

M = meets, P = partly, F = fails, C = cannot be made to meet without replacing its core. "Meets" is judged from the sources above, not from running a scenario, except where noted.

| Requirement | turmoil | madsim | shuttle |
|---|---|---|---|
| 3.2.1 byte-identical traces from (binary, seed); trace hash printed | P: deterministic by construction only for code that avoids real clock, RNG, `HashMap` seeding, threads; no trace hash facility found; `tracing` output exists | P: global RNG seeded, std `HashMap` seeded, libc time/entropy overridden, `check_determinism` compares RNG logs not event traces | P: execution is replayable from a schedule; no network or time events to trace |
| 3.2.2 seed picks next runnable task and order of simultaneous events | F: task order is tokio's; only host order and `select!` order are seedable | M: random pick of ready tasks; simultaneous timers use seeded RNG [13][15] (not verified for timers) | M for task choice; time and delivery not modeled |
| 3.2.2 time advances only when nothing is runnable | M in principle (paused tokio time auto-advance), but advanced in fixed ticks by the driver [6] | M [15] | F: no virtual clock |
| 3.2.3 ns resolution; 1 virtual hour, 100 nodes under 60 s on one core | F measured below; ticks are 1 ms by default [8] | Unknown: not measured; event-skipping clock suggests it can | not applicable |
| 3.3 loss | M | M | F |
| 3.3 duplication, corruption, MTU with or without ICMP, jitter, reorder | P: latency range and curve give jitter and incidental reorder; duplication, corruption, MTU not found | P: latency range only | F |
| 3.3 one-way and two-way partitions | M [9] | P: clog node (direction) and link [18]; one-way per link not verified | F |
| 3.3 host crash at any await point, torn unsynced writes | P: crash between ticks, not at an arbitrary await; unsynced writes lost; torn writes via `block_size` [10] | P: kill node at a step boundary [14]; disk power failure is TODO [19] | F |
| 3.3 host restart | M [9] | M [14] | F |
| 3.3 disk read errors, corrupt reads, full disks | M (unstable feature) [10] | F [19] | F |
| 3.3 clock skew and steps | P: separate per-host runtimes can differ, no API found [6] | Unknown: one global virtual clock found; no per-node offset found | F |
| 3.3 CPU stalls | Unknown (could be built with `hold`-like barriers; none found) | Unknown; `pause(node)` stops a node [14] | P: scheduler can starve a task |
| Seams: batch send/receive, interface list, direct block access | F: API mirrors tokio sockets and `std::fs` | F: mirrors tokio | F |
| NAT devices, routers, 10,000 hosts per world | F: flat network | F: flat network | F |

### What running production `tokio` code under each requires

- turmoil: build the production code against a `tokio` it controls (it needs a current-thread paused runtime and the `turmoil::net` socket types), so network and file code must be written against its types or an abstraction over them [7]. No `cfg` flag or source patching. Also needs `tokio_unstable` for panic forwarding and RNG seed, and the `unstable-fs` feature for disks [6][10].
- madsim: replace `tokio` with `madsim-tokio` in `Cargo.toml` and build with `--cfg madsim`; patch third-party crates that read time or randomness; Linux or macOS only [12][17]. Production `alloy-rt` on `tokio` stays as is outside the cfg.
- shuttle: replace `tokio` with `shuttle-tokio` behind a `shuttle` feature; code must also use the shuttle sync and rand wrappers. Networking and disk are not simulated [23][24].
- In all three the code under test still sees `tokio` or a look-alike. ARFC 0005 section 2 instead gives components a `Runtime` of five traits and forbids other paths to the world (3.1.1), so none of these adapters is needed for our own code. They matter only for third-party dependencies that call the OS or `tokio` directly (unknown which will exist; see R-0004 for the crate candidates).

## What was verified by running

Experiment: turmoil 0.7.2, release build, idle hosts that each sleep 1 virtual second in a loop, plus one client that sleeps for the simulation length; default 1 ms tick, no network traffic (source: the 20-line program in the scratch directory, not committed).

```
$ p.exe 10 5
hosts=10 virt=5s ok=true wall=55.54ms
$ p.exe 100 3
hosts=100 virt=3s ok=true wall=4.8910957s
$ p.exe 100 60      # run alone, did not finish within 120 s of wall time and was stopped
```

100 hosts x 3 virtual seconds took 4.9 s wall, which is about 16 microseconds per host tick (300,000 ticks), against about 1 microsecond per host tick for 10 hosts (50,000 ticks in 55 ms). The 3.2.3 target is 3,600 virtual seconds x 100 hosts = 360 million host ticks at the default tick, in 60 s, that is 0.17 microseconds per host tick, and this is with idle hosts and no traffic.

Dependency counts:

```
$ cargo tree -e normal --prefix none --target all   (per crate, unique, minus duplicates)
turmoil 40   madsim 86   shuttle 46   shuttle-tokio 4
```

Not run: madsim and shuttle performance, determinism, and fault behavior (only their source was read). `cargo audit` and `cargo deny` are not installed, so no advisory check was made.

## Inference

- The 3.2.3 target fails for turmoil as designed, not because of tuning: it advances every host's `tokio` runtime on every tick (`Rt::tick` runs `block_on` per host) [6]. A larger `tick_duration` reduces ticks but lowers delivery resolution and was not measured. The Windows host used here may inflate the figure; the shortfall is two to three orders of magnitude, which is larger than plausible platform noise.
- Seam-driven design makes the existing network and disk models of limited value: they would sit behind our `Net` and `DiskIo` traits, which add batch I/O, interface lists, and direct block access that neither library models. The libraries' value is the executor and clock, and that is the part that fails 3.2.2 (turmoil) or needs a platform-specific libc interposition (madsim).
- madsim's libc interposition (`clock_gettime`, `getrandom`) exists because it must catch code that does not use its seams. Alloy bans such calls outside seam implementations (3.1.1, enforced by `check-repo`), so the interposition buys nothing for first-party code and costs `unsafe`, Linux and macOS only.
- Estimated surface of an in-house `alloy-sim` core that meets the ARFC (rough, based on the scale of turmoil's 7.7k lines and madsim's 6.1k lines, which include network and disk models that cover fewer faults than the ARFC asks for):

| Part | Lines of Rust (estimate) |
|---|---|
| Single-thread executor: task slab, wakers, seeded pick of next runnable, join and cancel, crash drops all tasks of a host | 600 to 1,000 |
| Virtual clock and timer heap, ns resolution, per-host skew and steps, stalls | 300 to 600 |
| Seeded RNG (one stream per purpose), event trace, hashing, streaming to disk with cap | 400 to 700 |
| Network model: links, loss, dup, reorder, delay, jitter, corruption, MTU with ICMP, partitions, UDP and stream sockets, interface list, batch I/O | 2,500 to 4,000 |
| Disk model: files, block devices, write cache and sync, torn writes, errors, corrupt reads, full disk, crash | 1,500 to 2,500 |
| World, hosts, crash and restart, scenario API | 600 to 1,000 |
| Checkers (linearizability, isolation, durability) | 1,500 to 2,500 |
| Total, excluding `alloy-natlab` and tests | about 7,500 to 12,000 |

  Nothing in the core needs `unsafe`: the executor can use `std::task::Wake` and `Rc` or indices. The dependency set would be `rand`-class crates only; a small fixed PRNG (for example xoshiro or PCG) is about 50 lines and removes even that.
- Risk of the in-house path: the executor must not be polled by anything non-deterministic (no `HashMap` iteration order, no threads, no wall clock). That is enforceable by `check-repo` (3.1.1) and by running each scenario twice and comparing trace hashes in CI, which is what 3.2.1 already requires.
- `turmoil` could still be used as a reference oracle or for a smoke test, but making it a dependency of `alloy-sim` would tie our determinism to `tokio` internals.

## Unknown

- Whether madsim meets the 60 s budget for 100 nodes and one hour; not measured.
- Whether madsim supports per-node clock offsets, one-way link partitions, and seeded ordering of simultaneous timers; the source read did not show it.
- Whether `turmoil` plans to add duplication, corruption, or MTU faults, or a task-scheduling hook; its issue list was only searched by title for "determin" (one match, #19 "Document determinism guidelines") [25].
- Known security advisories for all three crates and their trees: not checked.
- Which third-party crates Alloy will use that call the OS directly; that determines the real cost of the "run production tokio code" path.
- Real effort for the in-house estimate: it is derived from line counts of other projects, not from a design.
- `unsafe` count in `shuttle-engine` and `shuttle-std`.

## Options

| Option | For | Against |
|---|---|---|
| A. In-house `alloy-sim` on the five seams | Meets 3.2.2 and 3.3 by construction; no `unsafe`; no `tokio` coupling; one place owns time, scheduling, network, disk; the NAT lab needs routers and NAT in the network model regardless | Roughly 7,500 to 12,000 lines before NAT lab; we own all bugs in the simulator; more work before M0 can close |
| B. Build `alloy-sim` on `madsim` | Gives a random scheduler, virtual clock, RNG, and node kill and restart on day one | Linux and macOS only; `--cfg madsim` build and `[patch]` git dependencies conflict with `agent/eng/deps.md` (no git revisions); thin disk and network models would be rewritten anyway; last release 13 months old; 86 crates; `unsafe` libc interposition |
| C. Build `alloy-sim` on `turmoil` | Maintained weekly to monthly, MIT, richest disk model, `tokio`-native | Fails 3.2.2 and the measured 3.2.3 budget; crash only at tick boundaries; ties determinism to `tokio` internals; no network faults beyond loss, latency, partition |
| D. In-house, but use `shuttle` as a separate tool for lock and thread level tests inside single components | Cheap, finds interleaving bugs the simulator does not model | Orthogonal to the question; adds `shuttle` wrapper feature flags to production code |

Recommendation: A, because ARFC 0005's seams already make the existing libraries' adapters unnecessary and the parts they provide (scheduler, clock) are the smallest parts of the surface, while the parts they lack (full fault matrix, batch I/O, direct block access, NAT) are the large ones. Option D can be decided separately, later. Class N decision for the lead: the ARFC's open question 1 closes as "write our own"; if the pilot or architect disagrees, the deciding fact to revisit is the turmoil measurement above (re-run it on Linux with a larger `tick_duration` first).
