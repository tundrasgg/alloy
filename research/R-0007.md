# R-0007: How should the console's TypeScript API client be generated from the Protocol Buffers definitions

- Task: T-0035
- Used by: arfc-0008 section 3.10, arfc-0019 section 3.2 (spec task to follow)

## Answer

Generate it with `protoc-gen-es` (protobuf-es) and use the Connect-ES runtime (`@connectrpc/connect-web`), driven by `buf generate` from a `cargo xtask` subcommand. All are Apache-2.0 and active. That client speaks the Connect protocol or gRPC-Web over `fetch`, including server streaming (`Watch`), but not client or bidirectional streaming. Native gRPC cannot be called from a browser, and ARFC 0008 does not say what its "JSON over HTTP" surface looks like, so the spec must name a browser-callable protocol. The Rust server can serve gRPC-Web without a proxy (tonic-web on prost) or Connect (connect-rust, which uses buffa, not prost).

Protocol behavior
- Connect protocol: unary, client streaming and server streaming work over HTTP/1.1. Only bidirectional streaming needs HTTP/2. Content types `application/proto`, `application/json`, `application/connect+proto`, `application/connect+json`. Errors are JSON with `code`, `message` and `details[]` (type plus base64 value). Safe RPCs marked `NO_SIDE_EFFECTS` can use GET. No HTTP trailers are used. [20]
- Connect-ES requires only `fetch` and the Encoding API, ES2017 and TypeScript 4.1. [21] Server streaming is consumed as an async iterable (`for await`). [22] The docs pages I could read do not state browser support for client or bidirectional streaming (see Inference).
- Errors in Connect-ES are `ConnectError` with a `code` enum, and `findDetails(schema)` decodes `google.protobuf.Any` details. [23] Streaming error handling is not in the pages I read.
- gRPC-Web in Connect-ES: "Any gRPC service can be made available to gRPC-web with the Envoy Proxy"; `createGrpcWebTransport()` exists beside `createConnectTransport()`. [24]
- Server side in Rust, no proxy:
  - `tonic-web` 0.14.9 (MIT) wraps a tonic service in a layer so it serves gRPC-Web without an external proxy. Unary and server streaming only. [25][26]
  - `connectrpc` 0.9.1 (Apache-2.0, 2026-09-21; repo `connectrpc/connect-rust`) serves Connect, gRPC and gRPC-Web, all four streaming types, as a `tower::Service` that fits axum or hyper. The RFC page reports HTTP/1.1 and HTTP/2 support. It is pre-1.0 ("may shift in 0.x"). It uses `buffa`, not `prost`; the RFC says a prost adapter is "feasible if ecosystem pressure demands it". Reported conformance: 100% on the connectconformance v1.0.5 categories listed. [27][28][26]
  - Codegen for connect-rust is `buf generate` with `protoc-gen-buffa` and `protoc-gen-connect-rust`, or `connectrpc-build` from `build.rs`. [27]
- Generation with protobuf-es: install `@bufbuild/protoc-gen-es` and `@bufbuild/buf` as dev dependencies, configure a `local: protoc-gen-es` plugin in `buf.gen.yaml`, run `buf generate`. The README says the plugin also works with `protoc`. [14][10]

## Inference

- The spec text does not yet make 3.10 satisfiable for a browser. Native gRPC needs HTTP trailers and full-duplex framing that `fetch` does not provide, so the console needs a Connect or gRPC-Web endpoint. ARFC 0008 section 2's "JSON over HTTP" is not defined (route shape, `Watch` framing, error body). The API must therefore name one browser protocol, or the console will call something that is not "generated from the same definitions".
- Client and bidirectional streaming almost certainly cannot reach a browser under any option here (gRPC-Web and tonic-web say so; `fetch` request streaming is not part of the supported baseline stated by Connect-ES). Console features should not depend on them. `Watch` (server streaming) works under Connect and gRPC-Web.
- An OpenAPI-derived client is a weaker fit. OpenAPI cannot express `Watch` streams in general, and it would be generated from a derived artifact rather than the proto files that 3.10 names. Not verified against an Alloy generator, since none exists.
- The 300 KiB compressed budget (ARFC 0019 section 7) is likely met by the protobuf-es + Connect-ES pair (about 28 KiB gzip for the runtime before tree shaking, 2.4 KiB for `connect-web`), but generated code size for nine services is unmeasured.
- `cargo xtask` could own generation: a subcommand (for example `cargo xtask codegen`) runs `buf generate` for the TypeScript output (and Rust output if the spec wants it), and `cargo xtask ci` regenerates and fails on diff. This needs Node plus pinned `buf` and `protoc-gen-es` on the build machine for any change that touches the console. How the pin is held (npm lockfile) is a choice for the spec task.
- `cargo deny` does not see npm. ADR 0035 and `deps.md` would need an npm license and advisory check (for example in `xtask`), or the permissive-license rule is unenforced for the console.
- Choosing connect-rust moves the Rust side off the standing `prost` choice. Choosing tonic + `tonic-web` keeps `prost` but limits browsers to gRPC-Web and needs a separate JSON surface.

## Unknown

- Whether `connectrpc` and its transitive tree pass `deny.toml` rules, its `unsafe` usage, and its transitive crate count. Not measured. It pulls `buffa`, `serde`, and optionally `zstd` (native C build). [27]
- Transitive count, `unsafe` use, and advisories for `tonic-web`. Not measured.
- npm advisories for the TypeScript candidates. Not checked.
- Connect-ES behavior for client and bidirectional streaming in browsers, `rawDetails`, and streaming error handling: not found in the pages read.
- Real generated-code size and tree-shaken bundle size for Alloy's services.
- Whether `buf generate` output is byte-deterministic across versions and platforms. The tutorial page does not say.
- Whether ARFC 0008's "JSON over HTTP" was intended to be Connect-compatible. The spec is silent.

## Options

| Option | For | Against |
|---|---|---|
| A. protobuf-es + Connect-ES, server speaks Connect (connect-rust, axum) | One protocol for browsers and curl. JSON and binary, GET for reads, streaming over HTTP/1.1. Errors carry typed `details`. Also serves gRPC and gRPC-Web on one registration | connect-rust is pre-1.0 and uses `buffa`, not the standing `prost`. Supply-chain review needed. Two protobuf stacks if tonic is used elsewhere |
| B. protobuf-es + Connect-ES with `createGrpcWebTransport`, server uses tonic + tonic-web | Keeps `prost` and tonic (both active, MIT/Apache-2.0). No proxy. Same TS client code | Unary and server streaming only. A separate JSON/OpenAPI surface still has to be built and kept in step. No GET caching |
| C. `ts-proto` with a custom or grpc-web transport | ISC, active | No official Connect or fetch transport. We would write and maintain the transport and error mapping. grpc-web paths need a proxy or tonic-web |
| D. Google `grpc-web` | Mature, Apache-2.0 | Needs a proxy or tonic-web, no client or bidi streaming, `protoc` plus `protoc-gen-js` toolchain |
| E. OpenAPI-generated client (`openapi-typescript`, `@hey-api/openapi-ts`) | Matches the existing `/openapi.json` promise. No protobuf runtime in the browser | Not generated from the proto files. No `Watch`. Depends on an OpenAPI generator that does not exist yet. Slower or pre-1.0 releases |

Recommendation: protobuf-es with Connect-ES for the TypeScript side, in either A or B, since it is the only candidate here with an official fetch transport, typed error details, and server streaming that is actively maintained. The spec task should pick the server side: B keeps `prost` and costs nothing in policy; A gives a real JSON and streaming surface at the price of a pre-1.0 dependency and a change to the standing choice.
