# R-0004: Which crates should back consensus, the embedded state store, and cryptography

- Task: T-0014
- Used by: ARFC 0006 section 5 (seams `log-store`, `state-store`), ARFC 0003 section 3.1, `agent/eng/crypto.md`

Crate versions and publication dates below are from crates.io as queried while writing this note (latest non-yanked stable release at that time). Repository activity is from the code host API. Advisory data is from the RustSec advisory database snapshot taken while writing.

## Answer

- Consensus: `openraft` 0.10.0 fits the "Raft through openraft" default. It is pre-1.0 and async, not sans-I/O, but its runtime is a pluggable trait, which is the seam a simulator needs. `raft` (tikv raft-rs) is the only true I/O-free alternative, but it is unreleased since March 2023 and hard-depends on `protobuf` 2.x, which is hit by RUSTSEC-2024-0437.
- Embedded store: `redb` 4.5.0 fits the default. It has zero normal dependencies, a documented crash-recovery design, and a stable format claim. `fjall` 3.1.13 is the credible alternative (LSM, fits a Raft log well). `heed` is blocked by the LMDB license (OpenLDAP is not on the allowlist). `canopydb` says "do not trust it with production data".
- Cryptography: every crate in `agent/eng/crypto.md` passes license, maintenance and advisory checks at the versions listed in section "Cryptography" below. `rustls` needs a provider choice that the allowlist rules do not yet settle (`aws-lc-rs` builds C; `ring` has had no release since 2025-03).
- Noise: `snow` 0.10.0 can run the ARFC 0003 handshake (IK with XChaChaPoly, BLAKE2s, 25519, custom protocol name string) behind the `use-xchacha20poly1305` feature, but it pulls the previous RustCrypto generation (0.10 era, `curve25519-dalek` 4.1.3), and it cannot produce the section 3.3 key schedule as written. See "Noise handshake".

## What the sources say

### Consensus

- `openraft` 0.10.0 is MIT OR Apache-2.0, published 2026-11-10, 74 non-yanked versions, repository pushed the day this note was written. [1][2]
- Its README says "Upgrades before `1.0.0` may include incompatible changes", that `main` is 0.10.0 and that release-0.9 gets bug fixes only. [3]
- Membership: "Any set of nodes can be changed in one operation", using "one log entry when safe or joint consensus otherwise". Source also documents rejected unsafe transitions (`UnsupportedMembershipTransition`). [3][4]
- Snapshots: snapshot replication to lagging nodes, snapshot building by policy or on demand, pluggable snapshot transport. [4]
- Storage traits are `RaftLogStorage`, `RaftLogReader`, `RaftStateMachine`, `RaftSnapshotBuilder`, with a reusable test `Suite` for storage implementations in `openraft::testing::log`. Its rules: logs consecutive, all write IO serialized (vote and log together). [4]
- Runtime: `AsyncRuntime` is a trait in `openraft-rt` (spawn, sleep, `Instant`, timeout, `ThreadLocalRng`, channels, mutex). Tokio, compio and monoio are offered; a `deterministic_rng` and a `testing` module exist in `openraft-rt`. [4][5]
- The consensus core (`engine`) is documented as an event in, command out state machine ("Engine ... emits several Commands to let the underlying Runtime take place"), but the module is `pub(crate)`. The public API is `Raft<C>` driving tasks on the `AsyncRuntime`. No mention of "sans-I/O" anywhere in the crate source or docs. [4]
- Testing claims: a Turmoil deterministic simulation fuzzer in CI, and a Jepsen suite with eight nemesis scenarios on each push to main. [3]
- Default features are `tokio-rt` and `clap`. Direct dependencies at 0.10.0 include `chrono`, `clap` (optional), `rand` 0.10, `futures-util`, `thiserror` 2, `tracing`, `anyerror`, `validit`, `derive_more`. [6]
- `unsafe`: 1 real use (`src/log_id/std_log_id.rs:17`, a pointer cast); the other `unsafe` tokens in a text search are comments. [4]
- `raft` (tikv raft-rs) 0.7.0 is Apache-2.0, published 2023-03-07, 13 versions. Repository pushed 2026-05-13. [1][2]
- raft-rs provides "the core Consensus Module only" with user-supplied log, state machine and transport. The API is `RawNode` with `ready()` and `advance()`, i.e. it is I/O-free. `propose_conf_change` and `apply_conf_change` exist, and the crate has `confchange` and `quorum` modules with joint-consensus support. [7][8]
- raft-rs 0.7.0 declares `protobuf = "2"` as a non-optional dependency. RUSTSEC-2024-0437 (uncontrolled recursion in `protobuf`, patched in >= 3.7.2) therefore applies to any build that links it. Default features add `slog` logging crates. [8][9]
- `async-raft` 0.6.1 was last released 2021-05-19 and is the ancestor of openraft. `raft-engine` (tikv) is a log store, not a consensus library. [1][3]

### Embedded store

- `redb` 4.5.0 is MIT OR Apache-2.0, published 2026-11-05, 77 versions, pushed the day of writing, 2 open issues, MSRV 1.90, zero normal dependencies. [1][2][6]
- Design: copy-on-write B+trees, MVCC with concurrent readers and one writer, XXH3_128 checksums in a Merkle-style tree. Default commit is "1PC+C" with one `fsync`, relying on a single-byte atomic "god byte" flip and verification of checksums on open. Optional 2PC commit uses two `fsync`s and makes the primary slot guaranteed valid. Non-durable commits exist and remain consistent. [10]
- Stated media assumptions: single-byte writes are atomic, writes are durable after `fsync`, and bytes outside a written range do not change on power loss. [10]
- XXH3 is not cryptographic: "Users who need to accept malicious input are encouraged to use 2PC". [10]
- File format described as stable with "a reasonable effort to provide an upgrade path". [11]
- Space: freed pages are reused only after readers that may reference them finish. Compaction exists and needs an exclusive writer. Savepoints cost about 64 kB per 1 GB of values. [10]
- Published numbers (author's machine): individual writes redb 920 ms vs lmdb 1598 ms vs rocksdb 2432 ms; batch writes redb 1595 ms vs rocksdb 451 ms vs fjall 353 ms. No write amplification figure is published. [11]
- `unsafe`: a text search finds 54 occurrences of the word in `src` (includes comments), no crate level `forbid(unsafe_code)`. [6]
- `fjall` 3.1.13 is MIT OR Apache-2.0, published 2026-10-25, 54 versions, MSRV 1.90, 47 transitive crates. LSM tree via `lsm-tree`, one LSM per keyspace, journal, transactional modes (`SingleWriterTxDatabase`, `OptimisticTxDatabase`). By default writes go to OS buffers, not disk; `persist(PersistMode::SyncAll)` syncs. States a "stable disk format" with migration on major versions. No write amplification figures published. [12]
- `heed` 0.23.1 is MIT but statically links LMDB (C), which is under the OpenLDAP license; its README says users must comply with both. Opening an environment is `unsafe`. About 342 occurrences of `unsafe` in `src`. 67 transitive crates. [13]
- `canopydb` 0.2.5 is MIT, last release 2025-11-22, 162 stars, and its README says "early stage software" and "Do not trust it with production data". [14]
- `sled` 0.34.7 was last released 2021-09-12 and is a beta; `rocksdb` 0.25.0 is Apache-2.0 and wraps C++. Both are listed only to show why they were not evaluated further. [1]

### Cryptography

Versions are the latest stable on crates.io. "Tree" is the count of unique normal transitive dependencies with default features, from `cargo tree`.

- `chacha20poly1305` 0.11.0 (2026-06-28): "has received one security audit by NCC Group, with no significant findings", of an earlier release (report dated 2020-02). Portable software implementation "only constant time on processors which implement constant-time multiplication". No `unsafe` tokens found. Supports XChaCha20Poly1305. [15]
- `x25519-dalek` 3.0.0 and `ed25519-dalek` 3.0.0 (2026-07-06): BSD-3-Clause, `no_std` with `default-features = false`. ed25519 says signing is constant time and keys zeroize on drop, and sets `forbid(unsafe_code)`. The only audit I found is Quarkslab's 2019 review of `curve25519-dalek`, `subtle` and a lighter look at the two wrappers; it predates current code. [16][17]
- `curve25519-dalek` is under both. A timing variability advisory (RUSTSEC-2024-0344) is patched in >= 4.1.3; the 3.0.0 wrappers use curve25519-dalek 5.0.0. ed25519-dalek RUSTSEC-2022-0093 is patched in >= 2. [9][17]
- `blake2` 0.11.0 (2026-08-26), `hkdf` 0.13.0 (2026-03-30), `hmac` 0.13.0 (2026-03-29), `sha2` 0.11.1 (2026-10-12), `argon2` 0.6.0 (2026-08-27): all MIT OR Apache-2.0. Advisories on file (`blake2` RUSTSEC-2019-0019, `sha2` RUSTSEC-2021-0100) are for versions far older than these. I found no audit statement in their READMEs. `argon2` supports Argon2id, `no_std`. [9][15]
- `blake3` 1.8.7 (2026-08-20): CC0-1.0 OR Apache-2.0 OR Apache-2.0 WITH LLVM-exception. About 238 `unsafe` occurrences (SIMD backends). No advisories on file. Released 6 times in the last 12 months. [9][2]
- `subtle` 2.6.1 (2024-06-24): BSD-3-Clause. Its README calls it a "best-effort" attempt at constant time. Last release is older than 12 months at the time of writing, but it is small and finished. `zeroize` 1.9.1 (2026-10-06): Apache-2.0 OR MIT, `no_std`. [18]
- `rustls` 0.23.46 (2026-10-14): Apache-2.0 OR ISC OR MIT. Seven advisories on file in 2024 to 2026; the latest four (RUSTSEC-2026-0346 to 0349, published 2026-10-14) are all patched in >= 0.23.46 and include a downgrade to classical key exchange and exposure of secrets via `Debug`. Its default provider is `aws-lc-rs` 1.19.0 with `aws-lc-sys` 0.47.0 (C code; license string `ISC AND (Apache-2.0 OR ISC) AND Apache-2.0 AND MIT AND BSD-3-Clause ...`, no OpenSSL clause in the 0.47.0 metadata). The `ring` crate 0.17.14 was last released 2025-03-11. [9][19]

### Noise handshake

- `snow` 0.10.0 (2025-07-19, repository pushed 2026-07-06), Apache-2.0 OR MIT. "has not received any formal audit". Tracks Noise revision 34; implements everything except the fallback modifier. [20]
- XChaChaPoly (not in the Noise spec) is available behind the feature `use-xchacha20poly1305`. [20]
- Its XChaChaPoly nonce is 16 zero bytes followed by the 64-bit counter little-endian: `nonce_bytes[16..]` is `nonce.to_le_bytes()` (source: `snow-0.10.0/src/resolvers/default.rs`, XChaChaPoly `encrypt`). That is the layout ARFC 0003 section 3.1 describes, except that the ARFC does not state the byte order of `n`. [20][21]
- `NoiseParams` has a public `name: String` and a `NoiseParams::new(name, base, handshake, dh, cipher, hash)` constructor, and `SymmetricState::initialize` hashes or zero pads whatever name it is given. So a protocol name such as `alloy/al/handshake/v1` can be used. It is 21 bytes, shorter than the BLAKE2s output, so Noise rules pad it with zero bytes. [20]
- Providers can be replaced with `Builder::with_resolver` and the `CryptoResolver` trait (`resolve_rng`, `resolve_dh`, `resolve_hash`, `resolve_cipher`). That is the route to feed randomness from the `alloy-rt` trait. [20]
- `HandshakeState` exposes `set_psk`, `get_handshake_hash`, `dangerously_get_raw_split`, `into_transport_mode`. It does not expose the final chaining key. [20]
- `snow` 0.10.0 depends on `blake2` 0.10, `chacha20poly1305` 0.10 and `curve25519-dalek` 4.1.3 (Cargo.toml in the crate), not the 0.11 / 3.0 generation in `agent/eng/crypto.md`. With `default-features = false` plus XChaChaPoly, 25519 and BLAKE2s its tree is 29 crates. [20]
- RUSTSEC-2024-0011 (unauthenticated nonce increment in `snow`) is patched in >= 0.9.5. [9]
- `clatter` 2.3.0 (2026-08-30), MIT, 45 stars, `no_std`, post-quantum hybrid patterns, no audit. It has no XChaChaPoly (source search finds none), and takes handshakes as compile time types. [22]
- `noise-protocol` 0.2.1 is licensed Unlicense, which is not on the allowlist. [1]

## Inference

- openraft is not sans-I/O, but the sans-I/O property that matters to ADR level simulation (every clock, task and random draw goes through a trait we own) is met through `AsyncRuntime`. `alloy-rt` would implement that trait for production (tokio) and for the simulator. Whether every timer and spawn inside openraft goes through the trait, so that a run replays bit for bit, is not proven here: only a task that builds it on the simulator can show that.
- If strict sans-I/O were a hard requirement, only raft-rs matches it today. Its cost is a protobuf 2.x hard dependency (open advisory), no release for over three years, and the user writing leader lease, read index and snapshot orchestration themselves.
- Control plane writes are small and mostly appended (Raft log), then applied into a state store. redb's copy-on-write path costs roughly one rewritten leaf plus its parent path per commit, while an LSM (fjall) amortizes the cost into sequential writes and later compaction. Neither project publishes a write amplification number, so any claim about the ratio is unmeasured.
- redb's default 1PC+C commit relies on XXH3 checksums to detect a torn commit, which is not an attack on an authenticated store, but the log and state live on disk that an attacker with local write access could alter. Choosing 2PC for the Raft vote and log is the conservative reading of redb's own caveat. The cost is a second `fsync` per commit.
- The 8 GiB per group limit and the 64 MiB batch limit in ARFC 0006 section 7 are well within the sizes redb and fjall are used at. No limit in either project's documentation contradicts them, but none was tested.
- `snow` is a workable base for ARFC 0003 section 3.1 because Noise IK message 1 is `e, es, s, ss` plus an encrypted payload, which gives exactly 32 + (32+16) + (16+16) bytes, and message 2 is 32 + (4+16) bytes. The `mac1`, `mac2`, cookie, `sender_index` and counter replay logic sit outside Noise either way and must be written by Alloy.
- ARFC 0003 section 3.3 derives `send_key`, `recv_key` and a 14 byte `salt` from "the final chaining key" by HKDF. Noise's `Split` derives two keys from the chaining key itself, and `snow` returns only those two keys (or the handshake hash), never the chaining key. The ARFC's derivation therefore cannot be reproduced on snow unless the ARFC changes to start from the split outputs or the handshake hash, or snow is forked or the handshake assembled from primitives.
- The ARFC also does not say where the pre-shared key slot sits (Noise psk0, psk1, psk2). Response fields (ephemeral plus encrypted payload, no static) are consistent with IKpsk2 as used by WireGuard, but that is an inference.
- Using `snow` means two generations of dalek, blake2 and chacha20poly1305 in one build unless a custom resolver routes primitives to the 0.11/3.0 crates; the resolver can supply the primitives while `snow` still compiles its own optional copies if the features stay on. Rule 1 of `agent/eng/crypto.md` (only `alloy-crypto` depends on primitives) is kept if `snow` is also depended on only from `alloy-crypto`.
- Assembling the handshake from primitives is about 300 lines (symmetric state, IK token processing, PSK mixing) but it is a new construction implementation, which crypto.md rule 2 puts in the deep tier exception and which has no external audit either; `snow` is also unaudited.

## Unknown

- Whether openraft reads any wall clock, thread local RNG or spawns outside `AsyncRuntime` (determinism on the `alloy-rt` simulator).
- Write amplification, in numbers, for redb and fjall under a Raft log workload with durable commits.
- Whether redb 4.x has had a published crash consistency test result under power loss or injected fault testing, beyond its own design document.
- Whether any audit covers `chacha20poly1305` 0.11 or `x25519-dalek` / `ed25519-dalek` 3.0 releases (only 2019/2020 audits of older code were found).
- Whether `aws-lc-sys` builds on every Alloy target without extra toolchain requirements (C compiler, possibly CMake), and its precise license text for the shipped version. Only crates.io metadata was read.
- Which pre-shared key position ARFC 0003 intends.
- The upstream's release plans for openraft 1.0.

## Options

### Consensus

| Option | For | Against |
|---|---|---|
| `openraft` 0.10.0 | Active, MIT OR Apache-2.0, joint-consensus membership, snapshots, storage test `Suite`, pluggable `AsyncRuntime`, Turmoil and Jepsen testing upstream | Pre-1.0 with breaking changes between minors (0.10 released two days before this note), not sans-I/O, 73 to 103 transitive crates, `chrono` and `rand` 0.10 enter the tree |
| `raft` (raft-rs) 0.7.0 | I/O-free `RawNode`, joint consensus, battle tested in TiKV | Last release 2023-03, hard `protobuf` 2.x dependency hit by RUSTSEC-2024-0437, `slog` default logger, we write everything around it |
| Own Raft in `alloy-ctl` | Full control, truly sans-I/O | Class P risk (consensus safety), far more than one task, no external review |

Recommendation: `openraft`, pinned to an exact version, with `default-features = false`. The deciding reason is that it is the only actively maintained candidate that passes `deps.md` and its runtime seam covers the simulator. The caveat is the unproven replay determinism, so the task that wires it into `alloy-rt` should gate on a seed replay test.

### Embedded store

| Option | For | Against |
|---|---|---|
| `redb` 4.5.0 | Zero normal dependencies, MIT OR Apache-2.0, documented commit and recovery design, stable format claim, fastest individual writes in its own table, 2PC available | Single writer, copy-on-write cost, MSRV 1.90, no published write amplification, 1PC+C relies on non-cryptographic checksums |
| `fjall` 3.1.13 | LSM suits append heavy logs, MIT OR Apache-2.0, stable format claim, faster batch writes in redb's table | Default does not sync (must call `persist` with `SyncAll`), compaction adds background IO, 47 transitive crates, no published write amplification |
| `heed` 0.23.1 (LMDB) | Mature engine, very fast reads | OpenLDAP license is not on the allowlist, C code, mmap and `unsafe` open, 67 crates |
| `canopydb` 0.2.5 | Low write amplification claimed, WAL | "Do not trust it with production data", format not stable, one maintainer |

Recommendation: `redb` for both seams, with durable 2PC commits for the Raft vote and log and the default commit mode for the state store, subject to the ADR. The deciding reason is the dependency free tree and the documented recovery design. Keep `fjall` as the fallback if a measured log workload shows redb's commit cost is too high; the `LogStore` seam makes it replaceable.

### Cryptography

Recommendation: confirm every row in `agent/eng/crypto.md` at the versions in the table above, with `rustls` pinned at >= 0.23.46 because of the 2026-10-14 advisories. The provider choice for `rustls` (`aws-lc-rs` needs a C build and a license review of `aws-lc-sys`; `ring` has had no release in over 12 months) needs a decision in an ADR before the first task that builds TLS.

### Noise handshake

| Option | For | Against |
|---|---|---|
| `snow` 0.10.0 with `use-xchacha20poly1305`, inside `alloy-crypto` | Existing, many users, matches ARFC nonce layout, custom protocol name allowed, resolver trait for randomness | Unaudited, old RustCrypto generation, no access to the chaining key so ARFC 3.3 must change, one past nonce advisory |
| Assemble from primitives in `alloy-crypto` | Exactly the ARFC, one dependency set | New construction code, needs deep tier handling and review, also unaudited |
| `clatter` 2.3.0 | Has hybrid patterns for the reserved slot, explicit RNG argument | No XChaChaPoly, 45 stars, unaudited |

Recommendation: write the ARFC change first (section 3.3 key schedule from split outputs, byte order of `n`, psk position), then use `snow` behind `alloy-crypto` with a custom resolver. The deciding reason is that this keeps Alloy from implementing the Noise state machine, which is what crypto.md rule 1 and 2 push against. If the ARFC key schedule is frozen as written, only assembly from primitives satisfies it.
