# R-0006: Do current browsers accept Ed25519 TLS server certificates, and what key types must the API CA and API server certificate use for the console to load

- Task: T-0034
- Used by: arfc-0002 section 2 (API CA key row), arfc-0008 section 3.8 (API certificate), arfc-0019 sections 2 and 3.2.4 (console served at the API endpoint, browser support)

## Answer

No. Chromium and Firefox do not offer Ed25519 as a verifiable TLS signature scheme and their certificate verifiers have no Ed25519 signature algorithm, so an Ed25519 server key, or any Ed25519 signature anywhere in the chain, will not load the console [1][2][3][4][5]. For Safari it is unknown: Apple documents only RSA and EC key types and no source shows Ed25519 working [9][10]. The CLI side is fine: `rustls` with either default provider verifies Ed25519 chains, shown by running it. To load the console the API server certificate key and every signature in its chain, including the API CA key, must be ECDSA P-256 (or RSA).

## What the sources say

Chromium (stable on the research date is 158.0.8127.37 [11]; source read at tip, not at the 157 or 158 tags):

- Chrome's TLS client sets an explicit verify list, `kVerifyPrefs`: ML-DSA-44/65/87, ECDSA P-256/P-384 with SHA-2, RSA-PSS SHA-256/384/512, RSA PKCS#1 SHA-256/384. `SSL_SIGN_ED25519` is absent. Ed25519 is therefore not in the `signature_algorithms` Chrome sends [1].
- BoringSSL's own default verify list `kVerifySignatureAlgorithms` also omits Ed25519, while its signing list `kSignSignatureAlgorithms` includes it (BoringSSL can sign Ed25519 as a server or client, but does not accept it by default as a verifier) [2].
- Chromium's certificate path validator (BoringSSL `pki`) has a `SignatureAlgorithm` enum with RSA PKCS#1, ECDSA, RSA-PSS, ML-DSA, and a Merkle-tree proof value, and no Ed25519; the string "25519" does not occur in `signature_algorithm.h` [3]. So an Ed25519-signed certificate cannot be validated either.
- Chrome 137 (May 2025) shipped Ed25519 in the Web Cryptography API only. That is a different code path from TLS [12].

Firefox (stable on the research date is 160, ESR 153 [13]; source read at mozilla-central tip, not at release tags):

- NSS defines the code point (`ssl_sig_ed25519 = 0x0807`) but `defaultSignatureSchemes` lists only ECDSA, RSA-PSS, RSA PKCS#1, DSA, and ML-DSA schemes [4][5].
- In the scheme-policy switch, `ssl_sig_ed25519` is grouped with `ssl_sig_none` and `ssl_sig_ed448` and returns `PR_FALSE` [4]. In the hash-mapping switch it falls into the assert-fail group [4].
- Bug 1325335 added an EdDSA implementation to NSS's library layer and is resolved fixed. Its one comment on TLS says TLS support would "require some work" and was not scheduled [6]. The bug does not say TLS was done.

Safari / Apple:

- Apple's TLS security guide lists RSA and EC keys ("minimum 2048-bit RSA key or 256-bit elliptic curve key") and ECDSA/RSA cipher suites. It does not mention Ed25519 or EdDSA [9].
- Apple's trusted certificate requirements for iOS 13 and macOS 10.15 list RSA key size and SHA-2 signature requirements. They do not mention Ed25519 [10].
- Safari 17 added Ed25519 to WebCrypto, which is not TLS [14].

CLI (`rustls`):

- `rustls` 0.23.46 with the `ring` provider, and the `aws-lc-rs` provider by source reading, map `SignatureScheme::ED25519` to webpki's `ED25519` verification algorithm. The `aws-lc-rs` mapping is at `src/crypto/aws_lc_rs/mod.rs:210`, the `ring` one at `src/crypto/ring/mod.rs:140` [7].
- A doc comment in `rustls` on loading EdDSA keys says Ed25519 "does not have wide support in browsers" and is not supported by the WebPKI because the CA/Browser Forum Baseline Requirements do not allow it for publicly trusted certificates (`src/crypto/aws_lc_rs/sign.rs:83-86`) [7]. This is a library author's statement, not the Baseline Requirements text.

## What was verified by running

Experiment: `rustls` 0.23.46 (`ring` provider only, default features off), `rustls-webpki` 0.103.17, `rcgen` 0.13.2. Generate a CA and a leaf with `rcgen`, both of one key type, and verify the leaf with `WebPkiServerVerifier`.

```
$ cargo run -q    (ten-line program: CA + leaf of one key type, verify_server_cert for "api.test")
ed25519 chain: verify_server_cert = Ok("ok")
ed25519 chain: supported_verify_schemes = [ECDSA_NISTP384_SHA384, ECDSA_NISTP256_SHA256, ED25519, RSA_PSS_SHA512, RSA_PSS_SHA384, RSA_PSS_SHA256, RSA_PKCS1_SHA512, RSA_PKCS1_SHA384, RSA_PKCS1_SHA256]
p256 chain: verify_server_cert = Ok("ok")
p256 chain: supported_verify_schemes = [same list]
```

Not run: the `aws-lc-rs` provider (needs a C toolchain; source reading only), and any real browser. No browser is installed in the research environment, so every browser statement rests on source code and documentation, not on a handshake.

## Inference

- A server using an Ed25519 key cannot complete a TLS 1.3 handshake with Chrome or Firefox: the client never offers `ed25519`, and a TLS 1.3 server must pick a scheme from the client's list (RFC 8446 section 4.2.3). The expected failure is a handshake error before any page loads. Not observed.
- Using ECDSA only for the leaf while the CA stays Ed25519 does not work either: the leaf's signature would be Ed25519, and Chromium's validator has no Ed25519 signature algorithm [3]. The reverse (ECDSA CA, Ed25519 leaf) fails on the leaf key as above. So the whole chain, keys and signatures, must avoid Ed25519.
- Because the trust anchor is pinned by the CLI and must be installed by the user in the browser, the root being self-signed does not matter; what matters is the key that signs the leaf.
- Absence in tip source suggests the same holds for the previous major versions of Chromium and Firefox, since neither has a change that adds it. No release-by-release check was made.
- Safari most likely behaves like the others, because Apple lists only RSA and EC. This is a guess; no Apple source says Ed25519 is rejected.
- The CLI does not constrain the choice: its verifier handles Ed25519 and ECDSA P-256 alike, and it pins the CA fingerprint, so it works with any of the options below.

## Unknown

- Whether Safari (macOS 26 and the previous major) accepts an Ed25519 server certificate. Needs a test on Apple hardware.
- Behavior of the previous major versions (Chromium 157, Firefox 159 or ESR) checked at release tags; only tip was read.
- Whether any browser flag or enterprise policy enables Ed25519 in TLS.
- Whether the `aws-lc-rs` provider verifies an Ed25519 chain when run (source mapping present, not executed).
- Real-handshake confirmation for any browser.

## Options

| Option | For | Against |
|---|---|---|
| A. Change the API CA key to ECDSA P-256, issue ECDSA P-256 API server certificates | One CA, one chain, works in the browsers read and on the CLI. Smallest change to ARFC 0002 section 2 (one row) | Adds ECDSA P-256 to `alloy-crypto` and to the primitives table in `agent/eng/crypto.md`, which needs an ADR. Key is no longer Ed25519 like the other keys |
| B. Keep Ed25519 for all cluster keys; add a separate ECDSA P-256 API CA used only for API TLS (the "API CA key" row changes type, nothing else does) | Same effect as A in the table. Makes explicit that no other key changes | Same as A. It is the same option stated differently, since the API CA is already a separate key |
| C. Keep an Ed25519 API CA; use ECDSA only for the TLS certificate | No change to the table | Does not work: the leaf would carry an Ed25519 signature that Chromium cannot validate [3] |
| D. Keep Ed25519 and drop the browser requirement of ARFC 0019 3.2.4, or require a public ACME certificate for the console | Table unchanged | Breaks 3.2.4 on private clusters. ACME certificates are ECDSA or RSA, so this works only for clusters with a public name (ARFC 0008 3.8) |
| E. RSA-2048 or larger for the API CA and certificates | Accepted everywhere, including Safari, with no doubt | Slower to generate, larger, and RSA is a new primitive for the project |

Recommendation: option A (equivalently B). The deciding reasons: it is the only one that meets ARFC 0019 3.2.4 on a private cluster, it works in Chromium and Firefox by source, and ECDSA P-256 is the one key type Apple documents as accepted [9]. Before freezing, run the Safari handshake test listed under Unknown. The choice, and whether it needs a pivotal-decision ADR for the change to `agent/eng/crypto.md`, belongs to the spec task.
