# R-0005: Licenses inside the Cloud Hypervisor UEFI images

- Task: T-0019
- Used by: arfc-0011 section 5 (the `cloud-hypervisor` implementation of the `hypervisor` seam); the ADR choosing which firmware Alloy ships (`agent/eng/deps.md`, ADR 0035)

## Answer

Release `ch-97eeb7b09` of the Cloud Hypervisor edk2 fork builds `CLOUDHV.fd` (x86_64) and `CLOUDHV_EFI.fd` (aarch64) with no iPXE (GPLv2) driver and no Intel E1000 driver. The only network driver in either image is the in-tree `VirtioNetDxe`. The Intel E1000 driver enters an OVMF build only with `-D E1000_ENABLE` plus a manually downloaded binary, and the release workflow passes neither. The only copyleft-licensed source linked is libfdt in the aarch64 image, which is dual licensed `GPL-2.0-or-later OR BSD-2-Clause` and can be taken under BSD-2-Clause. This is established from the build recipe and sources; the shipped binaries were not decomposed (compressed volumes), so the claim is "by construction", not "by inspection".

## What the sources say

Release examined: edk2 fork tag `ch-97eeb7b09` (commit `97eeb7b0901da9f7b5d98a2e6a5e8694978298e9`), published 2026-09-22, assets `CLOUDHV.fd` (4194304 bytes) and `CLOUDHV_EFI.fd` (3145728 bytes) [1][2]. It is the release named in R-0002.

Build configuration the release uses:

- The workflow `release.yaml` runs on every push and builds both images in GitHub Actions on ubuntu-24.04 [3].
  - x86_64: `OvmfPkg/build.sh -p OvmfPkg/CloudHv/CloudHvX64.dsc -a X64 -b RELEASE`, artifact `Build/CloudHvX64/RELEASE_GCC/FV/CLOUDHV.fd` [3].
  - aarch64: `build -p ArmVirtPkg/ArmVirtCloudHv.dsc -a AARCH64 -t GCC -b RELEASE --pcd gEfiMdeModulePkgTokenSpaceGuid.PcdDxeNxMemoryProtectionPolicy=0xC000000000007FD1`, artifact `Build/ArmVirtCloudHv-AARCH64/RELEASE_GCC/FV/CLOUDHV_EFI.fd` [3].
  - No `-D` flags are passed. Submodules are initialised with `git submodule update --init --recursive` [3].
- Platform defaults (x86_64 DSC) [4]: `SECURE_BOOT_ENABLE = FALSE`, `SMM_REQUIRE = FALSE`, `NETWORK_TLS_ENABLE = FALSE`, `NETWORK_IP6_ENABLE = FALSE`, `NETWORK_HTTP_BOOT_ENABLE = FALSE`, `NETWORK_ISCSI_ENABLE = TRUE`, `NETWORK_PXE_BOOT_ENABLE = TRUE`, `BUILD_SHELL = TRUE`; TPM2 off by default (`TPM2_ENABLE = FALSE`) [8]. `E1000_ENABLE` is not defined in the DSC or in `CloudHvDefines.fdf.inc` [4][9].
- Platform defaults (aarch64 DSC): `SECURE_BOOT_ENABLE = FALSE`, `NETWORK_TLS_ENABLE = FALSE` [5].

Components named in `OvmfPkg/README` that are the subject of the question:

- iPXE NIC drivers (GPLv2): the README says they are separate prebuilt drivers shipped with the qemu source distribution and "automatically available to and configured for OVMF in the default qemu installation", i.e. qemu loads them as PCI option ROMs [19]. Neither CloudHv FDF lists any iPXE driver: the x86_64 FDF network section has an `E1000_ENABLE` conditional, `Network.fdf.inc` and `VirtioNet.inf` only [6], and the aarch64 FDF lists `VirtioNet.inf` only and has no network include [7]. The only mention of iPXE is documentation.
- Intel proprietary E1000 driver `E3522X2.EFI`: it is embedded only if the builder passes `-D E1000_ENABLE`, after downloading Intel's driver pack and placing the file at `Intel3.5/EFIX64/E3522X2.EFI` [19][6]. In the CloudHv x86_64 FDF this is a `!if $(E1000_ENABLE)` block placing a `FILE DRIVER` with `SECTION PE32 = Intel3.5/EFIX64/E3522X2.EFI` [6]. The flag is not set by the release workflow [3], so the block is not built. The README text restricts the flag to `OvmfPkgX64.dsc` and `OvmfPkgIa32X64.dsc` [19]; the CloudHv FDF carries the block anyway, which is an inheritance quirk, but it is inactive.
- The README says the NIC drivers are "independent" of the virtio-net driver, which "is located in OvmfPkg/VirtioNetDxe" and is part of the default build [19].

Build tooling (not shipped): nasm 2.15.05, iasl, gcc, BaseTools [3]. Not part of the image.

The string scan is weak evidence only: the DXE volume in an OVMF-style flash image is LZMA compressed, so a zero count does not prove absence. The build-recipe analysis above is the main evidence. The images were not built, and no tool that unpacks the volumes (for example UEFITool) was run.

## Inference

- Because the workflow passes no `-D` flags and the DSC defaults do not define `E1000_ENABLE`, the released x86_64 image contains no Intel E1000 driver. The aarch64 DSC and FDF have no E1000 or iPXE reference at all. Inferred from [3][4][5][6][7], not by unpacking the binaries.
- No GPL-only or proprietary component is in the released images. The one GPL-mentioning component, libfdt (aarch64), is offered under BSD-2-Clause by its dual license; relying on that is a license-election question, which `agent/core/3-autonomy.md` classes as pivotal if Alloy must decide it.
- A "build without them" already exists: it is the fork's default release build. Nothing needs to be left out by flags or source changes. Alloy would only need to ensure that anyone rebuilding the firmware does not pass `-D E1000_ENABLE`.
- Guests that need a NIC at the UEFI stage (PXE, iSCSI boot) get only virtio-net. Cloud Hypervisor's own device is virtio-net, so this is consistent with ARFC 0011; not checked against the ARFC text.
- Alloy would run these images as separate program inputs passed with `--firmware`, not link them, so `agent/eng/deps.md` "Not dependencies" (seam implementations get an ADR license review) applies rather than the crate allowlist. Inference from R-0002 [20].

## Unknown

- The exact module list inside the shipped binaries. Not unpacked.
- Whether OpenSSL is actually pulled into each image (depends on which modules call `BaseCryptLib`; `IScsiDxe` and image verification are candidates). Either way it is Apache-2.0.
- The license of the LZMA SDK copy used by `LzmaCustomDecompressLib`, and of `MdeModulePkg/Logo/Logo.bmp` used by `LogoDxe`. Neither was read. These are not named in `OvmfPkg/README`.
- Whether the UEFI Forum / Microsoft Secure Boot default keys are embedded: `SECURE_BOOT_ENABLE = FALSE` in both DSCs, so no key enrollment payload is expected, but this was not checked in the FDF.
- Whether the fork's repository license (reported NOASSERTION by the GitHub API in R-0002 [21]) has any file outside `License.txt` that differs. Only the files above were read.
- The licenses of the other submodules (mbedtls, brotli, oniguruma, jansson, libspdm, TCG TPM reference code) were not examined because the CloudHv DSCs read do not use them: no `MbedTls`, `Brotli`, `Onig` or `Spdm` strings appear in `CloudHvX64.dsc` [4]; TPM2 defaults to FALSE [8]; for aarch64 only `OpensslLib` and `FdtLib` appear in the library mappings [5].

## Options

| Option | For | Against |
|---|---|---|
| A. Use the fork's released `CLOUDHV.fd` and `CLOUDHV_EFI.fd` as they are | No GPL-only or proprietary component by the build recipe; BSD-2-Clause-Patent, Apache-2.0 (OpenSSL), and a dual-licensed libfdt that can be taken as BSD-2-Clause; no build step for Alloy | Not verified at binary level; relies on the aarch64 libfdt dual-license election; fork has no tagged versions beyond commit-named releases |
| B. A, plus a short task to unpack both images (for example with UEFITool) and list the module GUIDs and strings against the DSC/FDF | Turns the "by construction" claim into evidence before the ADR; also settles the OpenSSL, LZMA and Logo unknowns | Needs a tool outside the repository; small extra task |
| C. Build the firmware from the fork at the same tag in Alloy's own pipeline | Alloy controls flags and provenance; can never accidentally enable E1000 | Needs a toolchain (nasm, iasl, gcc, BaseTools) and an owner; build was out of scope here; adds supply chain surface |

Recommendation: B, then A. The recipe shows the default release is clean, and the one remaining gap (binary inspection plus the libfdt election) is small and can be closed before the ADR is written. C is justified only if Alloy wants reproducible firmware provenance for other reasons.
