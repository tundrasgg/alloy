# R-0003: Which NAT and firewall behaviors must the lab model, as which named presets, and what path class does each pairing reach?

- Task: T-0005
- Used by: ARFC 0005 section 3.4 (presets, matrix), ARFC 0004 section 3.3 (normative matrix), `tests/natlab/matrix.toml`

## Answer

- Model the eight axes of ARFC 0005 section 3.4. They cover RFC 4787 (mapping, filtering, port assignment, hairpin, timeout) plus layering, family and UDP reachability. Two corrections are proposed below: the timeout range (30 to 300 s) and the keepalive margin.
- Twelve presets are proposed (section "Presets"), covering home, CGN, cloud, mobile, enterprise, IPv6-only and UDP-blocked networks.
- Under ARFC 0004 version 1 rules, 55 of the 144 ordered pairs reach `direct`. The rest are `relayed` (table in "Pairing table").
- The deciding rule: direct works unless both sides have endpoint-dependent mapping, or one side has endpoint-dependent mapping and the other has address-and-port-dependent filtering, or there is no common IP family, or either side blocks UDP.
- Published numbers: about 11% of peers behind endpoint-dependent mapping (2011); cellular CGN about 40% symmetric (2016); DCUtR hole punching about 70% in the wild (2025). No source measures a clean share per preset.

## What the sources say

### Behavior axes (RFC 4787)

- Mapping: a NAT MUST have endpoint-independent mapping (REQ-1, section 4.1). Variants are address-dependent and address-and-port-dependent. [1]
- Port assignment: port overloading is forbidden (REQ-3). Port parity preservation is recommended (REQ-4). [1]
- Mapping timer: MUST NOT expire in under 2 minutes unless the port is well known (REQ-5); recommended default 5 minutes or more (REQ-5c); outbound traffic MUST refresh (REQ-6). [1]
- Filtering: endpoint-independent recommended when application transparency matters; address-dependent when stricter filtering is wanted (REQ-8). [1]
- Hairpinning: MUST be supported (REQ-9), and the hairpinned packet MUST carry the external source address and port (REQ-9a). [1]
- ICMP must not terminate a mapping (REQ-12). [1]
- CGN (RFC 6888): paired IP pooling default (REQ-2), endpoint-independent filtering recommended, address-dependent allowed (REQ-7), freed ports held 120 s (REQ-8), ports should be hard to guess (REQ-15). RFC 6888 defers UDP timers to RFC 4787 and says nothing on hairpinning. [3]
- IPv6 CPE (RFC 6092): inbound default deny (section 2.3); UDP state not expired under 2 minutes, default 5 minutes (REC-14); default filtering endpoint-independent for unmanaged gateways, address-dependent allowed (REC-17). [4]

### Discovery tests (RFC 5780)

- Mapping (4.3): Test I checks connectivity and whether the mapped address equals the local one. Test II sends to the server's alternate address, same port: same mapped endpoint means endpoint-independent. Test III sends to the alternate address and port: same as Test II means address-dependent, otherwise address-and-port-dependent. [2]
- Filtering (4.4): Test II asks for a reply from a changed IP and port: a reply means endpoint-independent filtering. Else Test III asks for a changed port only: a reply means address-dependent, none means address-and-port-dependent. [2]
- Binding lifetime (4.6): binary search over idle time, using a second port with RESPONSE-PORT to test whether the first binding is alive. [2]
- Hairpin is described in section 3.4 and has no test in section 4. Attributes: CHANGE-REQUEST 0x0003, RESPONSE-ORIGIN 0x802b, OTHER-ADDRESS 0x802c. RESPONSE-ORIGIN helps detect double NAT. [2]
- Consequence for the lab: the lab's classification tests can be written as RFC 5780 conformance checks against each preset, so a preset's axis values are verified by the same procedure real devices are.

### Real devices

- Linux conntrack UDP timeouts: 30 s for a one-way flow, 120 s once traffic is seen both ways ("stream"). [5]
- Residential CPE leave the source port unchanged in more than 92% of non-CGN sessions. CPE with strictly symmetric mapping: under 2% of tests. [6, section 6.2 and 6.5]
- CGN port allocation (non-cellular / cellular): preserving 41.2% / 27.9%, sequential 22.2% / 26.0%, random 35.6% / 44.7%. Chunk allocation (small per-subscriber port blocks) in 4.6% / 3.7% of ASes. [6, Table 6]
- CGN mapping: among non-cellular CGN ASes, 11% have symmetric as the most permissive mapping seen. Cellular is bimodal: about 40% symmetric and about 20% full cone. [6, section 6.5]
- UDP timeouts: 74% of detected NATs expire idle UDP state after 1 minute or less; observed 10 to 200 s; median CGN 65 s cellular and 35 s non-cellular; CPE mostly 65 s. The probe only waited up to 200 s and 30.9% of tests saw no expiry. [6, sections 6.3, 6.5]
- Cellular device addresses are mostly 10/8 (58.7%) and 100.64/10 (17.3%); non-cellular CGN-side device addresses are 192.168/16 for 92.4%. [6, Table 4]
- AWS NAT gateway: idle connections time out at 350 s and then answer with RST (TCP). The page does not state mapping or filtering behavior. [7]
- GCP Cloud NAT: public NAT with endpoint-independent mapping exists only with static port allocation; it cannot be combined with dynamic port allocation; ports 0 to 1023 are not used; 64,512 UDP ports per NAT IP. The page states no filtering behavior or UDP timeout. [8]
- Tailscale describes cloud NAT gateways and office routers as the typical "hard" NATs (endpoint-dependent mapping), home routers as generally "easy", and the Berkeley guest Wi-Fi as an example of blocking all outbound UDP except DNS, which only a relay over HTTPS gets around. [9]
- UDP NAT check data (2005, user submitted): UDP hole punching works through 310 of 380 (82%) of tested NATs, hairpin through 80 of 335 (24%). Linux-based 81% / 12%, Linksys 98% / 12%. [10]

### Measured prevalence

- Halkes and Pouwelse (2011, BitTorrent-like network): about 64% of peers sit behind a NAT or firewall where punching should work, and over 80% of attempts between them succeed. About 11% of peers were behind endpoint-dependent mapping (figure quoted by [11]). [11, 12]
- Richter et al. (IMC 2016): over 90% of cellular ASes deploy CGN; 17 to 18% of non-cellular eyeball ASes do. CGN is stricter than CPE. [6, section 5, 6.5]
- Trautwein et al. (arXiv 2510.27500, IMC 2026 version arXiv 2604.12484): libp2p DCUtR, 4.4 million attempts from over 85,000 networks, 167 countries, hole-punch stage success 70% +- 7.1%; TCP and QUIC about equal; 97.6% of successes on the first attempt. The sample is volunteer clients and may overestimate. No per-NAT-class split in the paper. [11, 13]
- ProbeLab follow-up on the live IPFS network: Port-Restricted Cone 19.6% of classified peers, 82.9% success; address-and-port-dependent filtering with mapping unresolved 42.5%, 37.0% success; symmetric 3.9%, 39.7% success but the authors doubt it; directly reachable 8.3%. [14]
- Tailscale's own estimate: simultaneous probing after STUN gives direct connections "over 90% of the time". This is an estimate, not a study. [9]

### Open source harnesses

- Tailscale `tstest/natlab`: a simulated network. `SNAT44` has `Type` (EndpointIndependentNAT, AddressDependentNAT, AddressAndPortDependentNAT), `MappingTimeout` (default 30 s), an optional `Firewall` with its own `Type` (address-and-port-dependent default, address-dependent, endpoint-independent) and `SessionTimeout` (30 s). So mapping and filtering are modeled separately, as in ARFC 0005. IPv4 only. [15]
- Tailscale `tstest/natlab/vnet`: four named NATs: `One2OneNAT`, `EasyNAT` ("address+port filtering"), `EasyAFNAT` ("address filtering (not port)"), `HardNAT`. The type comment says easy is Linux-style and hard is FreeBSD-style. The mapping and port rules of each are not in the doc comments. A `NATTable` interface lets implementations pick the outgoing source and incoming destination; implementations must not read real time. [16]
- libp2p (rust-libp2p, go-libp2p): ProbeLab reports a controlled testbed covering "every relevant RFC 4787 NAT and transport combination". How the NATs are built is not stated on the page. [14]
- Not found or not checked: harnesses based on network namespaces and nftables beyond that, Mininet-based work, and the pion/ICE test suites. Treated as unknown.

### Port prediction (one paragraph, out of scope)

Tailscale's analysis: one side with an easy NAT and the other hard, with 256 ports open on the easy side, random probing from the hard side succeeds 50% with 174 probes, 64% with 256, 98% with 1,024, 99.9% with 2,048 (birthday paradox). Both hard: about 0.01% after 20 s of 256 and 2,048 probes, and about 170,000 probes each for 99.9%. Router session tables (64,000 sessions on one named device) can be exhausted by this. [9] ARFC 0004 section 9 already defers this to M1.

## What was verified by running

I wrote a small model of the probing procedure in ARFC 0004 section 3.2 and ran it over all 144 ordered pairs of the presets below. Model assumptions: one anchor; each node first contacts the anchor from the data socket and learns its reflexive endpoint; each side then probes the other's reflexive endpoint for 5 rounds; an authenticated probe arriving from an unexpected source is answered at that source (peer-reflexive reply, ARFC 0004 section 3.4 last bullet); dependent mappings take random fresh ports (no prediction); direct means a packet was delivered both ways. The script is not committed; it is about 90 lines and the rule it implements is stated in "Inference" so it can be re-derived. 200 seeds per pair gave one result per pair.

```
$ python -I natsim.py
|1 full-cone|D|D|D|D|D|D|D|D|D|D|R|R|
|5 enterprise-symmetric|D|D|R|R|R|R|R|R|R|R|R|R|
|12 udp-blocked|R|R|R|R|R|R|R|R|R|R|R|R|
asym: []
direct 55 of 144
```

(Three rows shown; the full table is below.) The result is symmetric: no ordered pair differs from its reverse.

## Presets

Names are proposals. "src" gives the source for the behavior; "inf" means chosen by inference where no source states the value. Layers are given as inner + outer, and the effective behavior is the more restrictive of the two on each axis (mapping dependent if either layer is; filtering the stricter).

|---|---|---|---|---|---|---|---|---|---|---|---|
| 1 | `full-cone` | Router with a UPnP/forwarded port, or a host with a public IP | EI | EI | preserving | yes | 120 s | single | v4 | allowed | RFC 4787 REQ-8, REQ-9 [1]; share of full cone about 8% [14]; timeout inf from REQ-5 |
| 2 | `addr-restricted` | Consumer router with address-restricted behavior | EI | AD | preserving | no | 65 s | single | v4 | allowed | Tailscale EasyAFNAT [16]; CPE port preservation over 92% [6]; timeout from CPE mode 65 s [6]; hairpin inf from [10] |

Notes on the table:

- `full-cone` also stands in for a host with a public address and no filtering.
- Mobile networks that are IPv6-only with 464XLAT are not modeled separately; `v6-only-fw` against `mobile-symmetric` (both at once) is a relayed pair in the table below because there is no common family in the lab. Whether carrier IPv6 firewalls behave like `v6-only-fw` is unknown.
- Address-dependent mapping is omitted from the presets: against any peer on another IP it behaves as address-and-port-dependent for the probing procedure, and no source reports it as a distinct device class. The model supports it (AD) and the lab should keep the axis value.
- Hairpin is only relevant for two nodes behind the same NAT device. All presets other than `full-cone` are set to no hairpin; sources report 24% overall support [10] and nothing for CGNs [6].

Time bounds to put in the matrix come from ARFC 0004 section 3.2: relayed reachable within 2 s of joining, direct active within 5 s of first traffic. Every R pair must be relayed-reachable within 2 s, including `udp-blocked`, which needs the `stream` underlay and so waits 3 s for UDP replies from every anchor (ARFC 0004 section 3.6). Inference: the 2 s bound cannot hold for `udp-blocked` at join; the matrix needs a separate bound for it, or section 3.6 needs a shorter wait. See Issues.

## Inference

- The rule behind the table. Let Y be the receiving side. A probe from X reaches Y only if (1) Y's mapping is the one it advertised, which holds if Y has endpoint-independent mapping or an endpoint-independent filter, and (2) Y's filter admits X's actual source. X's actual source equals X's advertised endpoint only if X has endpoint-independent mapping. So: EI mapping on both sides is always direct; one EI-mapped side with address-dependent or endpoint-independent filtering works against a dependent-mapping peer; EI mapping with address-and-port filtering against a dependent-mapping peer fails (that is what port prediction would fix); dependent mapping on both sides fails (no preset here has endpoint-independent filtering on a dependent-mapping NAT, which would pass).
- ARFC 0004 section 3.3 says "when both sides are behind endpoint-dependent NATs, version 1 stays on the relay". The table agrees. It is silent on the mixed case. The table shows `full-cone` and `addr-restricted` reaching `direct` against symmetric peers. That needs the peer-reflexive reply (answer a probe at the source it came from). ARFC 0004 section 3.2 probes "every candidate pair" and section 3.4 moves the return path only for data; if the reply-at-source behavior is not in version 1, rows 1 and 2 against columns 5, 7, 8 and 10 become R. The matrix should state which.
- Layered NAT is reduced to one effective NAT for this table. That ignores an extra hop of timeout (the shorter of the two applies) and hairpinning at the inner layer, which does not matter between different homes.
- Numbers for how common each preset is cannot be derived from these sources. The sources classify with the old cone vocabulary (full, restricted, port-restricted, symmetric) which does not map one to one onto the mapping and filtering axes.
- Timeout margin. The keepalive is 25 s (ARFC 0004 section 3.4). The axis lower bound is 30 s, leaving 5 s. Richter observed timeouts down to 10 s and 74% of NATs at 1 minute or less [6]. So 25 s is safe for most devices and unsafe for a minority; a lab preset with a timeout under 25 s should exist to show the failure and the 3-keepalive failure rule working. This is a recommendation, not in the presets above.

## Unknown

- Filtering behavior and UDP timeout of AWS NAT gateway, GCP Cloud NAT, and Azure NAT Gateway for UDP, from primary documentation. AWS documents 350 s idle timeout and says nothing on mapping behavior [7].
- Share of home routers that are address-restricted versus port-restricted versus full cone: no published measurement that separates them on the RFC 4787 axes.
- Share of enterprise firewalls with endpoint-dependent mapping.
- Whether carrier IPv6 firewalls use endpoint-independent or address-and-port filtering.
- Hairpin support of CGNs: no measurement found.
- How the libp2p testbed builds its NATs, and whether any other open source project publishes a model of named NAT devices beyond Tailscale's.
- Whether nftables can express every axis value for real mode (ARFC 0005 section 3.5). Not checked here. Mapping endpoint-independence and filtering modes in particular should be tested before the real mode scripts are specified.

## Options

| Option | For | Against |
|---|---|---|
| A. Adopt the 12 presets and the table as the normative matrix | Covers every ARFC 0005 axis value at least once; each preset has a source or is marked as inference; symmetric and verified by a model | Rows 1 and 2 against symmetric peers depend on peer-reflexive replies that the ARFC does not state; several values are inference |
| B. Adopt the presets but mark rows 1 and 2 against columns 5, 7, 8, 10 as R | Matches the narrowest reading of version 1; no spec change needed | Gives up connections that need no port prediction and that the simulator would otherwise reach |
| C. Cut to 8 presets (drop 2, 6, 9, 10) | Smaller matrix | Loses the address-restricted case, the double layer with endpoint-independent mapping and both cloud cases, which are the cases where outcomes differ |

Recommendation: A, with a spec clarification that an authenticated probe is answered at the source it arrived from. The deciding reason is that the model shows the extra direct pairs need no port prediction, and the lab should say so in the matrix instead of leaving it to the implementation.
