# R-0008: Which rustls crypto provider, and which library produces the ECDSA P-256 keys and signatures ARFC 0002 section 2 requires

- Task: T-0048
- Used by: ARFC 0002 section 2, ARFC 0008 section 3.8, `agent/eng/crypto.md` (the "once its ADR chooses one" row), the ADR that settles the `rustls` provider (R-0004 left it open)

Crate versions are the latest non-yanked releases on crates.io on the day of writing. Source line numbers are from the unpacked crate sources of exactly those versions. Repository activity is from the GitHub API.

## Answer

- No `rustls` provider can meet ARFC 0002 section 2 for its own ECDSA signing. `ring` 0.17.14, `aws-lc-rs` 1.19.0 and `graviola` 0.4.5 all choose the signing nonce from their own random source, hedged with the key and message, and none takes a random source from the caller or exposes pure RFC 6979. `rustls-rustcrypto` 0.1.0-pre.0 uses the RustCrypto randomized signer, which also mixes in `getrandom` bytes. See "Nonces and randomness".
- The requirement is met by a split, and the split works. `p256` 0.14.0 + `ecdsa` 0.17.0 + `rfc6979` 0.6.0 (RustCrypto, MIT OR Apache-2.0, no `unsafe` token) generate the key from any `rand_core` 0.10 `CryptoRng`, so the `alloy-rt` trait can be adapted, and sign by pure RFC 6979 through the plain `Signer::sign`. `rustls` takes that key through its public `SigningKey` and `Signer` traits, so the provider is chosen on other criteria. I ran this end to end with three providers (below).
- `rcgen` 0.14.10 (MIT OR Apache-2.0) builds the API CA certificate, leaf certificates and PKCS#10 CSRs with an external signer. With its default features off it has no `ring` or `aws-lc-rs` dependency and 10 other crates in its tree, but then it needs an explicit serial number and an explicit key identifier.
- Provider: see Options. In short, `aws-lc-rs` and `ring` work today; `rustls-rustcrypto` is the only pure Rust choice in the same RustCrypto generation as the rest of `alloy-crypto`, but it is pre-release, tells its users not to use it in production, and fails `cargo deny` advisories through `paste`.

## What the sources say

### Nonces and randomness

- ARFC 0002 section 2 requires every Alloy P-256 signature (API CA key and API server certificate key) to use RFC 6979 section 3.2 nonces with SHA-256, so that signing draws on no random source, and requires the private keys to be generated from the `alloy-rt` randomness trait. `spec/arfc-0002-identity-and-join.md` section 2, last bullet. [1]
- `ring` 0.17.14: `EcdsaKeyPair::sign` is documented "using a random nonce generated by `rng`" (`src/ec/suite_b/ecdsa/signing.rs:172`), hedges it with the digest (`:183`), and draws the scalar with `private_key::random_scalar(..., rng)` (`:249`). The `rng` parameter is `&dyn SecureRandom`, whose supertrait lives in a private `sealed` module (`src/rand.rs:23`, `:62`), so a caller cannot implement it; only `SystemRandom` (`:162`) exists. Key generation (`generate_pkcs8`, `signing.rs:82`) takes the same sealed trait. Importing an existing scalar is possible (`from_private_key_and_public_key`, `:136`). [2]
- `aws-lc-rs` 1.19.0: `EcdsaKeyPair::sign` ignores its random argument (`src/ec/key_pair.rs:224`, `_rng`), and so does `generate_pkcs8` (`:118`). The C code underneath, `aws-lc-sys` 0.47.0 `aws-lc/crypto/fipsmodule/ecdsa/ecdsa.c`, hashes the private key and digest into "additional data" and calls `ec_random_nonzero_scalar` for `k` (lines 276 to 300; comment: "Pass a SHA512 hash of the private key and digest as additional data into the RBG. This is a hardening measure against entropy failure"). The only entry points with a caller chosen nonce are named `..._for_known_answer_test` and `..._and_leak_private_key_for_testing` (`ecdsa.c:223`, `:251`). [3][4]
- `graviola` 0.4.5: `sign` fills 16 bytes from `SystemRandom` (`src/high/ecdsa.rs:190` to `192`) and passes them to the private `rfc6979_sign_with_random`, documented "RFC6979 deterministic ECDSA signing, _with added randomness_" (`:227`). The deterministic form is reachable only inside the crate (its tests call it, `:592`). [5]
- `rustls-rustcrypto` 0.1.0-pre.0: its P-256 `SigningKey::choose_scheme` returns `GenericRandomizedSigner` (`src/sign/ecdsa.rs`, `impl_ecdsa!`), whose `sign` creates `getrandom::SysRng` and calls `try_sign_with_rng` (`src/sign.rs:32` to `35`). The `ecdsa` 0.17.0 `RandomizedSigner` impl fills a field size array from the rng and passes it to `sign_prehashed_rfc6979` as the `ad` argument (`src/signing.rs:225` to `232`), so the output is not the plain RFC 6979 value. The crate also has `GenericSigner` (`src/sign.rs:45` to `62`), which calls plain `try_sign`, but the ECDSA keys do not use it. [6][7]
- RustCrypto `ecdsa` 0.17.0 plain `Signer::try_sign` goes to `PrehashSigner::sign_prehash`, which is `sign_prehashed_rfc6979::<C, C::Digest>(&secret_scalar, prehash, &[])` with empty additional data (`src/signing.rs:171` to `172`). `sign_prehashed_rfc6979` builds `rfc6979::KGenerator` and loops `fill_next_k` (`src/hazmat.rs:102` to `124`). No rng is involved. The randomized variants are separate traits (`RandomizedSigner`, `src/signing.rs:225`). [7]
- Key generation in `ecdsa` 0.17.0: `impl Generate for SigningKey<C>` calls `NonZeroScalar::<C>::try_generate_from_rng(rng)` for any `R: TryCryptoRng` (`src/signing.rs:132` to `138`), which does rejection sampling on the caller's rng (`elliptic-curve` 0.14.3 `src/scalar/nonzero.rs:200` to `209`). The old `SigningKey::random` is deprecated (`signing.rs:123`). `rand_core` 0.10.1 defines `TryRng` (three methods) and the marker `TryCryptoRng` (`src/lib.rs:189`, `:249`), so an adapter over the `alloy-rt` trait is a short impl. [7][8]

### What `rustls` lets a caller replace

- `rustls::sign::SigningKey` has `choose_scheme`, `public_key`, `algorithm`; `Signer` has `sign(&self, message) -> Vec<u8>` and `scheme()` (`src/crypto/signer.rs:59` to `88`). The TLS 1.3 server calls `signer.sign(message)` for `CertificateVerify` (`src/server/tls13.rs:845`). `CertifiedKey::new(chain, Arc<dyn SigningKey>)` (`signer.rs:180`) plus a `ResolvesServerCert` implementation bypasses the provider's key loading. [9]
- `CryptoProvider` has `secure_random: &'static dyn SecureRandom` and `key_provider: &'static dyn KeyProvider` (`src/crypto/mod.rs:213`, `:216`). Ephemeral key exchange and the hello randoms come from the provider, not from the key, so no stock provider draws TLS handshake randomness from `alloy-rt` (`rustls-rustcrypto` uses `getrandom::SysRng`, `src/lib.rs:66` to `67`, `src/kx.rs:19`). ARFC 0002 requires `alloy-rt` only for the long term private keys, but a simulator that wants byte identical handshakes would need a custom provider. [6][9]
- `rustls` 0.23.46 default features include `aws_lc_rs`; features `ring` and `aws-lc-rs` select a provider; `custom-provider` exists (`Cargo.toml` `[features]`). [9]

### Certificates and CSRs

- `rcgen` 0.14.10: trait `SigningKey: PublicKeyData` with one method `sign(&self, msg) -> Result<Vec<u8>, Error>`; `PublicKeyData` needs `der_bytes()` and `algorithm()` (`src/key_pair.rs:660`, `:757` to `771`). `CertificateParams::self_signed`, `signed_by(&key, &Issuer)` and `serialize_request(&key)` accept any `impl SigningKey` (`src/certificate.rs:140`, `:154`, `:334`). [10]
- `rcgen`'s own `KeyPair` generates and signs through the `SystemRandom` of `ring` or `aws-lc-rs` (`src/key_pair.rs:97`, `:236`), so `KeyPair` must not hold Alloy's keys. [10]
- The `crypto` feature (default, through `ring`) is the only thing that pulls `ring` or `aws-lc-rs`; it is a compile error to enable `crypto` with neither (`src/ring_like.rs:50`). With it off, a missing serial number is an error (`src/certificate.rs:470`) and the default key identifier method is `PreSpecified(vec![])` (`:102` to `105`), so both must be set. `#![forbid(unsafe_code)]` (`src/lib.rs:29`). [10]
- The CSR path refuses a serial number, an authority key identifier flag, name constraints and CRL points (`src/certificate.rs:387` to `392`, `UnsupportedInCsr`), so the CSR must be built from separate parameters. Its docs say repeated calls "will not produce the exact same output"; with an RFC 6979 signer and the `crypto` feature off they did (below). [10]

## What was verified by running

Scratch crate outside the repository: `rcgen` 0.14.10 (default features off, feature `pem`), `p256` 0.14.0, `ecdsa` 0.17.0 (feature `der`), `rand_core` 0.10.1, `sha2` 0.11, `rustls` 0.23.46 with the provider chosen by a cargo feature. It generates keys from a fixed seed `TryCryptoRng`, signs through `p256`'s plain `Signer`, wraps the key as `rcgen::SigningKey` and as `rustls::sign::SigningKey`, builds a self-signed P-256 CA, a leaf with SAN `api.test` and a CSR, then runs an in-memory TLS 1.3 handshake whose server chain is leaf plus CA.

## Inference

- Because `rustls` accepts any `SigningKey`, the provider question and the signing question are independent. Whatever provider is picked, the API CA key and the API server key are `p256` keys wrapped by Alloy: key generation over the randomness trait, a `rcgen::SigningKey`, a `rustls::sign::SigningKey`, and PKCS#8 encode and decode for storage through `p256`'s `pkcs8` feature. Adding `p256`, `ecdsa`, `rfc6979`, `rcgen` and what they pull in is a class N decision under `agent/eng/deps.md`.
- ACME needs a CSR signed by the certificate key (`rcgen` `serialize_request`, shown working) and an account key for JWS requests. If the account key is ES256 it is also an ECDSA P-256 signature Alloy makes, and ARFC 0002's "every ECDSA P-256 signature Alloy makes" arguably covers it. I did not resolve whether the clause is meant to; it is a spec question.
- With a stock provider, the provider's own P-256 code is used to verify (the CLI checking the API CA chain, a pinned fingerprint verifier). Verification has no nonce, so a provider's hedged signer never runs for Alloy's keys as long as they are not loaded through the provider's `key_provider`.
- The provider choice affects the build story more than the cryptography: `aws-lc-rs` and `ring` need a C compiler; `aws-lc-rs` adds a larger C tree and more build crates; the pure Rust choices need none, which suits "any hardware from one board", at the cost of maturity.
- `ring` brings `getrandom` 0.2 next to the `getrandom` 0.4 that the RustCrypto generation uses (`rustls-rustcrypto` resolved `getrandom` 0.4.3 in the experiment). That would trip `multiple-versions = "deny"` if the Alloy tree contains both. I did not build the Alloy workspace, so this is unconfirmed.
- The ARFC 0002 property "the same key signing the same message yields the same signature" fails for every hedged signer read here. Only the RustCrypto plain `Signer` path passes it.

## Unknown

- Whether browsers (ARFC 0019 clause 3.2.4) accept the experiment's certificates. Not tested; R-0006 covers algorithm support.
- Whether `rustls-rustcrypto` will reach a stable release, and when. Its first non-alpha version is 3 days old at the time of writing.
- Whether `ring` will release again. Activity on `main` is high; no statement about release plans was found in `README.md` or `RELEASES.md`.
- Whether `aws-lc-sys` builds on every Alloy target without extra toolchain steps. One Windows host was tried.
- Whether the Alloy workspace's full dependency graph produces duplicate versions under any option. Not built.
- `rcgen` behavior for features the experiment did not use: name constraints, CRLs, the ACME identifier extension, importing an existing CA through `x509-parser`.
- Any independent audit of `p256` 0.14 or `ecdsa` 0.17: none found; the README says none exists.
- `unsafe` counts for `graviola` and `rustls-rustcrypto`: not measured.

## Options

| Option | For | Against |
|---|---|---|
| A. `rustls` with the `aws-lc-rs` provider; P-256 keys and signing from `p256`, `ecdsa`, `rfc6979`; certificates from `rcgen` (default features off) | `rustls` default, frequent releases, FIPS build possible later, widest suite and platform coverage; handshake verified | C compiler plus extra build crates, large C tree with a multi-license string, 383 lines with `unsafe`, two P-256 implementations in the binary (one verify only) |
| B. Same split with the `ring` provider | Smaller C and assembly tree than A, permissive license; handshake verified | No release since 2025-03-11 and 0.17.15 unreleased, pulls `getrandom` 0.2 beside RustCrypto's 0.4 |
| C. Same split with `rustls-rustcrypto` (pure Rust) | No C anywhere, same RustCrypto generation as the other `alloy-crypto` crates, one P-256 implementation, simplest cross compilation; handshake verified | `0.1.0-pre.0`, README says not for production, not audited or FIPS, few suites, `paste` (RUSTSEC-2024-0436) fails the current `cargo deny` advisories check until ignored or removed upstream, pulls `rsa` 0.10 |
| D. Same split with `graviola` | No C compiler, formally verified assembly routines, fast | x86_64 and aarch64 only with CPU features that exclude Raspberry Pi 4 and older boards, README says very new; Alloy targets any hardware from one board. Not run in the experiment |
| E. A custom `CryptoProvider` assembled from the `alloy-crypto` primitives | Only crates already approved; would allow TLS randomness from `alloy-rt` | New cryptographic glue, which `agent/eng/crypto.md` rules 1 and 2 discourage; most of it is what option C already is |
| F. Use a provider's own ECDSA signing and amend ARFC 0002 to allow hedged nonces | No custom signer | Contradicts ADR 0048 and ARFC 0002 as written, and loses the same input same signature property |

Recommendation: the split (P-256 from `p256`, `ecdsa`, `rfc6979`, with `rcgen` as the certificate builder) regardless of provider, because no provider meets the nonce rule. For the provider, A if a C toolchain is acceptable now; the provider is one `CryptoProvider` value, so moving later does not touch the signing code. C if "no C anywhere" outweighs pre-release status, in which case the `paste` advisory needs an ADR-recorded ignore or an upstream fix first. The deciding trade is a mature provider with a C toolchain (A) against a young pure Rust one (C); the evidence here does not make B or D preferable to A.
