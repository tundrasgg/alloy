# R-0002: Cloud Hypervisor capabilities against ARFC 0011

- Task: T-0004
- Used by: arfc-0011 section 5 (the `cloud-hypervisor` implementation of the `hypervisor` seam); the license ADR for that seam (`agent/eng/deps.md`)

## Answer

Version examined: v54.1 (the latest release, a security point release). Cloud Hypervisor supports every capability asked for except where noted: balloon runtime resize is not documented, Windows on aarch64 is not documented, and the 3 s create-to-first-instruction and 500 ms migration downtime targets have no published measurement. The gaps that matter for ARFC 0011 are: vhost-user needs guest memory `shared=on`, live migration is version-bound (n-2, forward only, since v54), postcopy is unavailable with vhost-user devices, and Landlock cannot admit paths after start (hotplug of file-backed disks needs a pre-declared rule). The license is Apache-2.0 AND BSD-3-Clause; the UEFI firmware is BSD-2-Clause-Patent; Rust Hypervisor Firmware is Apache-2.0.

## What the sources say

Status key: supported, partial, unsupported, unknown (sources silent).

| Capability | Status | Version | Detail [source] |
|---|---|---|---|
| x86_64 | supported | v54.1 | "main supported architectures are x86-64 and AArch64" [1] |
| aarch64 | supported | v54.1 | Needs GICv3; recommended host kernel 5.13 [1]. v54.0 added firmware-aided direct kernel boot via `fw_cfg`, ACPI on direct boot with `acpi=on`, SMBIOS [2] |
| vhost-user-net | supported | v54.1 | Used as `--net ...,vhost_user=true,socket=...,num_queues=N,vhost_mode=server` in the project's OVS example; requires `--memory ...,shared=true` (hugepages in that example) [3]. v54.0: MAC and MTU taken from the backend, malicious-backend crash fix [2]. The doc's prose says client mode and its command says `vhost_mode=server`; the option exists, which side Alloy uses is a choice |
| vhost-user-blk | supported | v54.1 | CH is the client; connects to the backend's socket: `--disk ...,vhost_user=true,socket=...,num_queues=4,queue_size=128`; guest memory must be shared [4]. `docs/memory.md`: `shared=on` is the recommendation for vhost-user, hugepages not required [5] |
| Direct kernel boot | supported | v54.1 | `--kernel`; x86_64 needs PVH or bzImage [1] |
| UEFI boot | supported | v54.1 | EDK II fork firmware `CLOUDHV.fd` (x86_64) and `CLOUDHV_EFI.fd` (aarch64), passed to `--firmware` [6] |
| Hotplug of disks, NICs | supported | v54.1 | `add-disk`, `add-net`, `remove-device`; PCI hotplug needs ACPI, on arm64 direct boot that means `acpi=on` and a kernel with `CONFIG_EFI` and `CONFIG_ACPI` [7]. Caveat: under Landlock, hotplugging file-backed resources without a matching rule fails with permission denied [8] |
| Hotplug of vCPUs | partial | v54.1 | x86 only [7]. ARFC 0011 does not require it |
| Live migration | partial | v54.1 | TCP (mutual TLS with `tls_dir`) between hosts, UNIX socket on one host [9]. Disks, kernel, initramfs must be at the same paths on both hosts [9]. Forward migration from the previous two releases (n-2) from v54; no backward migration [9][2]. `releases.md` says migration is not supported across major versions, which conflicts with [9]; the v54.0 release note and `live_migration.md` agree with each other and are newer than the generic statement, so treat n-2 as current [2][9][10]. Postcopy is not supported with VFIO, vDPA, vfio-user or vhost-user devices [9]. Default target downtime `downtime_ms` 300, `timeout_s` 3600, `timeout_strategy` `cancel` or `ignore` [9]. On failure before the VM reaches the destination it should resume on the source [9]. Source and destination fully trust each other; listener reachability equals management power [11]. Same-architecture requirement is not stated in the docs read |
| Control API | supported | v54.1 | REST over a UNIX socket (`--api-socket path=` or `fd=`), JSON; `vm.create/boot/info/reboot/shutdown/delete/pause/resume`, `vm.snapshot/restore`, `vm.send-migration/receive-migration/cancel-migration`, `vm.add-*`, `vm.remove-device`, `vm.resize`, `vm.power-button`, `vm.balloon-stats`. Optional D-Bus API, not compiled by default; event monitor [12] |
| seccomp | supported | v54.1 | On by default, violation kills the process; `--seccomp false|log|errno` [13]. v54.0 gave the main thread its own filter [2] |
| Landlock | supported | v54.1 | Opt-in per VM at `vm_create` (`--landlock` or `landlock_enable`), path rules `--landlock-rules`; all paths must be known at start [8]. Landlock does not cover AF_UNIX sockets, so namespaces are needed alongside [11] |
| Memory ballooning | partial | v54.1 | virtio-balloon with `size`, `deflate_on_oom`, `free_page_reporting`; stats via `vm.balloon-stats` [14][2]. A runtime resize procedure is not documented in `balloon.md` [14] and `memory.md` describes only virtio-mem for resizing [5] |
| Serial console access | supported | v54.1 | Legacy serial `--serial off|null|pty|tty|file=<path>|socket=<path>` (default null); virtio-console defaults to tty [15][16]. The repository has a `serial_buffer` crate; what it does was not read |
| Windows guests | partial | v54.1 | x86_64 only documented. Tested Windows Server 2019, Server Core 2004, Windows 11 IoT Enterprise LTSC 2024; UEFI only, no BIOS; guest image needs virtio drivers (`viostor`, `NetKvm`); no VGA, console via SAC; Windows 11 with TPM 2.0 reportedly panics; no CPU hot-remove, RAM hot-remove usually fails; hotplug of CPU, RAM, network, disk supported with caveats [17]. README lists Windows 10 and Server 2019 [1]. Windows on aarch64 is not documented. v54.0 fixed balloon requests above 256 pages, which affected Windows guests [2] |

Other facts:

- ACPI shutdown: `vm.power-button` exists in the API [12]. That it maps to the ACPI shutdown ARFC 0011 section 3.1.4 needs is inference.
- Virtio-rng is always enabled, entropy from `/dev/urandom` by default [16]. Matches the "entropy" device in ARFC 0011 section 3.1.2.
- Threat model: guest, guest kernel, initramfs and disk images are untrusted; management interfaces, the host kernel and snapshot files are trusted; a vhost-user backend gets control of the guest but not of the VMM process [11]. Until AF_UNIX restrictions exist, sandbox escapes are not treated as vulnerabilities [11].
- Releases: a major release about every six weeks, point releases as needed, each major gets bug fixes for two further cycles (about 12 weeks), no LTS mentioned. Changes to REST API, CLI or device model get two releases notice [10].
- Activity: repository not archived, with commits within the last day of the check, v54.1 is the latest release [18][19].
- License of the program: `license = "Apache-2.0 AND BSD-3-Clause"` in `cloud-hypervisor/Cargo.toml`; `LICENSES/` holds Apache-2.0, BSD-3-Clause, CC-BY-4.0 texts [20][21].
- Firmware licenses:
  - EDK II fork (`CLOUDHV.fd`, `CLOUDHV_EFI.fd`): upstream `License.txt` states BSD-2-Clause-Patent [22]. The GitHub API reports the fork's license as NOASSERTION [23]. The fork's `OvmfPkg/README` names iPXE NIC drivers as GPLv2 and an Intel E1000 driver under a proprietary agreement [24]; whether the shipped `CLOUDHV` images include either was not established.
  - Rust Hypervisor Firmware: Apache-2.0 per the GitHub API; latest release 0.5.0 (2024-11-30), repository pushed 2026-09-30 [25][26].
  - Latest edk2 fork release `ch-97eeb7b09` published 2026-09-22 with assets `CLOUDHV.fd` and `CLOUDHV_EFI.fd` [27].
- Boot time:
  - The project's performance metrics list `boot_time_ms`, `boot_time_pmem_ms` and 16 vCPU variants with a 2 s timeout per iteration; no pass threshold, and the start and stop points are not defined. The only numbers shown are sample output (mean about 106 ms) that the page says is "for illustration purpose only" [28].
  - No primary documentation of time to first guest instruction was found. Secondary sources (search results, not opened) repeat "under 100 ms" and a KVM Forum 2022 talk is said to report 64 ms for a pmem root with hugepages; neither was verified [29].

## What was verified by running

Nothing was run. This task had no Cloud Hypervisor binary or KVM host, and the environment denied a script fetch, so every row above is from documentation and release notes at tag v54.1. "Supported" here means documented, not tested.

## Inference

- ARFC 0011 section 3.1.3 (under 3 s from `Create` to first guest instruction) is very likely met on the VMM side: the project's own harness times boot with a 2 s timeout and shows about 106 ms in sample output [28]. The dominant costs are in Alloy (clone, vhost-user setup, namespace and cgroup setup), not in the VMM. Not measured.
- Section 3.5 (downtime under 500 ms at 100 MiB/s dirty rate) is plausible given a 300 ms default target, but the target is a goal the migration loop tries to reach, not a guarantee, and `timeout_strategy=ignore` proceeds regardless [9]. Needs a measurement on real hardware.
- The shared-memory requirement for vhost-user is compatible with `alloy-net` and `alloy-blk` as backends, but it forces shared-memory backing for all guest RAM. This interacts with live migration: `memory_mode=memfds` and snapshot copy-on-write modes also depend on shared memory [9][30].
- The seccomp filter is a fixed, built-in filter of Cloud Hypervisor [13], not one generated per guest from its device list. ARFC 0011 section 2 says the filter and Landlock policy "allow only what that guest's devices need". The Landlock policy can be per guest (rules are passed per VM) [8]; the seccomp filter being per guest is not supported by the sources read. Alloy can add its own outer filter around the process.
- Landlock plus hotplug: ARFC 3.1.4 requires hot attach of volumes. With vhost-user-blk the volume is a socket, not a file; whether a socket path needs a Landlock rule, and how AF_UNIX connect is treated, was not established. The threat model says Landlock does not cover AF_UNIX [11].
- Migration crossing releases is limited to n-2 forward. Rolling upgrades of nodes would need to respect that window.

## Unknown

- Time from `vm.create` to first guest instruction in a real configuration (no primary figure).
- Achievable migration downtime at 100 MiB/s dirty rate; behavior with vhost-user backends during migration beyond "devices can be migrated again after a migration" [2].
- Whether live migration requires the same CPU architecture or model on both ends (docs silent; expected, not stated). CPU model compatibility across heterogeneous hosts.
- Runtime balloon resize through the API.
- Windows on aarch64.
- Whether the shipped `CLOUDHV.fd` and `CLOUDHV_EFI.fd` contain GPL or proprietary components (see firmware licenses above).
- Transitive crate dependency count, `unsafe` usage and RustSec advisories of Cloud Hypervisor. Not needed if it runs as a separate process (`agent/eng/deps.md`: seam implementations get an ADR license review), but not collected. v54.0 bumped `rustls` for RUSTSEC-2026-0285 affecting TLS migration [2].
- How Landlock treats vhost-user socket paths.
- Contents of `release-notes.md` beyond v53 (the second half of the file was not read).

## Options

| Option | For | Against |
|---|---|---|
| A. Adopt Cloud Hypervisor v54.x as the first `hypervisor` implementation, as ARFC 0011 assumes | Every required capability is documented; active (six week majors); Rust; seccomp and Landlock built in; REST API suits `alloyd`; permissive licenses for the VMM | Shared guest memory needed for vhost-user; migration bound to n-2 forward; no LTS so upgrades follow a six week cadence; Windows aarch64 and balloon resize unconfirmed |
| B. A with a short measurement task first (boot time, migration downtime with vhost-user backends, Landlock plus vhost-user hotplug) on a real KVM host | Turns the three performance and sandbox inferences into evidence before the conformance suite fixes numbers | Needs a KVM host; delays nothing else since the `mem` implementation exists |

Recommendation: B. The documented feature set matches ARFC 0011, so the choice of Cloud Hypervisor stands. The numeric targets in sections 3.1.3 and 3.5, and the "allow only what that guest's devices need" seccomp wording, are not supported by any measurement or document read and should be checked before the conformance suite freezes them. Filing the Windows aarch64 and balloon-resize questions against the "Windows guests" open question in section 9 is enough for now.
