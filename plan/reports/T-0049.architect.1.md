The named source meets RFC 6979: R-0008 "What was verified by running" reproduces the RFC 6979 appendix A.2.5 P-256 vector through the plain `p256` signer, and `ecdsa` 0.17.0 `src/signing.rs:171` to `172` calls `sign_prehashed_rfc6979` with empty additional data.

External facts for the ACME account key, read from the RFC Editor text:

- RFC 8555 section 6.2 (https://www.rfc-editor.org/rfc/rfc8555.txt): an ACME server "MUST implement the "ES256" signature algorithm" and "SHOULD implement the "EdDSA" signature algorithm using the "Ed25519" variant".
- RFC 7518 section 3.4 (https://www.rfc-editor.org/rfc/rfc7518.txt): the `ES256` JWS signature is R then S, each 32 octets big-endian, "The resulting 64-octet sequence is the JWS Signature value."

## Decisions

- N: `rustls` uses the `aws-lc-rs` provider (R-0008 option A). `rustls-rustcrypto` fails `cargo deny` advisories and says not for production, `graviola` excludes Raspberry Pi 4 and older boards, `ring` has no recent release and risks a duplicate `getrandom`; the cost of A is a C compiler for every target. Recorded in ADR 0053.
- N: the ACME account key is ECDSA P-256 and signs JWS as `ES256` under the ARFC 0002 section 2 nonce and key rules, because RFC 8555 section 6.2 guarantees only `ES256` at every ACME server. ADR 0053 states this narrows ADR 0048's "every other signing key stays Ed25519" by that one key; ADR 0048 was not edited (outside `touches`) and is otherwise unchanged.

## Issues

- `spec-issue`: `spec/arfc-0008-native-api.md` clause 3.8 does not name the ACME account key or its type, and `spec/arfc-0002-identity-and-join.md` section 2 lists only the API CA key and API server certificate keys in its RFC 6979 rule; both should name the ACME account key as ADR 0053 decides (fits T-0045 or a new spec task).
- `spec-issue`: every `rustls` provider, `aws-lc-rs` included, draws TLS ephemeral key shares and hello randoms from its own generator (R-0008), which `agent/eng/crypto.md` rule 4 ("Nothing else seeds anything") forbids as written and which breaks I-20 if TLS runs under the simulator. Needs a ruling (an exception to rule 4, or provider key exchange and `secure_random` fed from `alloy-rt`) before the first task that builds TLS.
- `follow-up`: ADR 0048 consequence "The `rustls` provider ADR must confirm RFC 6979 signing for P-256, or name what supplies it" is answered by ADR 0053; the lead may want ARFC 0002 and 0008 `Decisions` headers to list 0053 (outside `touches`).
- `follow-up`: `deny.toml` needs `p256`, `ecdsa`, `rfc6979`, `rcgen`, `rustls`, `aws-lc-rs` and their trees in the task that first builds them; whether `multiple-versions = "deny"` holds for the full tree is unknown (R-0008 Unknown).
