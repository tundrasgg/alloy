## Summary

ARFC 0007 now lets a user hold access keys, created only by exchanging a login
code (section 3.9), and gives each control node a built-in local admin
`root@<node name>` limited to three actions through a root-only Unix socket
(section 3.10). Ruling: neither change weakens ARFC 0020, so both were made and
ARFC 0020 is unchanged. ADR 0041 records the ruling and what it depends on.

The check against ARFC 0020, clause by clause:

- Section 2.1, hostile tenant, underlay attacker, outside client: the local admin socket is a pathname Unix socket with no network listener (3.10.2). A guest reaches it only by breaking the guest to host boundary. User access keys add no reachability.
- Section 2.1 and 3.3, compromised compute node: the control plane takes the node name from the accepting socket or from the node record bound to the AL session, never from the request, and refuses a record without `control` (3.10.4). The refusal does not depend on the compromised node's own `alloyd`.
- Section 2.1 and 3.4, stolen credential: a stolen user access key grants its user's policies until revoked, within 5 seconds (3.9.6). The local admin holds no credential to steal.
- Section 2.2, trusted parties: user id 0 on a running control node is read as inside "the hardware and kernel of each node" and "the cluster key". Basis in the repository: ARFC 0002 section 2 gives the cluster key to the control plane and section 9 leaves threshold custody open; ARFC 0020 section 3.7 guards a node's secrets at rest with a node key file of mode `0600`, the same gate as the socket.
- Section 3.5, closed defaults: a user with no role cannot issue a login code (3.9.2).
- Section 6, fail closed: section 6 of ARFC 0007 as extended.
- I-15: 3.9.9, 3.10.5, 3.10.6. I-22: 3.9.4, 3.9.9.

External facts used, fetched for this task from https://man7.org/linux/man-pages/man7/unix.7.html:

- `SO_PEERCRED`: "returns the credentials of the peer process connected to this socket", "those that were in effect at the time of the call to connect(2), listen(2), or socketpair(2)", "possible only for connected AF_UNIX stream sockets".

## Decisions

- The ruling rests on one reading of ARFC 0020 section 2.2: user id 0 on a running control node already is a trusted party. The other reading, that only a quorum of control nodes is trusted and one control node is not, was rejected because section 2.1 names only a compromised compute node as an adversary and ARFC 0002 has no threshold custody. ADR 0041 says it must be superseded if either fact changes.
- The local admin is not a cloud admin. It has a fixed policy of three actions, and it issues login codes only for users that hold `cloud-admin`, so it cannot impersonate a tenant user (ARFC 0007 section 3.3).
- An exchange never replaces a key. A taken name gets `-2`, `-3`, and so on. Reason: hostnames collide, and replacing would silently log out another computer.
- Revocation does not revoke descendant keys by default. It voids unspent login codes the key issued, reports the descendant count, and takes `descendants: true`. Reason: revoking by default would log out every computer set up from the revoked one on a plain re-login.
- Issuing a login code is an authorized action, `iam:IssueLoginCode`, on the caller's own user. A deny in an org policy is how an org forbids user access keys. No separate setting.
- Named here because nothing named them yet: actions `iam:IssueLoginCode`, `cluster:CreateJoinToken`, `cluster:UpdateNode`; error code `PermissionDenied`; socket path `/run/alloy/admin.sock`; field `issued_by`; request field `descendants`.
- The local admin path is specified in ARFC 0007, not in ARFC 0002 where PB-0001 placed it, because it is a principal and a policy and the task touches only ARFC 0007.

## Issues

- `follow-up`: research whether `SO_PEERCRED` can report user id 0 for a peer that is root only inside a user namespace, and add a hostile scenario for it (`spec/arfc-0007-tenancy-and-iam.md`, clause 3.10.2).
- `spec-issue`: ARFC 0008 section 3.7 lists session token and SigV4 as the only authentication, and section 3.8 says the API is served on TLS. The local admin socket is a third way in and needs a sentence there (`spec/arfc-0008-native-api.md`).
- `spec-issue`: ARFC 0002 must state, with the login code from T-0022, the exchange call, whether a failed exchange spends the code, and that a login code records its issuer, so that clauses 3.9.4, 3.9.5, and 3.9.7 have their counterpart (`spec/arfc-0002-identity-and-join.md`). Clause 3.9.3 fixes the key name rule the CLI uses; ARFC 0019 should point to it.
- `spec-issue`: ARFC 0019 must say when the CLI uses the local admin socket: user id 0, on a control node, and no context selected (`spec/arfc-0019-cli-and-console.md`). It should also have the CLI revoke the key it held for a context after logging in to that context again, which is what keeps one key per computer.
- `spec-issue`: PB-0001 offers `sudo alloy node update node1 --advertise` "on node1" and `sudo alloy token create` "on a control node". The first works only when the anchor is also a control node. A node without `control` has no local admin (`product/briefs/PB-0001.md`, Errors table).
- `spec-issue`: nothing stops the removal of the last `cloud-admin` binding. After that the local admin has no user to issue a login code for and the cluster cannot be administered (`spec/arfc-0007-tenancy-and-iam.md`, clause 3.10.1).
- `spec-issue`: `alloy cluster recover` (ARFC 0006 section 3.11) and `alloy cluster grace` (ARFC 0002 section 3.5) run without quorum, when no API call can be authorized, and neither says how the caller is authenticated. They are not local admin actions under 3.10.1.
- `spec-issue`: ARFC 0020 section 3.7 does not list the cluster key among secrets at rest, and no ARFC says where a control node keeps it (`spec/arfc-0020-security-model.md`).
- `follow-up`: glossary entries for `local admin` and `user access key` (`agent/domain/glossary.md`).
- `follow-up`: conformance cases for 3.9 and 3.10 in `tests/conformance/authn`, and a simulator scenario where a node without `control` sends a forwarded local admin write (clause 3.10.4).
