## Summary

Clause 2.5 of ARFC 0011 now states the Landlock thread scope and start point: the thread that applies the rule set and the threads it starts afterwards, from application, before the guest's first instruction. It records that `cloud-hypervisor` v54.1 applies it at `vm_create` without TSYNC, so its main and HTTP threads run outside it, and that the per-guest boundary rests on 2.1 to 2.4. Clause 2.7 now states the Unix socket premise as a property of the Landlock ABI in use (v54.1: ABI 3), and notes ABI 6 and ABI 9. ARFC 0020 lists 0038 in `Decisions`. Both edits are clarifications, so there is no new ADR.

## Changes

I fetched the external sources again for this task:

- https://raw.githubusercontent.com/cloud-hypervisor/cloud-hypervisor/v54.1/vmm/src/landlock.rs: `static ABI: ABI = ABI::V3;`, `self.ruleset .restrict_self()` with no flags, and the handled rights are `AccessFs::from_all(ABI)` (filesystem only).

## Decisions

- F1 ruling: I took the second reading the review offered. Clause 2.5 states the scope that v54.1 provides and relies on 2.1 to 2.4 for the other threads. This is a clarification, not a behavior change, so it needs no ADR. The accepted clause never stated a thread scope (2.4 does, 2.5 did not), and ADR 0038 requires "every thread" only for seccomp. The first reading would also make the first implementation non-conformant, which goes against ADR 0038's stated consequence. The reviewer was right that the scope was missing.
- F2 ruling: the reviewer was right. The required socket confinement in 2.7 is unchanged, and only its premise is corrected, so this is a clarification.
- F3: ADR 0038 grants read-only access to "the guest's boot files". ARFC 0011 clause 2.5 grants it to every file outside the guest directory that the configuration names at start, including read-only images. Where the two differ, clause 2.5 governs, because an accepted ARFC outranks an ADR (`agent/core/1-authority.md`). ADR 0038 was not edited.

## Issues

- `follow-up`: the conformance tests for clause 2.5 should check the thread scope as now stated, using the TID of the thread that applies the rule set and of the threads started after it, not every TID. This belongs with the M3 verify task that already holds review F5 (`plan/reports/T-0020.reviewer.1.md`).
- `follow-up`: if a later `hypervisor` implementation or CH release uses Landlock ABI 8 or later with TSYNC, clause 2.5 could require that every thread be covered. That would be a behavior change and needs an ADR (`spec/arfc-0011-compute.md` clause 2.5).
