| F1 | block | `spec/arfc-0002-identity-and-join.md:1088-1097`, `:359-362`, `:740-742` | A compromised anchor without `control` can write another node's control plane state. A `forwarded` `withdraw` that names any mesh key deletes that joiner's `pending` request or `joining` node. A `forwarded` replay of a `renew` it once carried, with serial s, issues a new record and a `cluster:RenewNode` record with principal `node:<victim>`. That happens as soon as the victim's current record has expired, because the 3.5 exception applies only while "that record has not expired". It can repeat at every expiry, which keeps a stopped node's record alive past the I-09 bound. Section 8 states the withdraw as allowed, and it says the replay "issues nothing once that `renew` has been handled", which is false after expiry. Withdraw forgery predates this branch. The expiry gap and the false claim are new | ARFC 0020 clause 3.3 ("write control plane state beyond its own status, or forge audit records"); I-15; ARFC 0018 line 100 (`RenewNode` principal `node:<node name>`); ARFC 0002 3.5 line 361; section 8 lines 1093-1095. Weakening ARFC 0020 is class P (`agent/core/3-autonomy.md`) | A join service request that an anchor forwards for another mesh key changes no control plane state for that node, and writes no audit record naming it, unless the joiner or node gave evidence the anchor cannot forge. A replayed `renew` issues no record, whether or not the current record has expired. Section 8 claims only what holds. Otherwise the ARFC 0020 clause 3.3 exception goes to the pilot as pivotal. Not reachable at rung 2, so the lead may split it out before rung 3 forwarding is built |
| F2 | fix | `spec/arfc-0002-identity-and-join.md:748-751`; `spec/arfc-0006-control-plane.md:185`, `:199-202` | Every request from a node with a valid record goes to the one control node it chose, and "a new request, which ends the one before". Heartbeats keep running during `leave` and `renew`, starting every 5 s, or 1 to 4 s after a failure. So the next heartbeat can end a `leave` or `renew` at any point inside its 10 s limit, as early as a few milliseconds after it was sent. The control node then drops any later resend as "a lower id". The spec does not say whether the node takes a reply to a request that was ended. A conforming node can therefore report `leave` as `Unavailable` after the node was deleted, or after a single lost datagram, well inside the 10 s that section 3.9 promises | ARFC 0002 3.9 ("does not answer within 10 seconds"); 3.13 lines 748-751 ("lower id is dropped"); ARFC 0006 3.13 Schedule and the `joined` sender condition | A `leave` or `renew` gets its full time limit and its resends while heartbeats run, or the spec states which request yields and the outcome the user sees. Whether a reply to an ended request is taken is stated |
| F3 | fix | `spec/arfc-0018-observability-and-audit.md:106-108` | The audit source address of a node message is "the underlay source address of its packet as the anchor saw it, which `forwarded` carries". From rung 3, `renew`, `leave`, and heartbeats reach a control node directly through `al0`, often over a relayed path, with no anchor and no `forwarded`. So the source address in `DeleteNode`, `RenewNode`, `SetNodeRelease`, and `ReportNode` records is undefined, and a verifier cannot test it | ARFC 0002 3.13 Who speaks and This version (branch); ARFC 0018 clause 3.3 table lines 99-103 | ARFC 0018 defines the source address of a node message that arrives with no `forwarded`, on a direct or a relayed path |
