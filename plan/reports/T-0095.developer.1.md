## Summary

`task/T-0095` was cut from `task/T-0083` (8059f64) and main was merged in with no conflict. The Linux failure was in the test, not the read: on Linux `block_size` is the device's logical block size, 512 on the evidence host, so the test's first read had a 512-byte buffer and `Ok(512)` was the right answer. The test now sizes its tail from the block (904 bytes for 4,096, 392 for 512).
The read loop is also changed as the task asks: on a direct handle, a read that stops off a block boundary ends only when the file length is reached. Inside the file, the read starts again at the last block boundary, and fails with `Io` if that makes no progress. Two new unit tests cover the loop with a scripted platform read.
`cargo test -p alloy-rt --locked` (68 tests), `cargo xtask ci`, and `check-repo --base main` pass on this Windows host. The workspace is not Linux: Linux is type-checked and Clippy-clean but not run, so the lead's Linux run is still owed.

## Changes

- `crates/alloy-rt/src/os/disk.rs`: `read_one` delegates to a new pure `fill`. On a direct handle a read off a block boundary ends only at the file length (`metadata().len()` for a file, `device_len` for a block device). Inside the file it rereads from the last block boundary, and returns `DiskError::Io` when that makes no progress.
- `crates/alloy-rt/src/os/disk/tests.rs`: `a_direct_read_across_the_end_returns_the_bytes_before_it` uses a tail of `904 % block` bytes, so every assertion holds for both 512 and 4,096 blocks. No assertion was removed or loosened.
- `crates/alloy-rt/src/os/disk/tests.rs`: new `a_direct_read_ends_only_at_the_end_of_the_file` (sector-short reads inside the file, a short read at the end, a read past the end, a stuck read, and no length query on aligned reads) and `a_buffered_read_goes_on_until_a_read_returns_zero`.

The cause, from the code at 8059f64. The Linux `platform::block_size` (`crates/alloy-rt/src/os/disk.rs`, Linux `platform` module) reads `/sys/dev/block/<major>:<minor>/queue/logical_block_size` and returns 512 when it reads 512. The old test then made `len = 512 + 904 = 1416` and read `read(block, block)`, a 512-byte buffer at offset 512, and asserted `Ok(904)`. A 512-byte buffer cannot hold 904 bytes. `Ok(512)` (a full buffer) is correct under clause 3.1.11, and it is exactly the lead's `left: Ok(512)`. With block 512, the old `read(2 * block, block)` at 1,024 would also have returned 392, not 0. With the new tail, block 512 gives `len = 904`: `read(512, 512)` returns 392 at the end of the file, `read(0, 1024)` returns 904, and `read(1024, 512)` returns 0, which is the same shape as the 4,096 case.

## Decisions

- Class N: on a direct handle, a read that stops inside the file short of the next block boundary returns `DiskError::Io`. A short `Ok` would break clause 3.1.11, and retrying from the same offset could loop forever.
