## Summary

Closed T-0102 review 2 F1 to F3 and T-0103 review 2 F1 and F2. Node channel state is now keyed by mesh keys, not by AL sessions. Request ids come from the handshake counter, so they only grow across rekeys and restarts.
A node with a valid record talks to a control node directly over a session it authenticated. Anchors forward only join service requests. So no anchor carries a heartbeat, `leave`, or valid-record `renew`, and the control session and origin numbering are gone.
Rung 2 has every anchor holding `control` and needs no forwarding. The general rule runs over the mesh from rung 3.

## Changes

- `spec/arfc-0002-identity-and-join.md`: 3.13 rewritten. It covers who speaks, the control node choice, join-service-only forwarding with a target that moves after 3 s, and request ids from the handshake counter. Once-only entries are per origin of mesh keys and last across a rekey. It also states the outcome of each request type handled twice, and This version for rung 2 and rung 3. `Forwarded` field 5 is now reserved and the overhead is 66 bytes. 3.5 adds an idempotent `renew`. 3.9 states that a `leave` may succeed even when its reply is lost. Sections 7 and 8 are updated to match.
- `spec/arfc-0006-control-plane.md`: 3.13 Path and Rungs now send heartbeats straight to a control node, and the 30 s bound is restated with its arithmetic. 3.14 takes the mesh key from the AL session only. Section 4.3 comment, section 7 anchor state, section 8 (no forwarded heartbeat commits), and one section 9 open question are updated.
- `spec/arfc-0003-mesh-wire-protocol.md`: 3.2 notes that request ids share the handshake counter. 3.3 notes that a rekey makes a new session, so state that must survive it is kept per mesh key.

Rulings:
- T-0102 F1: reading B holds, made exact. An origin is made of mesh keys, and ids come from the handshake counter (ARFC 0003 3.2), which only grows and never repeats across a crash. A rekey, a new session, or a restart therefore never reorders ids or resets an entry.
- T-0102 F2: once-only now survives a session replacement, because entries are keyed by mesh key. Only two cases can handle a request twice: an anchor moving its forwarding target, and a control node restart. Each request type's outcome is stated for that case. `renew` is now idempotent by serial. A `leave` whose reply is lost may have deleted the node (Unavailable semantics), and `--force` clears local state.
- T-0102 F3: the control session is removed, so no address has to be chosen for it. From rung 3 an anchor reaches control nodes through `al0` and the mesh (ARFC 0004 endpoints).
- T-0103 F1: one description now holds in both ARFCs. An anchor without `control` keeps no control session and forwards no heartbeat. Its own heartbeat goes to a control node like any node's. Failover moves to the node, which cycles control nodes. The bound is 28 s with 4 control nodes.
- T-0103 F2: a heartbeat is taken only on an AL session that the reporting node authenticated, never in a `forwarded`, so a forged `NodeStatus` from an anchor commits nothing. ARFC 0002 section 8 now bounds what an anchor can assert to join service requests.

## Decisions

- N: `request_id` is drawn from the handshake counter rather than a new persisted counter. Reason: it is already persistent and monotonic, survives handover, and needs no new file.
- N: registered nodes' node messages go straight to control nodes, and forwarding is limited to the join service. Reason: this ends anchor forgery of status, `leave`, and `renew`, and removes the control session.
- N: the `Forwarded.origin_session` field is reserved. Reason: replies route by mesh key, which survives rekeys.

## Issues

- `follow-up`: these are behavior changes to accepted ARFCs and partly supersede ADR 0042's node channel consequence (control session, per-session numbering). An ADR is needed, and the task allocated no number (`agent/protocol/spec-change.md`, `agent/protocol/decisions.md`).
- `spec-issue`: a compromised anchor can forge `withdraw` for any mesh key in a `forwarded` and delete another joiner's `pending` request or `joining` node, against ARFC 0020 clause 3.3. Section 8 of ARFC 0002 now states this. Fix candidate: sign `withdraw` with the joiner's identity key.
- `follow-up`: a forwarding anchor whose target answers only read-only requests can stay on a control node that cannot commit. This is an edge case in rung 3+ joins (`spec/arfc-0002-identity-and-join.md` 3.13 Forwarding).
