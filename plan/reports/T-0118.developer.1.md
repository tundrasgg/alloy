## Summary

`rustls`, `tokio-rustls`, and `rustls-webpki` are dependencies of `alloy-crypto` only. Its new `tls` module holds the configurations, the ClientHello reader, and the streams. `alloy-api` names no TLS crate, and neither do its tests.
The API port now counts three kinds of connection apart: unproven (256 in all, 8 per source), proven API (512), and `stream` (256).
A rejected call never counts as activity. An unproven connection closes 20 s after accept, or after 4 rejected calls.
Every bound and the behavior at it are stated on `ConnLimits` and `AdminLimits` (I-21). T-0109 re-review F3 is fixed: the ClientHello and the handshake share one 10 s deadline.

## Changes

- `crates/alloy-crypto/src/tls.rs`: `ServerCert`, a chain plus an `ecdsa::SigningKey` that signs `CertificateVerify` through the RFC 6979 signer. Also `ServerTls`, `ClientTls::pinned`, `ApiCaFingerprint`, `HelloReader`/`ClientHello`, `ServerStream`/`ClientStream`, `HandshakeError`, and the `WallClock` trait.
- `crates/alloy-crypto/src/tls/tests.rs`: in-memory handshakes, the pin and address refusals, the leaf-key check, ClientHello splits, the kx groups, the alert bytes, and the fingerprint.
- `crates/alloy-crypto/Cargo.toml`, `src/lib.rs`: the TLS crates, plus `tokio` with no features (for the I/O traits), and the module docs.
- `crates/alloy-api/src/conn.rs`: `Source` (an IPv4 address or an IPv6 /64), `Pools`/`Place` (the three counts), and `Gate` (when one HTTP/2 connection closes). Unit tests are included.
- `crates/alloy-api/src/transport.rs`: `ConnLimits` with every bound and its behavior, and `AdminLimits` for the local admin socket.
- `crates/alloy-api/src/server.rs`: places taken at accept, one handshake deadline, rejected calls counted, the API count taken at the first authenticated call, a refusal with `Unavailable` and a 1 s retry when that count is full, and a GOAWAY close with `CLOSE_GRACE` of 1 s.
- `crates/alloy-api/src/tls.rs`, `client.rs`, `lib.rs`: these go through `alloy-crypto::tls`. `ConnectError::Certificate` now holds a `TlsError`.
- `crates/alloy-api/src/tests.rs`: the PKI is built with `alloy-crypto` x509 and fixed keys. New tests cover the API count being full, rejected calls, and the attack.
- `crates/alloy-api/Cargo.toml`, `Cargo.toml`, `Cargo.lock`, `deny.toml`: the TLS crates and `rcgen` (with `aws_lc_rs`) are gone from alloy-api and the root manifest. The lock loses 17 packages (the `x509-parser` tree), and the reasons in `deny.toml` are updated.

## Decisions

- N: `alloy-crypto` gains `tokio` with no features, only for `AsyncRead` and `AsyncWrite`, which the TLS streams implement.
- N: The `alloy-crypto::tls` API wraps every `rustls` type, so no `rustls` type appears in `alloy-api`.
- N: The server key now reaches `rustls` only as an Alloy `ecdsa::SigningKey`, in the tests too, so the provider's randomized signer is never used.
- N: The API port bounds are 256 unproven (8 per IPv4 address or IPv6 /64), 512 proven API, and 256 `stream`, for 1,024 in all. The times are 10 s to hand shake and 20 s to prove, with at most 4 rejected calls and 60 s idle. A close sends GOAWAY and allows a 1 s grace.
- N: A call that names no method is rejected like a call that fails authentication: the path is checked first, so neither carries a principal.
- N: When the API count is full, the call that would prove a connection fails with `Unavailable` and a 1 s retry delay. It counts as rejected, and the connection stays unproven.
- R: `serve_local_admin` takes `AdminLimits` instead of `ConnLimits`.

## Issues

- `spec-issue`: ARFC 0008 section 7 states none of these bounds. It should carry the API port and local admin numbers above and the per-source rule (`spec/arfc-0008-native-api.md`).
- `follow-up`: T-0109 re-review F2 is still open: `Transport::of` takes any `RuntimeConfig`. Closing it needs `alloy-rt` to expose its `net` implementation name, which is outside `touches` (`crates/alloy-api/src/transport.rs`).
- `follow-up`: A `stream` connection frees its place in the port's `stream` count only when the underlay drops it. The underlay must close a peer that has not finished an AL handshake within a stated time (`spec/arfc-0004-path-manager.md` section 3.6).
- `follow-up`: A flood from many sources can still fill the 256 unproven places. Per-source shares only stop a single source (ARFC 0020 section 2.1).
