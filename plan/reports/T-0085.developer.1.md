## Summary

`alloy-crypto` now has the module `al`: the Noise `IKpsk2` handshake built from primitives (D-0032), the section 3.3 session and probe keys with erasure, `mac1`, `mac2`, cookies, the cookie reply, and transport seal and open with the section 3.4 nonce.
The caller supplies every random byte. Key types erase themselves on drop, print no secret, and are not `Clone`. The handshake states are consumed when they produce keys.
The state machine reproduces the cacophony vector for `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s`. The AL instantiation matches an independent straight-line computation. The primitives pass RFC 7748, draft-irtf-cfrg-xchacha and RFC 7693 vectors.
All three acceptance commands pass. The diff is 3,650 lines: about 1,820 of product code and docs, 1,500 of tests, and 245 of `Cargo.lock`.

## Decisions

- N, the interface, following the D-0029 pattern. Everything is in `alloy_crypto::al`, and it works on the cryptographic fields as byte arrays:
  - `InitiatorHandshake::write_initiation(&StaticSecret, &PublicKey, EphemeralSecret, &[u8; 16]) -> (InitiatorHandshake, [u8; 112])`.
  - `InitiatorHandshake::read_response(self, &StaticSecret, &PresharedKey, &[u8; 52]) -> (SessionKeys, [u8; 4])`. On failure it returns `ResponseRejected { error, handshake }`.
  - `ResponderHandshake::read_initiation(&StaticSecret, &[u8; 112]) -> (ResponderHandshake, PublicKey, [u8; 16])` and `ResponderHandshake::write_response(self, EphemeralSecret, &PresharedKey, &[u8; 4]) -> (SessionKeys, [u8; 52])`.
  - `SessionKeys { send: SendKey, recv: RecvKey, probe_send: ProbeKey, probe_recv: ProbeKey }`.
  - `SendKey::seal_in_place(queue, counter, &[u8; 9] header, buf)` and `RecvKey::open_in_place(...) -> &mut [u8]`.
  - `Mac1Key::{new, mac1, verify_mac1}`, `CookieSecret::{from_bytes, cookie}`, `Cookie::mac2`, `verify_mac2(current, previous, src, m2, mac2)` and `CookieReplyKey::{new, seal, open}`.
  - `alloy-crypto` cannot depend on `alloy-wire` (`plan/workspace.md`), so the payloads stay encoded bytes and `alloy-link` decodes them with `alloy-wire`.
- N, HMAC-BLAKE2s and HKDF are composed in `alloy-crypto` over the `blake2` crate, not taken from `hmac` and `hkdf` at run time. The `hmac` crate's `SimpleHmac`, which is the only HMAC it offers for BLAKE2, keeps `opad_key` (the key XOR opad) with no erasure (`hmac-0.13.0/src/simple.rs:12-15`, no `Drop`). `hkdf` 0.13 keeps the extract output and every expand block in plain locals (`hkdf-0.13.0/src/lib.rs`, `extract` and `expand_multi_info`). Section 3.3 requires the chaining key and `prk` to be erased, and both pass through HMAC as keys. Both crates stay as dev-dependencies. Property tests show this crate's HMAC and HKDF equal theirs, and the cacophony vector covers the composition end to end.
- N, the probe keys `pi2r` and `pr2i` are derived and returned. The task says the result is "`i2r`, `r2i`, and the 14-byte `salt` and nothing else", but section 3.3 derives the probe keys from `prk` and then requires `prk` to be erased, so they can only be derived here. `ProbeKey` is opaque and has no operation, because section 3.6 sealing is outside this task's sections.
- N, an all-zero Diffie-Hellman result (a small-order public key) fails the handshake with `HandshakeError::NonContributory`. See `spec-issue` below.
- N, a response that fails to authenticate hands the initiator's handshake back unchanged. The response is read into a duplicate of the state, so a forged response cannot end a pending handshake. A response that succeeds consumes the handshake.
- R, pending handshake states and transport keys live on the heap (`Box`) and are filled in place. Moving a handshake or `SessionKeys` then moves a pointer and does not copy key bytes through stack frames.
- R, `seal_in_place` refuses a counter of 2^31 or more and a queue of 64 or more (sections 3.4 and 7). `open_in_place` checks neither, because the receive checks are the caller's.
- N, `deny.toml`: a `skip` for `syn@2.0.119`, which builds only `curve25519-dalek-derive` on x86_64, while `thiserror-impl` uses syn 3. `fiat-crypto` is allowed because cargo-deny resolves every target cfg.
- R, folded both T-0074 review notes (F1 `deny.toml` spacing, F2 `Hasher` doc).

## Issues

- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` section 3.1 is silent on small-order X25519 public keys and all-zero DH results. This implementation rejects them (`HandshakeError::NonContributory`). The section should say so, so that a second implementation does the same.
- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` section 3.3, erasure. The rule ("a Noise library that keeps a copy ... that its caller cannot erase does not meet this section") does not say whether it covers transient stack copies inside primitives. Examples are the zero-padded key block that `blake2`'s keyed constructor builds on the stack, and the key array passed by value to `XChaCha20Poly1305::new`. Safe Rust cannot erase those. This crate erases every value it holds in a state or buffer it owns.
- `follow-up`: `agent/eng/crypto.md`, primitives table. The row "Hash and KDF in the handshake: `blake2`, `hkdf`" no longer describes the build. `hkdf` and `hmac` are now test oracles, and HMAC and HKDF are composed over `blake2` for erasure (the decision above).
- `follow-up`: section 3.6 probe sealing and opening on `ProbeKey` (XChaCha20-Poly1305, nonce `16 zero bytes || counter`, the message header as associated data) in `crates/alloy-crypto/src/al/session.rs`. `alloy-link` needs it before it can send probes.
- `follow-up`: section 3.9 process handover moves `send_key`, `recv_key` and the probe keys to a successor process. The interface has no export or import of key material, so the task that builds handover needs one, specified first.
