Attack 1: byte arithmetic and the MAC definitions. A throwaway probe outside the repository (Python stdlib `hashlib`, run with `python -I`):

```
sizes 152 96 64
init payload 16 resp payload 4 noise bytes 112 52
name len 21
mac1 len 16 mac2 len 16 nn=16 differs from truncated nn=32: True
cookie uses rejected in keep window: 0 min slack s: 0.001617    (zero network delay)
nonce collision bound log2: -65
```

The table sizes, the payload sizes and the Noise byte counts all match the text. `MAC` with a 32-byte key (`mac1`, `cookie_secret`) and with a 16-byte key (`cookie`) is well defined as RFC 7693 keyed BLAKE2s with `nn = 16`. A truncated 32-byte output gives different bytes, and the text says "with a 16-byte output", which selects `nn = 16`. The cookie reply nonce bound, 2^-65 for 2^64 replies, matches the text's "below 2^-64".

Attack 2: the cookie validity window with network delay. The text says secret `i` is current for 120 s and then accepted as "previous" for 120 s. The initiator keeps a cookie "for 120 seconds from receipt". Lines 166 to 168 conclude "so a cookie stays valid for at least those 120 seconds". The probe draws a cookie made in the last second before a rotation, a one-way delay from 1 to 200 ms, and a send time in the last second of the initiator's keep window. The model is: secret `i` accepted on `[120i, 120(i+2))`, the cookie made at `t_r`, received at `t_r + d`, sent at `u <= t_r + d + 120`, and arriving at `u + d`. It runs 1,000 seeds (`random.Random(7)`, throwaway probe outside the repository):

```
seeds 1000, initiations sent inside the keep window that the responder rejects: 25
first (seed, d, made, sent, arrives, secret expiry): (91, 0.1145, 719.9105, 839.9676, 840.0821, 840)
worked case: made 119.99 received 120.04 sent 240.03 (119.99 s after receipt) arrives 240.08 -> secret of 0..120 accepted until 240.0: REJECTED
```

The 120 s are counted from receipt at the initiator. The secret's acceptance runs from creation at the responder. So the guarantee falls short by up to the round-trip delay. Under load, such an initiation fails `mac2` and draws one more cookie reply, which costs one extra round trip. Nothing loops and no state is gained. This is F1, at `fix`.

Attack 3: rewrite fields on the path and inject cookie replies.
- A rewritten initiation `sender_index` makes the response go to an index the initiator does not hold. Because of 3.2, the genuine initiation then fails the counter check, so the handshake fails. That is denial of service, which an on-path party already has.
- A rewritten response `sender_index` makes the transport packets miss at the responder. The AEAD covers the transport header as associated data (3.4), so a packet misrouted to another session's index is dropped.
- A forged cookie reply needs the `mac1` of the pending initiation as AEAD associated data. `mac1` covers the ephemeral, so an off-path party cannot produce it. An on-path party can, but that only gains denial of service.
- A spoofed `src` reflects 64 bytes per 152-byte initiation, so there is no amplification.
- The responder keeps no state per cookie reply. The initiator stores a cookie only for an index it has pending, so its storage is bounded (I-06, I-21).

The claim at lines 221 to 225 holds.
