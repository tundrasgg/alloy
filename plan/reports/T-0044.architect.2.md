## Summary

The local admin's recovery of a user with no credential can no longer be stopped by anything the stolen credential changes first. No deny binds the local admin. Its `iam:RevokeUserAccessKeys` reaches any user. A new clause 3.10.8 keeps at least one enabled `cloud-admin` user in an enabled org.
Issuing a login code now checks, against committed state, that the key it is issued through is unrevoked. So a revoked key's 5 second authentication window can no longer mint a key that outlives the revocation.
ADR 0050 is rewritten to match. It still supersedes ADR 0041 and restates ADR 0041's other decisions. It reverses one of ADR 0041's decisions, that denies bind the local admin, and gives the reason.

Findings of `plan/reports/T-0044.reviewer.1.md`:

- F1 (block): resolved, by the first of the two outcomes the finding allows: the recovery succeeds whatever the stolen credential changed. These are the three things the thief could change, and the fix for each:
  - **A deny.** Clause 3.10.1 now says the fixed policy is the local admin's whole authorization and that no deny refuses a local admin call. Clause 3.1 names this as its one exception, and clause 3.9.2 says the same for `iam:IssueLoginCode`.
  - **The user's role or state.** The local admin's `iam:RevokeUserAccessKeys` is limited to no user, in the table in 3.10.1 and in 3.9.13. It must succeed for a user that is disabled, holds no role, or is under a deny. So the stolen key of any user can always be revoked, as ARFC 0020 section 3.4 requires.
  - **The last `cloud-admin`.** New clause 3.10.8 refuses, with `Conflict`, any call that would leave the cluster with no enabled `cloud-admin` user in an enabled org. So the local admin always has some `cloud-admin` user to issue a login code for, even if the thief removed the role from the victim, disabled it, or disabled its org.

  Attack 1 now fails at each step. The revocation goes through any deny and any role change. The login code goes through any deny. If the victim lost `cloud-admin`, the code goes to the user that 3.10.8 keeps.
  The ARFC 0020 check is in section 8 and in the ADR 0050 ruling. Revocation reads and grants nothing. The deny exemption reaches only login codes for `cloud-admin` users, whose power root on a control node already holds by the facts of ADR 0041, and both audit chains record each use. The deny still binds every other principal.
- F2 (block): resolved. Clause 3.9.2 now also refuses issuing when the request was authenticated by an access key, or by a session token that derives from one, and that key is not unrevoked. The check reads the state committed in the transaction that creates the code, not the authentication view that may lag by 5 seconds.
  The control plane orders a revocation and an issuing linearizably (I-11). If the revocation commits first, the issuing is refused. Otherwise the revocation voids the code (3.9.7). So no unspent login code exists through a revoked key, and no key created after a revocation has that key as `issued_by`.
  This makes the claims of 3.9.11 ("every key that an unrevoked key descends from is kept") and of 3.9.13 ("no unrevoked key") hold after their commit. Clause 3.9.13 now states it, and section 8 says a revocation ends the lineage for good, in the 5 second window too. Attack 2's scripted thief gets `PermissionDenied` on every login code it tries to issue after the revocation commits.
- F3 (note): resolved. The revocation bullet of ADR 0050 now says "Every built-in org role and the cluster role `cloud-admin`", the same set as clause 3.9.13.

## Decisions

- No deny binds the local admin. This reverses an ADR 0041 decision that ADR 0050 had kept, and ADR 0050 records the reversal. Reason: the stolen credential can attach the deny itself, which leaves the key unrevocable (ARFC 0020 section 3.4) or the cluster with no administrator.
- The local admin's revocation is limited to no user. Reason: a limit to `cloud-admin` users is defeated when the thief removes the role. Revocation only removes credentials, and the user's org chain records it.
- New clause 3.10.8 protects the last enabled `cloud-admin` user in an enabled org, with error `Conflict`. Reason: without it, a stolen `cloud-admin` credential can leave nobody that a local admin can log in. The code is the one ARFC 0002 uses to refuse removing the last control node.
- Issuing a login code is checked against committed key state. Writes in general are not. Reason: only a login code creates a credential that outlives the revoked key. Checking every write at commit would reach every service's write path.
