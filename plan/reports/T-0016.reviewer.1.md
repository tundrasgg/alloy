F1 source: GitHub workflow syntax, `concurrency`
(https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency).
When a new run is queued in a group, "any existing `pending` job or workflow in the same concurrency group will be canceled".
This happens whatever `cancel-in-progress` is set to. The optional `queue` property changes it.
On `main` the group is `ci-refs/heads/main`. Suppose push A is running, B is pending, and C arrives. B is cancelled and never gets a verdict.

Attacks tried, no finding:

- Fork PR privilege: the trigger is `pull_request`, top-level `contents: read`, `persist-credentials: false`. The workflow uses no secrets.
- Cache poisoning: `save-if` limits cache writes to `refs/heads/main`. Pull requests only restore. The cached `~/.cargo/bin/cargo-deny` therefore comes only from main runs.
- Gate exit propagation: `run:` steps use bash with `-e`. `cargo xtask ci` returns `ExitCode::FAILURE` on any failed step (`xtask/src/main.rs`), so the job fails exactly when the gate fails.
- Banned list (`agent/core/4-evidence.md`): no Rust changed, so nothing applies.
