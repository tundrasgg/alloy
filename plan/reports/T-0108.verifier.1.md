## Summary

`tests/conformance/log-store` (28 checks plus the two halves of the 5.5 kill check) and `tests/conformance/state-store` (45 checks) are written from ARFC 0006 sections 4.1 and 5.2 to 5.5. Each check is an `async fn(Env) -> Outcome` named after its clause, generic over the seam trait, and builds every instance through `Registry::instantiate` with configurations the suite encodes from 5.2.
Until T-0107 merges, each crate's `state.rs` declares the section 5.1 items the suite uses: types, traits and seam markers only, no implementation. The `Harness` that runs the checks against `mem` and `native` is not written: it needs `alloy-state`. `crates/` was not read.
Expected results come from suite-side models of 5.3 and 5.4 and an encoder of the 4.1 export (BLAKE3 through `alloy-crypto`). Each suite has a seeded random-history check with restarts, compared against its model.
No check has run against an implementation, so failing for the right reason is not shown. That needs T-0107's harness.
About 4,600 lines, more than the 2,000-line target for a verify task. The task covers two suites, and most of the length is per-clause checks.

Cases a real implementation cannot trigger deterministically, and so have no check:
- 5.3.8 and 5.4.7 on `native`: nothing makes redb fail on demand. They are checked on `mem` through `fail_after`.
- 5.3.2 kill during a call on `mem`: there is no process to kill. On `native` it is covered only by the harness-driven kill, whose kill point is not deterministic.
- 5.4.2 kill during `apply` or `finish`: 5.5 asks for no state-store kill. Only restart durability is checked.
- 5.2 `native` file name, mode `0600`, and Windows ACL: inspecting files breaks the direct-io ban of `clippy.toml`.
- 5.2 a second instance on the same `dir` "in any process": only the same process is checked, because a second process needs a harness.

## Decisions

- `Config(Invalid)` must name the field as exactly `name` or `dir`, the protobuf field names.
- `Malformed` is accepted from either `write` or `finish`. After a failed `finish`, no install is in progress.
- A `mem` instance built after `fail_after` is reached still fails every mutating call. `StateInstall::write` is not a mutating call.
- The stand-in is public module `state`, so that it raises no dead-code warnings. T-0107 replaces it with `pub use alloy_state as state;`.

## Issues

- `spec-issue`: In `spec/arfc-0006-control-plane.md` 5.3.7, take `purge_through(log_id)` where `log_id.index == last.index` and `log_id` differs from the held entry's id. The `LogState` doc gives `last = last_purged`, but 5.3.7 moves `last` only when the index is above. The suite avoids this case.
- `spec-issue`: In the same ARFC, 5.3.4 and 5.4.3 do not order the errors when one call breaks several rules, for example `Stale` together with an empty key. The suite never combines two.
- `spec-issue`: In the same ARFC, 5.4.6 does not say whether `write` may fail with `Malformed`, or whether an install is still in progress after `finish` fails. The suite assumes as in Decisions.
- `process-issue`: Every new workspace crate needs a `deny.toml` entry, but T-0108's `touches` left that file out. I edited it anyway so `cargo xtask ci` passes. Tasks that add a crate should list `deny.toml`.
