## Summary

`fuzz/` now holds a cargo-fuzz package with four libFuzzer targets: `message`, `inner_frame`, `initiation_payload` and `response_payload`. Each target checks that the decoder never panics and that an input that decodes encodes back to the same bytes. The seed corpora are the valid messages of the `alloy-wire` unit tests, and `fuzz/examples/write_seeds.rs` regenerates them.
Each target ran for 61 seconds on this Windows workspace with no finding, and `cargo xtask ci --base main` exits 0.
One thing is blocked. `libfuzzer-sys` declares `(MIT OR Apache-2.0) AND NCSA`, and NCSA is not on the license list in `agent/eng/deps.md`. On the fuzz graph, `cargo deny` passes advisories, bans and sources but fails licenses. Licensing is pivotal (`agent/core/3-autonomy.md`), so I left the license policy unchanged and ask below.

## Changes

- `fuzz/Cargo.toml`: new package `alloy-wire-fuzz`. It is a workspace of its own with `cargo-fuzz = true` metadata, depends on `alloy-wire` by path and on `libfuzzer-sys` 0.4.13, and declares one `[[bin]]` per target.
- `fuzz/Cargo.lock`: lockfile of the fuzz workspace, 12 packages.
- `fuzz/fuzz_targets/message.rs`: `Message::decode`. A message that decodes must encode into a buffer the length of the input, and the result must equal the input.
- `fuzz/fuzz_targets/inner_frame.rs`: `InnerFrame::decode`. Same check, and `encoded_len()` must equal the input length.
- `fuzz/fuzz_targets/initiation_payload.rs`, `fuzz/fuzz_targets/response_payload.rs`: `to_bytes()` and `encode()` must both reproduce the input.
- `fuzz/examples/write_seeds.rs`: writes `fuzz/seeds/<target>/`, using the values the unit tests in `crates/alloy-wire/src` use (handshake `ramp` fields, the transport `header()`, the inner frame and fragment layouts, and the payload layouts).
- `fuzz/seeds/**`: 18 seed files. Message has 5 seeds: initiation, response, cookie reply, and transport with the shortest ciphertext and with a longer one. Inner frame has 5, one per kind. Each payload target has 2, with queues 1 and 64.
- `fuzz/.gitignore`: ignores `target`, `corpus`, `artifacts`, `coverage`.
- `fuzz/.gitattributes`: marks `seeds/**` binary, so line-ending conversion cannot corrupt the seeds, several of which contain 0x0a.
- `fuzz/README.md`: lists the targets and gives the run command, the Windows ASAN runtime note, and how to regenerate the seeds.
- `Cargo.toml`: `exclude = ["fuzz"]` in the root workspace.
- `deny.toml`: adds `alloy-wire-fuzz`, `arbitrary`, `cc`, `find-msvc-tools`, `jobserver`, `libfuzzer-sys` and `shlex` to `bans.allow`. The fuzz tree's other crates (`cfg-if`, `getrandom`, `libc`, `r-efi`) were already listed. The license list is unchanged.

Root `Cargo.lock` is unchanged, because the fuzz package is not in the root workspace. `task/T-0061` has main merged in up to `650821c`. The merge resolved one conflict in `Cargo.toml`, where main added `alloy-rt` and `alloy-seam` to the members.

## Decisions

- N: `fuzz/` is a separate Cargo workspace, excluded from the root one, which is the layout cargo-fuzz generates. With it, `cargo xtask ci` does not need a nightly toolchain, a C++ compiler or the libFuzzer build, and root `cargo deny` does not see the fuzz graph. The graph is checked with `cargo deny --manifest-path fuzz/Cargo.toml`.
- N: `libfuzzer-sys`, its tree, and `alloy-wire-fuzz` are on `bans.allow`. That follows the standing choice "Fuzzing: `cargo-fuzz` (libFuzzer)" in `agent/eng/deps.md`, and the task asks for it. The license list in `deny.toml` is unchanged pending the question below.
- N: the fuzz targets carry a crate-level `allow(clippy::disallowed_types)`, because `fuzz_target!` expands to libFuzzer glue that names `std::fs::File`, and the root `clippy.toml` (main, T-0046) applies to `fuzz/` as well. The seed writer carries `allow(clippy::disallowed_methods)` for `fs::write` and `fs::create_dir_all`. Both follow the precedent of `xtask/src/main.rs`: test and repository tooling outside the runtime seams. `cargo xtask check-repo` checks such allows only under `crates/`.
- R: the committed seeds live in `fuzz/seeds/<target>/`, and libFuzzer's growing corpus lives in `fuzz/corpus/<target>/`, which is gitignored. A run passes both directories, and new inputs go to the first.
- R: the message target encodes into a buffer exactly as long as the input. A canonical encoding fits it exactly, so an encode error is itself reported as a finding.

## Issues

- `follow-up`: no CI job builds `fuzz/` (out of scope here). Until one does, `fuzz/` can rot when the `alloy-wire` API changes. The later task that wires the M1 fuzz runs should also run `cargo deny --manifest-path fuzz/Cargo.toml --locked --workspace check` and `cargo +nightly clippy --manifest-path fuzz/Cargo.toml --all-targets`.
- `follow-up`: `fuzz/` targets only the four decoders this task names. `Message::decode` reaches the `Initiation`, `Response`, `CookieReply` and `Transport` decoders, but `TransportHeader` has no public decoder, and `Fragment` is reached only through `InnerFrame::decode`. A new public decoder in `crates/alloy-wire/src` needs a new target.
- `process-issue`: `agent/eng/deps.md` names `cargo-fuzz (libFuzzer)` as a standing choice, but its license list cannot admit `libfuzzer-sys` as published. The choice and the rule contradict each other. Every user of the standing choice will hit this.

## Question

`libfuzzer-sys` 0.4.13 declares `(MIT OR Apache-2.0) AND NCSA` for its vendored libFuzzer. NCSA is permissive and OSI approved, but it is not on the `agent/eng/deps.md` list, so the license check on `fuzz/` fails. How should Alloy treat it?

1. **Recommended: allow NCSA for `libfuzzer-sys` only.** Add a `[[licenses.exceptions]]` entry for `libfuzzer-sys` in `deny.toml`, record it in an ADR, and note the exception in `agent/eng/deps.md`. libFuzzer links only into fuzz binaries, which are never shipped, and this is what the standing choice `cargo-fuzz (libFuzzer)` already implies.
2. **Add NCSA to the global license list** in `agent/eng/deps.md` and `deny.toml`. NCSA is a permissive BSD-style license, compatible with MIT OR Apache-2.0, but any product crate could then use it.
3. **Add a `[[licenses.clarify]]` entry for `libfuzzer-sys`** that restates its license as `(MIT OR Apache-2.0) AND Apache-2.0 WITH LLVM-exception`, which is what the vendored C++ headers say. `Apache-2.0 WITH LLVM-exception` would then need allowing for this crate, so this still needs a licensing decision, and it overrides the crate's own declaration.
4. **Replace the standing choice** with a fuzzer that vendors no libFuzzer. This reopens a settled choice and needs an ADR.
