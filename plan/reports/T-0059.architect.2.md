## Summary

Round 2 resolves all seven findings of `plan/reports/T-0059.reviewer.1.md` in ARFC 0003, ARFC 0017 section 6 and ADR 0057.
The 3.2 initiation replay table now travels with a handover, and a failed handover raises it to counters the successor recorded.
After a failed handover the old process re-handshakes every peer it lost within 1 s, so the drop has a stated bound.
Envelope counters, envelope replay state and the confirmed flag travel with the session. Older probe receive keys stay 10 s after the peer moves on.
ADR 0057 now records the rekey probe rule too. It is renamed to match.

## Changes

- `spec/arfc-0003-mesh-wire-protocol.md`: 3.2 says the responder table travels and is raised after a failed handover. 3.6 defines "newer" and keeps older probe receive state 10 s after the first probe under a newer session. 3.9 passes envelope state, the confirmed flag and the 3.2 table, adds the accepted-initiation record, failed-handover step 2 (raise the table), re-handshakes within 1 s with a keepalive, and states the drop bound. Section 9 gains the handshake retry question.
- `spec/arfc-0017-upgrades-and-versioning.md`: section 6 adds raising the replay table, the 1 s re-handshake, the drop bound, and states that a failed handover can exceed the 100 ms of 3.6.
- `adr/0057-sessions-are-used-only-with-current-state-the-peer-holds.md`: renamed from `0057-a-failed-handover-discards-the-sessions-the-successor-used.md`. It now decides the handover rule and the rekey probe rule. The counter-reservation alternative is rejected for a reason that holds.
- `adr/README.md`: 0057 row follows the rename.
- `plan/reports/T-0059.architect.2.md`: this report.

How each finding was resolved:

- F1 (fix): resolved by the first option the reviewer offered. 3.9 "State that travels" passes the 3.2 table. "Accepted initiations" has the successor record initiator key and counter before it stores the counter. Failed-handover step 2 raises the old process's table to those counters. "Exclusive use" stops the old process processing handshake messages after the handover. The three texts' claim now holds for initiations: the old process drops every initiation the successor stored.
- F2 (fix): 3.9 now sends an initiation to every peer whose newest session was discarded within 1 s of resuming, with or without outbound traffic, and seals a keepalive under the new session at once, so the peer confirms it (3.6). The drop is bounded by 1 s plus that handshake (retries included) and the keepalive. ARFC 0017 section 6 states the same bound. The old home-session-only rule is subsumed.
- F3 (fix): 3.9 "State that travels" now sends with each key every other counter or replay state used with it, naming the relay envelope `counter` (3.7) and any envelope replay state.
- F4 (fix): ADR 0057 now covers the rekey probe rule (3.6 session choice and probe key retention) as well as the handover rule, as the lead's round-2 commit notes. Both are one decision: a node uses only session state that is current and that its peer holds. Title, file name and index row are changed to match.
- F5 (note): accepted. Whether a session is confirmed now travels with it (3.9).
- F6 (note): accepted. 3.6 keeps an older session's `probe_recv_key` and window until 10 s after the first probe accepted under a newer session, never past the 180 s discard.
- F7 (note): accepted. The ADR's rejection of skipping counters is replaced. The new text rejects reserving counter bounds in the record because it needs a synced write per key and queue on the data path, and sessions the successor rekeyed still need the consumed mark.
- Reviewer `spec-issue` on "newest" in 3.6: resolved. 3.6 defines newer by local creation order: the initiator processes the response, the responder sends it. Each node applies the rules in its own order.

Check of the new rules against I-07 and ARFC 0020 section 3.2, adding to the seven cases in `plan/reports/T-0059.architect.1.md`:

8. Successful handover, initiation replay: the 3.2 table travels, so the successor drops every initiation the old process accepted.
9. Failed handover, initiation the successor accepted: the successor recorded its counter before storing it. Step 2 raises the old process's table to at least that counter, so the old process drops it. Recording without storing only drops an initiation that nobody accepted.
10. Old process keeps answering handshakes after passing its sessions: forbidden by "Exclusive use", so the two tables never diverge while both processes run.
11. Relay envelopes, successful handover: the envelope counter and envelope replay state travel with their key, so the successor neither restarts the counter nor accepts an envelope again.
12. Failed handover, peer with no outbound traffic: the initiation goes out within 1 s, so the peer's traffic is not dropped until the peer's own rekey (120 s).

## Decisions

- F4 goes into ADR 0057 and not a new ADR. The task allocated one number, and the lead's round-2 commit message says F4 concerns ADR 0057. The two rules share one principle, so the ADR states one decision with two applications. The file is renamed to match. ADR 0057 is not yet on main (D-0010).
- The re-handshake after a failed handover goes to every peer whose newest session was discarded, within 1 s, not only home sessions. This gives F2's bound without depending on outbound traffic. It costs at most one initiation per consumed session, which the old rule already paid on first traffic.
- The resuming old process seals a keepalive under each new session at once. Under 3.6 a responder confirms a session only when the initiator uses it. Without the keepalive the peer would keep using the discarded session for probes.
- The older probe receive state is kept 10 s after the first probe under a newer session. This matches the 10 s 3.3 gives the previous transport receive key.

## Issues

- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` 3.1. The handshake retry time is still unspecified. It is now listed in section 9 because 3.9's F2 bound depends on it.
- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` 3.3 and 3.4 (carried from round 1). No rule says which session a node seals transport under at a rekey. The F2 bound in 3.9 holds for transport only once the peer moves its transport to the new session when it sees it used, as 3.6 does for probes.
- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` 3.7 does not define the relay envelope's nonce, which key direction it uses, or whether the anchor keeps a replay window. 3.9 now sends whatever envelope state exists with its key, but 3.7 must define that state.
- `spec-issue`: `spec/arfc-0003-mesh-wire-protocol.md` 3.2 does not say whether the responder table of highest initiation counters is persistent. A crash or plain restart loses it, and the restarted process can accept again an initiation it accepted before. This is outside handover, so it is not in this task's scope.
