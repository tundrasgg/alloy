- Each session key has its own window, and the key and its window are erased together.
- A message is accepted when the key is held and its counter passes the 2,048 window.

Text trace for F1:

- ARFC 0017 section 3.5 (`spec/arfc-0017-upgrades-and-versioning.md:46-49`): the successor "takes over sockets ... by passing file descriptors and state, and the old one exits".
- Section 6 (`:69-70`): "A handover that fails before the old process exits leaves the old process serving."
- Section 3.6 (`:52`) and I-17 allow no network gap over 100 ms, so the successor serves before the old process exits.
- ARFC 0003 3.6 (`spec/arfc-0003-mesh-wire-protocol.md:364-367`) hands over only the window with the key. It says nothing about the probe send counter. It also says nothing about what the old process may do with the session after the handover.
- With counter-derived nonces (`:344-347`), a rolled-back send counter seals a new body under a nonce and key already used. Main's probes used random 24-byte nonces, so on main a handover could not repeat a probe nonce.

Text trace for F2:

- 3.6 (`:292-296`): a node sends probe messages, answers included, "only under the newest session it holds", and a responder holds a session "once it has sent the response". At a rekey, the responder therefore seals every probe and answer under the new session as soon as it sends the response.
- The initiator cannot open these until the response reaches it. If the response is lost, it cannot open them until a retried handshake completes, and 3.1 sets no retry time. They are dropped as naming no session (`:389-392`), although both nodes still hold the previous session, which works.
- ARFC 0004 section 3.2 step 6 (`spec/arfc-0004-path-manager.md:70-72`) verifies an endpoint only by an echo inside 2 s, so probe sets in that period verify nothing.

## Issues
