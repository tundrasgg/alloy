## Summary

`.github/workflows/ci.yml` gains a step, run only on `push`, that runs `cargo xtask check-commits "$from..$GITHUB_SHA"`, where `from` is the push's before commit when it is an ancestor of the after commit, and `78d3175` otherwise (D-0019).
actionlint 1.7.12 (official image, with ShellCheck 0.11.0) and `cargo xtask ci` exit 0.
`cargo xtask check-commits 78d3175..main` exits 1: main moved after dispatch, and its tip 9cb9b92, a lead commit, has the body line `T-0006: one block ...`, which the T-0018 `trailers` rule reports as a hyphenated trailer.
At main as dispatched (0c25163) the same command exits 0. Blocked on how to treat 9cb9b92 (Question).

## Changes

- `.github/workflows/ci.yml`: new step `Check the commit messages`, `if: github.event_name == 'push'`; the before commit reaches the shell only through `env`; `git merge-base --is-ancestor` picks the range start, so an all-zero before (new branch), a forced update, or a before commit missing from the clone falls back to `78d3175d124f308e6ce2100733081916c157d169`.
- `.github/workflows/ci.yml`: the checkout comment now says `check-commits` also needs the full history. `fetch-depth: 0` was already set, so nothing else changes.

## Decisions

- The check is its own step after the gate, in the same job, so a failing message shows as its own red step and the single required check (ADR 0037) still covers it. It is skipped when the gate fails.
- The fallback commit is written as its full id, so it cannot become ambiguous.
- Any non-zero exit of `git merge-base --is-ancestor` (1, not an ancestor; 128, unknown or all-zero commit) falls back to `78d3175`.
- actionlint ran from the official `rhysd/actionlint:1.7.12` image already on the machine, with `--pull=never`; nothing was downloaded.

## Issues

- `spec-issue`: `adr/0037-github-hosts-the-source-and-ci-runs-on-github-hosted-runners.md` says CI runs exactly `cargo xtask ci` and workflow files call only that; this task adds a second command. Either amend the ADR or fold the commit range into `cargo xtask ci` (for example a `--commits <range>` flag), which would leave the workflow calling one command.
- `follow-up`: the `trailers` rule in `xtask/src/commits.rs:338` reports any hyphenated `Key:` line in the body, and a task id such as `T-0006:` matches, though git only reads trailers from the last paragraph and `agent/eng/git.md` bans footers, not body prose. Either the rule skips keys shaped like task ids, or lead commits avoid starting a body line with `T-NNNN:`.

## Question

Main's tip 9cb9b92 (`chore(plan): send T-0006 back for round 2, T-0043 to review`) breaks the `trailers` rule because of the body line `T-0006: one block ...`. Main's history cannot be rewritten, so `cargo xtask check-commits 78d3175..main` exits 1. The workflow on this branch would also fail the first push that contains 9cb9b92, and every push that falls back to `78d3175`. What should happen?

1. (recommended) Cut a small xtask task so the `trailers` rule does not report keys shaped like task ids (`T-NNNN`). Land it before or with T-0051, then re-run the acceptance. This fixes a false positive and changes no behavior that matters, and the workflow stays as it is.
2. Move the D-0019 cut to 9cb9b92: commits up to and including it are not checked. Round 2 changes the fallback in the workflow to 9cb9b92 and the acceptance range to `9cb9b92..main`. This is the cheapest option, but it stops checking 52 commits that pass today.
3. Accept T-0051 as is, with acceptance shown at 0c25163, and make sure 9cb9b92 reaches GitHub in an earlier push than the T-0051 squash, so no push range contains it. This leaves the fallback path red until option 1 or 2 is done.
