## Summary

Resolved F1 to F3 of `plan/reports/T-0110.reviewer.1.md`. No node message now carries a token's secret. The secret seeds an Ed25519 token key, and the control plane stores only its public key. A `join_request` is a signed body, with a token key signature and a node identity key signature over `cluster_id`, the requester's mesh key, and every byte of the body. An anchor can no longer change a carried request, move it to another mesh key, use its token, or turn a joiner's request into a retry. A node holds at most one request of each of 7 kinds, so at most 6 wait. Section 8 and ADR 0065 now state only what holds, the remaining replay case included.

## Changes

- `spec/arfc-0002-identity-and-join.md`: section 2 adds the join token key. 3.2 defines the token key (seed `BLAKE3("alloy/id/token-key/v1" || secret)`, RFC 8032) and `token_pub`, sent and stored instead of `BLAKE3(secret)`. 3.3 step 6 defines the join message, `token_signature`, and `identity_signature`. Check 1, the token check, the refusal table, and 3.3 approval now use signatures, not the secret. 3.13 covers the forwarded `join_request` rule and request kinds, one held per kind and a request of a held kind not added. The proto splits `JoinRequest { body, token_signature, identity_signature }` and `JoinRequestBody` (field 2 reserved). 3.14 stores `token_pub`. Section 6 counts `token_refused` uses. Section 7 adds the kinds bound. Section 8 is rewritten for anchors.
- `spec/arfc-0018-observability-and-audit.md`: 3.3 digest example names the login code `secret`, since `join_request` holds no secret field.
- `adr/0065-node-requests-are-keyed-by-mesh-key-and-act-only-on-the-requ.md`: adds the token key, the two join signatures, and the per-kind bound. Rejects a MAC keyed with the stored hash, and a token proof without an identity signature.

Findings, by id:
- F1 (block): fixed. Both signatures cover the mesh key and the whole body. The anchor holds neither key nor the secret. A retry needs the joiner's identity signature (ARFC 0002 3.3 step 6, 3.13, section 8; ADR 0065).
- F2 (block): fixed. Each kind has at most one request outstanding or waiting, a due request of a held kind is not added and its asker takes the held one's outcome, and the waiting order is stated (3.13, section 7).
- F3 (fix): fixed. Section 8 lists every effect of an anchor: reading state, dropping or delaying, an unchanged replay while the token is usable, and `key_in_use` only with a token held by other means. It drops the false `key_in_use` claim for carried tokens.

## Decisions

- N: a token proves itself by an Ed25519 key derived from its secret, not by a MAC keyed with the stored hash, so a reader of the store cannot make join requests and no primitives row changes (`agent/eng/crypto.md`).
- N: ADR 0040's "secret matches" is read as "the token key's signature verifies". ADR 0065 records this refinement and does not supersede ADR 0040, whose ordering and refusal rules hold.
- R: a request of a kind already held is merged, not queued or refused, since every kind's bytes are fixed or periodic.
