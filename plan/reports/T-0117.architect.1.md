## Summary

`disk-io` gains four methods and their types in ARFC 0005 section 2.4: `create_file` and `create_dir_protected` take a `Protection` (`Default`, `Private`, `PrivateRoot`). `security` returns `Security::Unix` or `Security::Windows` without following a link at the last component. `set_mode` is for Unix only.
New clause 3.1.15 states their behavior under `os` on Linux, macOS, and Windows and under `mem`. It also gives the route by which a library that opens its own files, as `redb` does, gets the same protection. The trace operations 13 to 16 and two limits are added.
ARFC 0002 section 3.12 now says how `alloy` and `alloyd` meet the data directory rules through the seam. This resolves the T-0106 follow-up and gives T-0107 F4 a route that ARFC 0006 clause 5.2 already allows.

## Decisions

- N: the change is additive. `open`, `create_dir`, `metadata`, and `OpenOptions` are unchanged, so existing callers and the conformance suite stay valid. Only the three implementors change: `os`, `mem`, and the stub in `alloy-rt/src/runtime.rs`.
- N: on Windows, `Private` and `PrivateRoot` set the owner to `Administrators`. With the default owner, an admin user's unelevated token would own key files and so hold an implicit `WRITE_DAC`. Naming an owner the token cannot assign returns `PermissionDenied`.
- N: a Windows `Private` entry is created with an empty, unprotected list. Its list is then exactly what it inherits, or empty, never the token's default list.
- N: `set_mode` returns `Unsupported` on Windows, which adopts no existing directory (3.12).
- N: `mem` is shaped like Unix: every entry is owned by uid 0, there are no links, and modes are 0o755, 0o644, and 0o660 by default. Wrong-owner cases are therefore tested on `os` and through `alloy-id`'s pure fact checks.
- R: `Ace.allow` is false only for the four access-denied types, so an unknown type counts as a grant.
- R: no ADR. The task names no ADR number. The interface is additive and fills a gap that 3.12 already required.
