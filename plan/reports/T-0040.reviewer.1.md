Attacks tried. This is a spec task with no code, so there is nothing to fuzz or run in the simulator. Each attack is a scenario traced through the amended clauses:

1. Hostile tenant grows lineage state. Kept keys grow only at an exchange (3.9.1), which section 7 refuses at 1,000 kept keys per user. A revocation never adds a kept key. `issued_by` names only a key of the same user (3.9.2, 3.9.5), so descent never crosses users, and a revoked service account key has no user key descending from it and is deleted at once. Derivation lives in the signed token (2.3). The per user bound holds. No finding against the branch; the total over users is open (Issues).
2. Thief evades the remedy. Stolen key K, then a chain T1 to T999, each issued by the one before and each exchange naming the one before in `replaces`. Every revoked T stays kept while T999 is unrevoked, K stays kept, and one revocation of K with `descendants: true` revokes T999 and deletes the whole chain (3.9.7, 3.9.11). Deleting a key never changes descent among kept keys, since every ancestor of an unrevoked key is kept. Temporary key chains: `via_temporary_key` propagates through every credential obtained by a temporary key or by a credential carrying it, and 3.9.2 refuses both. Key id reuse after deletion cannot revive a token (the creation time check in 3.9.7). No finding. But the victim must hold a credential to send that revocation (F2).
3. Ordinary computers after the change. A computer whose key was revoked from another computer, with no descendant, finds that key deleted, then logs in again: the CLI sends `replaces` with the deleted id, and 3.9.10 and 3.9.11 give opposite outcomes (F1). A computer that rotates its own key by issuing a code with it and logging in with `replaces` keeps every replaced key, one per rotation (F3).
4. Exchange authorization (F4 of T-0023). Clause 3.9.4 now says no policy is evaluated at the exchange and the listed checks are the whole authorization, which matches ADR 0041 Consequences and section 8. No finding.

ADR 0041 checked against the amended text: each guarantee it states holds in ARFC 0007, as the architect report says. The limit of F2 is about whether the victim can send the revocation, not about what the revocation does.

## Issues

- `spec-issue`: ARFC 0007 section 7 bounds kept access keys per user but states no bound on users per org or per cluster, so the access key table as a whole still has no stated bound (I-21) (`spec/arfc-0007-tenancy-and-iam.md`, section 7).
- `follow-up`: conformance case in `tests/conformance/authn` for an exchange whose `replaces` names a deleted key, once F1 is ruled (`spec/arfc-0007-tenancy-and-iam.md`, clauses 3.9.10 and 3.9.11).
- `follow-up`: the lockout in F2 is also reachable on main through the 100 unrevoked key limit (a thief makes 99 more keys from the stolen one, and the local admin recovery exchange then fails). Any recovery path chosen for F2 should cover both limits (`spec/arfc-0007-tenancy-and-iam.md`, section 7 and clause 3.10.1).
