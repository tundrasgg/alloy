Attacks tried. This is a spec task with no code, so there is nothing to fuzz or run in the simulator. Each attack is a scenario traced through the amended clauses.

1. Thief disables the recovery path. User `admin` is the only `cloud-admin` and `owner` of `default` (PB-0001). A thief holds its only key K. Acting as `admin`, the thief attaches to `admin`, or to org `default`, a deny on `iam:RevokeUserAccessKeys` and fills the 100 unrevoked keys, or attaches denies on both `iam` actions. The local admin's revocation is refused (3.10.1, lines 295 to 297); its login code is refused by the deny on `iam:IssueLoginCode`, or its exchange is refused at the limit (section 7). No other path is specified, and K is never revoked: the outcome ADR 0050 line 40 rules is against ARFC 0020 section 3.4. Section 8 itself says the user's policies cover attaching a policy (lines 420 to 422). A variant, already raised by the architect as a `spec-issue`, removes `cloud-admin` from `admin`, after which neither local admin action reaches it (F1).
2. Thief outlives a revocation. The local admin revokes all of `admin`'s keys. For up to 5 seconds a control node that has not applied the commit still authenticates K (3.9.12, line 251). The thief, sending to every control node, has a login code issued with K in that window. Nothing refuses it at commit (3.9.2 checks only user and org state) and nothing voids it later (3.9.7 voids only codes that exist when the revocation commits). The thief exchanges it (3.9.4 checks only user and org state) for K2, unrevoked, `issued_by` K, which was deleted by the revocation. 3.9.13's "no unrevoked key" no longer holds after commit, 3.9.11's "every key that an unrevoked key descends from is kept" is false for K2, and no revocation can name K to reach K2. Revoking K2 repeats the same window, so a scripted thief is never removed. The same holds for one key revoked with `descendants: true`, which predates this branch (F2).
3. Deleted key ids (T-0040 F1). An exchange whose `replaces` names a deleted key: ignored, response and error those of the same exchange without it (3.9.10), so the computer logs in again. SigV4 with a revoked, deleted, or never issued id: `Unauthenticated`, one code and one message (3.9.12). Reading or revoking by a deleted id: `NotFound`, the only `NotFound` rule, scoped to that target (3.9.11). Each request now has one outcome. No finding.
4. Re-login chains (T-0040 F3). Traced a computer that rotates its key n times with codes issued by the key it replaces: n kept revoked keys, freed by revoking the newest, by 3.9.13, or by a re-login with a code from outside the chain, each of which leaves no unrevoked descendant and deletes the chain under 3.9.11. Matches section 7. No finding.
