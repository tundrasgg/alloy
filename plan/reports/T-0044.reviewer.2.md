Section 3.10.2 says the socket "serves the native API methods behind the four actions above and nothing else". Section 2.4 says actions take `*` as a suffix and resources take `*` per segment. `grep -rn -i "create.*user\|CreateUser"` over `spec/` finds no call that creates a user or lists users, and none that grants or removes a cluster role. PB-0001 line 189 says "Password login for other users is not part of this brief."

Attacks tried. This is a spec task with no code, so each attack is a scenario traced through the amended clauses. The setting is PB-0001: user `admin` is the only `cloud-admin` and is `owner` of `default`, and a thief holds its only key K.

1. **Hidden last `cloud-admin`.** Acting as `admin`, the thief creates or picks a user U2 in some org and gives it `cloud-admin`. Then it removes `cloud-admin` from `admin`, which 3.10.8 allows because U2 remains. The local admin can still revoke all of `admin`'s keys (line 298). It cannot issue `admin` a login code, because `admin` no longer holds `cloud-admin` (line 297). Its fallback in section 8 is a login code for U2. The table limits that action to "A named user", and the local admin has no action that lists users or their roles (lines 302 to 303, 3.10.2). Nothing it can call, and no error it can get, tells it U2's name or org, and the thief chose both.
   `admin` holds no credential. PB-0001 has no password login, and only `admin` itself could issue it a code (3.9.2). So no person can administer the cluster through any specified path. This contradicts lines 449 and 450 and ADR 0050 line 27 (F1).
2. **Deny on the recovered user.** Acting as `admin`, the thief attaches to org `default` a deny on `iam:*` over resource `*`, and optionally on every other service's `*`. The local admin revokes K and issues `admin` a login code: no deny binds it (line 304). `admin` exchanges the code, since no policy is evaluated at the exchange (3.9.4). Every call it then makes, detaching that deny included, is refused by 3.1, because the deny is attached to its org (the same attachment 3.9.2 lines 137 to 139 uses).
   No other `cloud-admin` exists, and no deny binds only the local admin, whose four actions cannot detach a policy. The key is revoked, so ARFC 0020 section 3.4 holds. But the cluster's only administrator can do nothing, against lines 449 and 450 and the task's goal that the user "can recover". Section 8 lines 458 to 460 list an attached policy as something the remedy does not undo and that "the audit log lists". That assumes the recovered user can remove the policy, and this attack makes sure it cannot (F2).
3. **Revocation window (round 1 F2).** The local admin revokes all keys of `admin`. For 5 seconds, a node that lags still authenticates K. The thief asks for a login code with K, or with a session token that derives from K. 3.9.2 now reads committed key state in the issuing transaction and refuses with `PermissionDenied`. If the issuing commits first, 3.9.7 voids the code. No key with `issued_by` K is created after the revocation, so 3.9.11 and 3.9.13 hold after their commit. Resolved.
   In the same window, K can still create a service account access key, which section 8 lines 458 to 460 already list as outside the remedy and ARFC 0020 section 3.4 permits for 5 seconds. ADR 0050 line 40 says the opposite: that only a login code makes a credential that outlives the key (F3).
4. **Deny and role on the revocation (round 1 F1, first half).** A deny on `iam:RevokeUserAccessKeys` attached to the user, a group, or the org does not refuse the local admin (line 304). Removing `cloud-admin` from the user, disabling the user, or disabling its org does not either (line 298, lines 307 to 310). Full key limits do not (section 7 line 398). The revocation of K always succeeds. Resolved for revocation.
5. **3.10.8 against other clauses.** It was checked against 3.7 (org deletion after a 7-day disabled grace, which never removes a counted user because a disabled org's users do not count), 3.9.8, ARFC 0002 section 3.1 (`init` creates `admin` with `cloud-admin`), and I-16. No contradiction found.
6. **Round 1 F3.** ADR 0050 line 17 names "Every built-in org role and the cluster role `cloud-admin`", the same set as clause 3.9.13 line 276. Resolved.
