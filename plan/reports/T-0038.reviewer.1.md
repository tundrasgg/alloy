Model (scratch, not committed, about 150 lines, `probereplay.py`). It encodes only the branch text of 3.6:

- The record holds the newest epoch, the highest index, and a window of 2,048 indexes.
- The pass rule and the replace-on-newer-epoch rule are as written.
- A record is kept at least 10 s after the last send or accept.
- At the limit, the least recently used record past its keep is dropped. If there is none, no record is created.
- Records live in memory. Only the epoch counter is persistent (3.6, "Epochs").
- Captures are 20 probe sets of 20 messages from A to B, with increasing epochs, delivered genuinely before the replays start.

```
$ python -I probereplay.py 1000
held: seeds 1000, replays accepted 0
after 10 s idle: seeds 1000, replays accepted 400000 of 400000
crash < 1 s after last accept: seeds 1000, replays accepted 400000 of 400000, max idle 1.00 s
pin: limit 4096, replayed peers 4096, seeds 50, probe starts to new peers refused 2500 of 2500
pin: limit 4096, replayed peers 4000, seeds 50, probe starts to new peers refused 0 of 2500
```

How to read the output:

- "held": while the record is held, no replay is accepted, in any order.
- "after 10 s idle": B drops the record, and then every captured message is accepted once more. The attacker replays them in epoch order. This repeats after every later 10 s idle period.
- "crash": the same happens after B crashes or restarts with no idle period, because no record survives.
- "pin": the attacker replays one unused captured message per peer every 8 to 9.5 s. When it does this for as many peers as the record limit, every attempt by B to start probing a new peer finds no free record (3.6 lines 364 to 370). With 96 slots left free (4,000 peers), B is never refused, which is the control case.

Verified sources (text trace): ARFC 0004 section 3.2 step 5 (`spec/arfc-0004-path-manager.md:68-69`) limits "answered only while the node is probing the sender" to messages from endpoints that are not verified. Verification lapses only when no `usable` path uses the endpoint and the node is not probing (`:72-73`). When A and B share an active direct path, A's endpoint stays verified. B's probe record of A still lapses after 10 s, because keepalives are transport packets and not probe messages. A replayed A-to-B probe sent from A's verified endpoint is therefore accepted (B holds no record) and answered at any time, not only while B is probing A.

Developer evidence check: the architect's CI output, grep output, and length arithmetic match what I observed. The F6 argument in the architect's report holds for replays of earlier probe sets.

## Issues

- `spec-issue`: `spec/arfc-0004-path-manager.md:199` (64 answer challenges per peer, oldest dropped first) can still be flooded without any replay. A probes every candidate pair, B's private local candidates included. On A's network, a host that holds the same private address receives those probes, which are genuine current-epoch messages that B never got. That host can inject each one at B once from a spoofed unverified source after A's newest set has been heard. Each one passes the 3.6 replay check and draws an answer challenge. I did not model this. It belongs with T-0043 or a follow-up, not with the replay check.
