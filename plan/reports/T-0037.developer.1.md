## Summary

CI now runs `cargo xtask ci` with `--base`, so the `check-repo` path lock runs on every pull request and every push to `main`.
A pull request passes `--base origin/<base branch> --branch <head branch>`, because its checkout is a detached merge commit. A push passes `--base <previous commit> --branch <pushed branch>`.
The checkout fetches the whole history (`fetch-depth: 0`) so the merge base resolves. Event values reach the shell only through environment variables.
`actionlint` (official `rhysd/actionlint` 1.7.12 image, shellcheck 0.11.0 inside) and `cargo xtask ci --base main` exit 0. A local copy of the pull request checkout runs the lock and rejects a probe commit under `tests/conformance/`.

## Changes

- `.github/workflows/ci.yml`: `fetch-depth: 0` on checkout, and the gate step picks `--base` and `--branch` per event

External facts the workflow relies on:

- `fetch-depth: 0` fetches all history for all branches and tags, so `origin/<base branch>` exists (https://github.com/actions/checkout#usage).
- `GITHUB_BASE_REF` and `GITHUB_HEAD_REF` are set only for `pull_request` events; `GITHUB_EVENT_NAME` and `GITHUB_REF_NAME` always (https://docs.github.com/en/actions/reference/workflows-and-actions/variables#default-environment-variables).
- A `push` event's `before` is all zeros when the ref had no previous commit, for example the first push of `main` (https://docs.github.com/en/webhooks/webhook-events-and-payloads#push). The workflow runs without `--base` then, since there is nothing to diff.

## Decisions

- `fetch-depth: 0` rather than a shallow fetch of the base branch. It always resolves the merge base, for pull requests and for `before` on pushes, at the cost of fetching full history; that cost grows with the repository and can be revisited if checkout time shows up.
- The push form also passes `--branch` (the pushed branch name), so the verdict does not depend on whether the checkout leaves HEAD on a branch. On `main` the lock judges nothing, since `main` is not a `task/T-NNNN` branch.
- `GITHUB_HEAD_REF` is chosen by the pull request author and is passed only through the environment, never through `${{ }}` in the script, so a branch name cannot inject shell.
- An event other than `pull_request` or `push` fails the step with a message, instead of running the gate without the lock.

## Issues

- `follow-up`: the path lock trusts the branch name, and on a pull request that name is the author's choice. A fork branch not named `task/T-NNNN`, or named after a `verify` task, skips the lock (`xtask/src/rules/path_lock.rs`). The lead decides whether the lock should judge pull requests by something the author cannot pick.
