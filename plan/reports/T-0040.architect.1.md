## Summary

ARFC 0007 now bounds all lineage state (I-21). Derivation is carried in the signed token, so the control plane keeps no record per session token or temporary key. A revoked key is kept only while an unrevoked key descends from it, and kept keys are capped at 1,000 per user, enforced by refusing the exchange and never by dropping a key.
F2, F3, F4, and F5 are closed in the ARFC. F6 is listed as a `follow-up`.
ADR 0041 is not edited. Each guarantee it states holds in the amended ARFC.

## Changes

- `spec/arfc-0007-tenancy-and-iam.md`: sections 2.3, 3.9.2, 3.9.4, 3.9.6, 3.9.7, 6, 7, 8 amended; new clause 3.9.11 (lineage state). No clause renumbered.
- `plan/reports/T-0040.architect.1.md`: this report.

Findings of `plan/reports/T-0023.reviewer.2.md`:

- F1 (block): resolved. Section 2.3 moves derivation into the token payload, as `derives_from` (the one access key a credential derives from, or empty) and `via_temporary_key`. Both are covered by the signature and copied on refresh. The control plane keeps no derivation record per credential, so the derivation table F1 names no longer exists. Clause 3.9.7 accepts and refreshes such a credential only while its key is kept, is unrevoked, and was created before the credential was issued. A deleted key therefore refuses its derived credentials, and a reused key id cannot revive them. Clause 3.9.11 keeps a revoked key exactly while an unrevoked key descends from it and deletes it in the transaction that ends this. Every ancestor of an unrevoked key is therefore kept, and deleting a key never changes descent among kept keys. Section 7 caps kept keys at 1,000 per user. An exchange at the cap fails without spending the code, and no limit refuses or narrows a revocation. Section 8 states the price: a thief can fill the cap and refuse new logins, and one revocation of the stolen key with `descendants: true` deletes the thief's keys and frees the room.
- F2 (fix): resolved by closing the gap. A session token obtained through a temporary key carries `via_temporary_key`, and clause 3.9.2 refuses a login code to a request authenticated by a temporary key or by such a token. The reason stated in ADR 0041 now holds.
- F3 (fix): resolved. Clause 3.9.7 accepts a revocation request on a key that is already revoked and still kept, however it was revoked, `replaces` included. With `descendants: true` it revokes every unrevoked descendant. A revoked key with an unrevoked descendant is always kept (3.9.11), so the section 8 remedy survives a re-login through `replaces`. A revoked key that is no longer kept has no unrevoked descendant, so the `NotFound` it returns loses nothing.
- F4 (fix): resolved. Clause 3.9.4 says that no policy is evaluated at the exchange, and that a valid unspent code plus the listed checks are its whole authorization. This matches ADR 0041 Consequences: a later deny does not void an issued code.
- F5 (note): resolved in one sentence. In clause 3.9.6, the cluster role `cloud-admin` now also lets a user list and revoke its own keys, which matches the roles that may issue on the holder's own user (3.9.2).
- F6 (note): not fixed. The fix needs the CLI to learn the user of the new key and revoke the old key itself, and that flow belongs to ARFC 0019. Listed under Issues.

ADR 0041 checked line by line against the amended text: issued_by, listing and revocation within 5 s (3.9.6); `replaces` (3.9.10); derivation and "a temporary key cannot issue a login code" (2.3, 3.9.2, now stronger); voiding, ending derived credentials, descendant count, `descendants: true` (3.9.7); one revocation removes every key, code, token, and temporary key that exists because of the stolen key (3.9.7, 3.9.11, section 8, including after `replaces`); `session` keys descend from no key (3.9.5, section 8). ## Decisions

- Derivation is carried in the signed session token (`derives_from`, `via_temporary_key`), not in a control plane table. Reason: a table would need a per-principal cap that could refuse the temporary credentials of an instance role shared by many instances (ARFC 0011). The token form adds no state at all. This also answers the T-0023 architect `spec-issue` about where derivation lives. The token payload grows by two fields. It is not frozen.
- A credential that derives from a key is accepted only while that key is kept, is unrevoked, and was created before the credential was issued. Reason: a deleted key refuses its credentials with no history kept, and a reused id cannot revive them.
- A revoked key is kept exactly while an unrevoked key descends from it, and is deleted in the transaction that ends that. Reason: this is the least state that keeps every descent guarantee. Purging by age or count could drop a stolen key that a thief's live key descends from.
- 1,000 kept keys per user, enforced by refusing the exchange, never by purging. Reason: a purge lets a thief push the stolen key out of state. Refusing costs at most a lockout of new logins, which the holder of the stolen key could cause anyway, and the remedy revocation frees the room. Ordinary use reaches the cap only through hundreds of re-logins of computers whose keys issued still-live keys.
- A request naming an access key that is not kept fails with `NotFound`. This names `NotFound`, which no ARFC named before.
- A credential obtained through a temporary key, by any chain, cannot issue a login code (`via_temporary_key`), rather than forbidding a temporary key from obtaining credentials. Reason: it keeps every existing way of obtaining credentials.
- No ADR is written. The touches list excludes `adr/`, and the task says ADR 0041 is not edited. The changes make ADR 0041's guarantees hold and add bounds. The lead decides whether the token payload change needs its own ADR under `agent/protocol/spec-change.md`, which asks for an ADR on a behavior change.

The CLI flow in ARFC 0019 should revoke the stored key with itself (ARFC 0007 clause 3.9.6) when the new key belongs to another user, or ARFC 0007 should state the limit (`spec/arfc-0019-cli-and-console.md`, `spec/arfc-0007-tenancy-and-iam.md` clause 3.9.10).

- `spec-issue`: the meaning of `key_id` in the token payload is not stated in any ARFC (`spec/arfc-0007-tenancy-and-iam.md`, section 2.3).
- `process-issue`: `agent/protocol/spec-change.md` asks for an ADR on any behavior change to an accepted ARFC, but this task's `touches` excludes `adr/`. The lead should either include `adr/` in `touches` for behavior-change spec tasks or record that the ADR is not needed.
- `follow-up`: conformance cases in `tests/conformance/authn` for: a session token obtained with a temporary key and refused as an issuer of a login code; `descendants: true` on a key already revoked through `replaces`; a revoked key deleted when its last unrevoked descendant is revoked, and `NotFound` afterwards; a derived credential refused after its key is deleted; an exchange refused at 1,000 kept keys without spending the code; a user holding only `cloud-admin` revoking its own key.
