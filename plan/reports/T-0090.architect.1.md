A node now holds the challenges of a path's checks apart from every other probe challenge, so no probe set of any size displaces one. The sending rules hold at most 11 outstanding checks per path, and section 7 states that bound and what happens at it. ## Decisions

- Checks get their own per-path table, which is never evicted. I did not cap candidate pairs per probe set. A cap would need a rule for which pairs to drop, and it would change behavior that no finding names.
- When E stops being verified, the node discards the challenges of the path's outstanding checks at once, not 2 s later. That keeps "since E last became verified" exact. An echo that arrives late verifies nothing, and the next probe set verifies E again.
- The bound is 11 per path, the exact maximum of the sending rules. It is not a padded number, so a verifier can reach it (the stress run does) and check that nothing is dropped.

## Issues

- `spec-issue`: the probe replay window of `spec/arfc-0003-mesh-wire-protocol.md` section 3.6 holds 2,048 counters. A probe set round can seal up to 4,096 probes (64 by 64 candidates, ARFC 0004 section 7). A check counts as missed with no packet dropped if at least 2,048 probe messages sealed after it in the same session reach the peer first over faster pairs. This needs ≥ 2,048 reachable pairs and reordering across them, and ARFC 0003 calls it "dropped or reordered", so it falls under the task goal's "lost or overtaken". A bound on probes per round relative to the window would close it. My model uses one delay for all pairs and does not exercise it.
- `follow-up`: I confirm the T-0080 reviewer's issue. Honest probe sets over many pairs to endpoints that are not verified can exceed the 64-entry answer challenge table (`spec/arfc-0004-path-manager.md:380`). This task does not touch it.
- `process-issue`: I repeat the T-0080 issue. The models behind the class counts still live only in scratch. This is the third round in which a reviewer cannot rerun them. A committed home such as `spec/models/` would fix that.
