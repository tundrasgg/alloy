## Summary

Added the `conformance-rt` crate at `tests/conformance/rt/`: 115 checks that are generic over the five runtime seams and run against any implementation through a `Harness`, plus 24 unit tests of `alloy-rt` items that need no seam instance.
Each check is named after its clause. A check of a clause that names one implementation runs only on that implementation (ARFC 0005 section 5).
The acceptance command compiles the suite. The 28 unit tests pass against `alloy-rt` today, and `cargo xtask ci` passes.
No `mem` or `os` implementation exists in the workspace yet, so the 115 seam checks compile but nothing runs them yet (see Issues).

## Changes

- `tests/conformance/rt/Cargo.toml`: new package `conformance-rt`, which depends only on `alloy-rt` and `alloy-seam`.
- `tests/conformance/rt/lib.rs`: the harness contract (`Implementation`, `Applies`, `Env`, `Failure`, `Outcome`, `Check`, `Harness`, `checks`, `run_suite`), plus catalogue tests that every check names its clause, that names are unique, and that the panic flags are correct.
- `tests/conformance/rt/support.rs`: shared helpers (deadline wrapper, poll-once, counting waker, gate, drop flag, SplitMix64 test data). None of them implements a seam.
- `tests/conformance/rt/clock/mod.rs`: suite `clock`, clauses 2.1, 3.1.3, 3.1.4.
- `tests/conformance/rt/rng/mod.rs`: suite `rng`, clauses 2.1, 3.1.3, 3.1.5.
- `tests/conformance/rt/spawn/mod.rs`: suite `spawn`, clauses 2.2, 3.1.6.
- `tests/conformance/rt/net/mod.rs`, `net/udp.rs`, `net/stream.rs`: suite `net`, clauses 2.1, 2.3, 3.1.7 to 3.1.9.
- `tests/conformance/rt/disk-io/mod.rs`: suite `disk-io`, clauses 2.1, 2.4, 3.1.3, 3.1.10, 3.1.11, 3.1.13.
- `tests/conformance/rt/runtime/mod.rs`: `Runtime`, `JoinHandle`, `sleep`, `timeout`, and `from_registry`, clauses 2.5 and 3.1.14.
- `Cargo.toml`: added `tests/conformance/rt` to `[workspace] members` in sorted order (shared workspace file).
- `deny.toml`: added `conformance-rt` to `[bans] allow` in sorted order (shared workspace file).
- `Cargo.lock`: cargo added the new workspace package.

## Decisions

- Class N: new workspace member `conformance-rt` at `tests/conformance/rt`, added to the root `Cargo.toml` `members` and the `deny.toml` `allow` list. The lead records it in `plan/decisions.md` and `plan/workspace.md`, which this role cannot write.
- Class N: the harness contract in `tests/conformance/rt/lib.rs` is how every implementation runs the runtime suites: a `Harness` builds a fresh `Env` per `Check` and returns its `Outcome`. The `mem` harness (alloy-sim, T-0075 to T-0078) and the `os` harness must satisfy the requirements in `Env`'s doc comment: a fresh host with no faults, an empty `scratch` directory, `unix_dir`, a zeroed block device of at least 1 MiB (required for `mem`), and `file_block_size`.
- Class N: two checks panic one task on purpose and carry `panics_a_task`. A `mem` harness must not count that panic against the check, since ARFC 0005 section 6 makes such a run's result `fail`.
- Class R: limit checks (4,096 UDP sockets, 65,536 streams and listeners, 65,536 disk handles, 1,048,576 tasks) build a fresh instance from the registry, so the count starts at zero. They require the exact limit on `mem`. On `os` they accept a lower platform limit, as long as the error at the bound is the specified variant.
- Class R: the stream-limit check uses Unix listeners, because `mem` TCP ports per address (16,384) cannot reach 65,536.
- Class R: `UnixPath::new` is checked to return `InvalidInput` for every rule it breaks. Section 7 names `InvalidInput` for the length bound, and the section 2.3 signature returns `NetError`.
- Class R: data in the checks comes from a SplitMix64 generator seeded by `Env::seed` or by fixed seeds, not `proptest`. This avoids the open `proptest` seeding rule noted in `plan/STATE.md`.
- Class R: to confirm that the interface matches ARFC 0005 section 2, I listed the `pub` signatures of `crates/alloy-rt/src/*.rs` with `grep`. I read no function bodies or tests of `alloy-rt`; the listing showed only some unit test function names.

## Issues

- `spec-issue`: ARFC 0005 clause 3.1.8 sets `max_payload` to "MTU minus the IP header minus 8". When the MTU is above 65,535, for example Linux loopback at 65,536, this gives 65,508 for IPv4, above the 65,507-byte IPv4 payload maximum that section 2.3 states (`RecvSlot::MAX_CAPACITY`), so no payload reaches the bound. The check skips that family in this case (`tests/conformance/rt/net/udp.rs`, `arfc0005_s3_1_8_datagram_above_the_path_mtu_is_message_too_long`). The spec should cap the path MTU at 65,535, or `max_payload` at 65,507 and 65,527.
- `spec-issue`: ARFC 0005 clause 3.1.9: "creates the socket file with the permission bits `unix_mode & 0o777`" cannot be observed through any seam. The suite may not call platform file APIs (the direct-io ban), and the native Unix path is not in the `disk-io` namespace. Either state it as `os`-only and checked by a system test, or give `Net` a way to report it.
- `spec-issue`: ARFC 0005 clause 3.1.8: "`PermissionDenied` when the platform refuses the port" has no deterministic trigger. On `os` it depends on the process's privileges, and for `mem` the spec does not say when, if ever, it refuses a port. Untested.
- `follow-up`: no harness runs the 115 seam checks yet. A `verify` task should add `tests/conformance/rt/tests/mem.rs` (a `Harness` over `alloy_sim::run`) once T-0075 to T-0078 merge. Another should add `tests/conformance/rt/tests/os.rs` once the `os` implementations exist.
- `follow-up`: ARFC 0005 section 2.6 (`OsHost`, `register_os`) is not exported by `crates/alloy-rt/src/lib.rs`. The `os` build task needs it, and so does an `os` harness.
- `process-issue`: T-0008's `touches` lists only `tests/conformance/rt/**`. The suite is a new crate, so it also changed the shared workspace files `Cargo.toml`, `deny.toml`, and `Cargo.lock`, which D-0006 says the task lists in `touches` (`agent/protocol/tasks.md`, Shared workspace files).
- `process-issue`: the diff is about 6,150 lines (rustfmt layout included), over the 2,000-line target for a verify task. One test per must across five seams does not fit that target. Splitting one verify task per seam would.
