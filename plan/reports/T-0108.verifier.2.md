## Summary

Both suites now run against the merged `alloy-state` and pass: `mem` on a simulated host and `native` on the host in a temporary directory.
The 5.1 stand-ins are gone. Each suite takes the seam items by `pub use alloy_state as state;`, and only the public interface of `alloy-state` was read, not its `src/` bodies.
Each suite has a `tests/conform.rs` harness. Every check gets a fresh `Env` and a seed taken from the check's name, and a failure prints that seed.
The 5.5 kill check (`crash::child`, `crash::after_kill`) is written but not run. Starting a child process needs `std::process::Command`, which the `direct-io` ban in `clippy.toml` forbids in this crate.
Failing for the right reason is not shown: the implementation was already merged when the checks first ran, and every check passed on that first run.

## Changes

- `Cargo.toml`: main's manifest plus the two suite members. The merge conflict came from CRLF line endings in round 1's copy.
- `Cargo.lock`: the suites' new dependencies `alloy-state` and `alloy-sim`.
- `tests/conformance/{log-store,state-store}/Cargo.toml`: depends on `alloy-state`; dev-depends on `alloy-sim`.
- `tests/conformance/{log-store,state-store}/lib.rs`: `state` is `alloy_state` re-exported.
- `tests/conformance/{log-store,state-store}/state.rs`: deleted.
- `tests/conformance/log-store/tests/conform.rs`: `MemHarness` runs each check as the boot task of one simulated host, with `mem` from one fresh `register_mem`. `NativeHarness` runs each check on an `os` runtime whose `disk-io` is rooted at the temp dir, with `native` registered and two fresh directories per check, which it removes afterwards. The file ends with one test per implementation.
- `tests/conformance/state-store/tests/conform.rs`: the same harnesses. On `native`, the registry also holds `mem` from one fresh `register_mem`, for the cross-implementation check.

These cases have no running check, each for the reason given:
- 5.3.2 kill during a call, and the 5.5 native kill check: the code is written but nothing runs it, because no process can be started here (see Issues).
- 5.3.8 and 5.4.7 on `native`: nothing makes `redb` fail on demand. Both are checked on `mem` through `fail_after`.
- 5.4.2 kill during `apply` or `finish`: 5.5 asks for no state-store kill check, so only durability across a restart is checked.
- 5.2 `native` file mode `0600` and the Windows ACL: inspecting the files would break the `direct-io` ban.
- 5.2 a second instance on the same `dir` in another process: needs a second process. Only the same-process case is checked.

## Decisions

- Seed per check: the FNV-1a hash of the check's name. The seed is fixed per check, so the same binary gives the same data. A failure prints the seed.
- Native directory names add 8 bytes from the `os` rng, so runs that happen at the same time never share a directory. The bytes do not reach any check's data.
- Failing to remove a check's directory does not fail the check: it is cleanup and changes no outcome.
- Round 1's decisions are unchanged and hold against `alloy-state`: `Config(Invalid)` field names, `Malformed` from `write` or `finish`, and `fail_after` across instances.
