## Decisions

- No API method may change which actions a built-in role allows, for any caller (3.10.1). Reason: otherwise a stolen `cloud-admin` key could shrink the local admin's cluster part and make the recovery guarantee hold vacuously (F3).
- Clause 3.10.7 fixes where a deny can apply to a call by the recovered key: the caller's side (`U`, its groups, `O`) and the target's side (resource policy, project, org, and a target principal with its groups), and nowhere else. Reason: 3.1 says "every policy that applies" without listing them, and the guarantee is testable only against a closed list (F1).
- The paths from `iam:*` to tenant data stay in the fixed policy and are named, not excluded. Reason: recovery needs a login code for any user, an org `owner` included (D-0020), so excluding them would bring back the dead ends ADR 0055 removes (F2).

Section 8 therefore describes the credential-setting actions by kind ("any other `iam` action that sets how the principal authenticates"). The spec task that names them must keep each such method an audited write in the org's chain (`spec/arfc-0007-tenancy-and-iam.md`, section 2.4).
- `spec-issue`: clause 3.1 says "gather every policy that applies" without defining which attachments apply to a call. Clause 3.10.7 now lists them for one case, and 3.1 should state the rule for all (`spec/arfc-0007-tenancy-and-iam.md`).
- `follow-up`: conformance cases for 3.10.7 should include a deny attached to an org other than the recovered user's, to a project, and to a target principal, each refused before and allowed after the local admin detaches it (`spec/arfc-0007-tenancy-and-iam.md`).
