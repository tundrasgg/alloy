## Summary

Rung 2 builds what `alloy node list` needs on each machine. That means login on every machine, as ARFC 0002 section 3.7 and ARFC 0018's rung 2 note already assume. It builds nothing more.
`init` creates the org `default`, the user `admin` with `cloud-admin`, the join token, and the login code. It creates no project, pool, or `disks/0`, and prints nothing about them. Join tokens and the identity objects get resource kinds.
Reflection is skipped until rung 3. An anchor sends only to the endpoint whose authenticated packet confirmed the session, and that endpoint never moves.
`net` gains `Stream::peer_uid` (`SO_PEERCRED`; Windows needs none, since it never holds `control`), and `disk-io` gains a durable `replace`. ADR 0068 records the profile.

## Decisions

- N: rung 2 includes `alloy login <code>` and local admin `--issue-code`. ARFC 0019 clause 3.1.14 does not route `node list` through the socket, and two of the three machines have no socket.
- N: rung 2 is released only as previews. A preview cluster never changes release, so deferred objects need no migration.
- N: access key secrets are sealed under the single control node's at-rest key until `key-provider` exists. This meets ARFC 0020 clause 3.7.
- N: login codes are issued only by `init` and the local admin, and `IssueLoginCode` on the API port is `PermissionDenied`. So no key lineage exists in rung 2.
- N: methods rung 2 does not build answer gRPC `UNIMPLEMENTED`.
- N: no standing warnings in rung 2. The `local-admin-used` record is still kept, and the audit log has every use.
- N: `mem` `peer_uid` is always 0. The refusal of another user id is tested under `os`.
- N: `replace` requires both names in one directory.
