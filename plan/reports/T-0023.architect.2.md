Findings:

- F1: resolved by closing the gap, not by narrowing the claim. Section 2.3 defines when a session token or temporary key derives from an access key. Clause 3.9.5 records the access key behind a session token as `issued_by`. Clause 3.9.2 refuses a temporary key as issuer. Clause 3.9.7 voids codes issued through derived session tokens, ends derived session tokens and temporary keys within 5 seconds, and keeps descent intact across a revoked key in the middle of a chain. Section 8 and ADR 0041 state the two limits that remain: other uses of the user's policies, and keys whose `issued_by` is `session`.
- F2: ruled that the deny binds the local admin. Clause 3.9.2 authorizes issuing with the target user as the resource and applies denies attached to that user, its groups, or its org to every caller. Clause 3.10.1 repeats it for the local admin. Section 8 and ADR 0041 match, and ADR 0041 records the lockout this allows.
- F3: clause 3.9.2 refuses issuing for a disabled user or a user of a disabled org. Clause 3.9.4 states what the exchange is authenticated by and authorized as, and refuses a disabled or deleted user and a disabled org. Section 2.2 defines enabled and disabled.
- F4: new clause 3.9.10. The exchange takes `replaces` and revokes the named key in the same transaction, the CLI must send it when its context holds a key, and the clause states the guarantee and its limit (a lost key store). ADR 0041 records both.
- F5: clause 3.9.3 cuts the CLI's name to 63 characters and makes an exchange with a name outside section 7 fail with `InvalidArgument` without spending the code.
- F6: ADR 0041 Context and ruling, and ARFC 0007 section 8, now cite ARFC 0006 section 3.4, ARFC 0008 section 3.7, ARFC 0007 section 3.8, ARFC 0020 sections 2.1, 2.2, 2.3, and 3.7, and I-11. The cluster key premise is removed. The supersession condition names the facts whose change would make the local admin a new trusted party.

## Decisions

- A deny on `iam:IssueLoginCode` in the target user's org binds the local admin. Reason: clause 3.1 says any matching deny denies, and an org must be able to rely on its deny. Cost: a cluster whose only `cloud-admin` users are under such a deny cannot be recovered through the local admin.
- A temporary key cannot issue a login code. Reason: a credential of at most 12 hours should not mint one with no expiry, and it removes one lineage path.
- Revoking an access key also ends the session tokens and temporary keys that derive from it, within 5 seconds. Reason: ARFC 0020 section 3.4 bounds a stolen credential by its revocation, and a derived credential that outlived it would break that bound.
- One key per computer is kept by `replaces` on the exchange, not by replacing on a name match. Reason: hostnames collide. The guarantee holds only while the computer keeps its key store.
- Access key names are unique among unrevoked keys, and the limit of 100 counts unrevoked keys. Reason: a replaced key must free its name and its slot.
- A revocation through `replaces` has the full effects of clause 3.9.7, so it voids other unspent login codes the replaced key issued. Reason: one revocation behavior, not two.
- A deny attached after a login code was issued does not void that code. Reason: the code expires on its own (ARFC 0002), and voiding on policy change would need a policy evaluation at exchange for a caller that has no principal yet.
- Named here because nothing named them yet: error code `InvalidArgument`, request field `replaces`, the terms `derives from` and `descends`.

## Issues

The issues in `plan/reports/T-0023.architect.1.md` stand, except that the ARFC 0019 item about revoking the old key is now clause 3.9.10 and ARFC 0019 only needs to point to it. New in this round:

- `spec-issue`: no clause says who may disable or enable a user, or through which method. Section 2.2 now defines only the state and its effect on authentication (`spec/arfc-0007-tenancy-and-iam.md`).
- `spec-issue`: no ARFC says how a session token or a temporary key is obtained with an access key, though section 2.3 now defines what such a credential derives from. The token payload `{principal, org, issued, expires, key_id, scope}` has no field for it, so whether derivation is carried in the token or held by the control plane is open (`spec/arfc-0007-tenancy-and-iam.md`, section 2.3).
- `spec-issue`: the registry issues a bearer token for a request made with an access key (ARFC 0015). It is a derived credential that clause 3.9.7 does not name, and ARFC 0015 should say that it ends with its key (`spec/arfc-0015-container-registry.md`).
- `spec-issue`: ARFC 0002, with the login code from T-0022, must carry `replaces` and `name` in the exchange call, record the issuer of a code including the access key behind an issuing session token, and leave the code unspent in the two cases ARFC 0007 fixes: a name outside the limits and the key limit (`spec/arfc-0002-identity-and-join.md`).
- `follow-up`: conformance cases in `tests/conformance/authn` for: a key issued through a session token obtained with a key and removed by `descendants: true`; a chain with a revoked middle key; a temporary key refused as issuer; an org deny refusing a local admin; a disabled user and a disabled org at issue and at exchange; `replaces` naming a live key, another user's key, and a revoked key; a 64-character name.
- `follow-up`: glossary entries for `derives from` and `descends` next to `local admin` and `user access key` (`agent/domain/glossary.md`).
