Round 1 findings, checked against the round 2 text:

- R1-F1 (lineage): resolved. Section 2.3 lines 53 to 58, clauses 3.9.5 and 3.9.7 carry lineage through session tokens and temporary keys, and revocation ends derived credentials. A new gap in the temporary key rule is F2 below.
- R1-F2 (org deny and local admin): resolved. Clauses 3.9.2 and 3.10.1 apply denies on the target user, its groups, and its org to every caller. Section 8 and ADR 0041 match.
- R1-F3 (disabled user): resolved for issue and exchange (3.9.2, 3.9.4, section 2.2). What the exchange is authorized against is still open (F4 below).
- R1-F4 (one key per computer): resolved by clause 3.9.10. It interacts with the descendants remedy (F3 below).
- R1-F5 (name length): resolved. Clause 3.9.3 cuts to 63, section 7 cuts to 59 before a suffix, and with at most 100 unrevoked keys the suffix is at most 4 characters.
- R1-F6 (premise): resolved. ADR 0041 Context and ARFC 0007 section 8 cite ARFC 0006 clause 3.4, ARFC 0008 clause 3.7, ARFC 0007 clause 3.8, and ARFC 0020 clause 3.7, which say what they are cited for. The supersession condition names those facts.

Attacks tried. This is a spec task with no code, so there is nothing to fuzz or run in the simulator. Each attack is a scenario traced through the clauses:

1. Hostile tenant grows control plane state. A user with one access key mints session tokens, or loops issue, exchange, and revoke, at the ARFC 0008 clause 3.9 rate of 100 requests per second. Each step adds a derivation record or a revoked key that the lineage rule of clause 3.9.7 needs, and no clause bounds either. See F1.
2. Stolen key outlives the temporary key ban. Stolen key, then a temporary key, then a session token obtained with that temporary key, then a login code. Section 2.3 admits the middle step and clause 3.9.2 refuses only a request authenticated by a temporary key. Lineage still holds, so `descendants: true` still finds the key. See F2.
3. Stolen key, then the natural recovery: log in again on the same computer. `replaces` revokes the stolen key without `descendants`, and the thief's descendant keys stay live. Whether the one revocation of section 8 is still available on an already revoked key is not stated. See F3.
4. Abuse of `replaces` by a holder of a login code. It can revoke any one key of the code's user. The code already yields a key with that user's policies, which allows revoking that user's keys (3.9.6), and the revocation is audited (3.9.9). No finding.
5. Local admin from a compromised compute node or a hostile guest, repeated from round 1 on the new text. Clauses 3.10.2 to 3.10.4 are unchanged in substance. No finding.

The ruling against ARFC 0020 was rechecked on the new text and holds.
