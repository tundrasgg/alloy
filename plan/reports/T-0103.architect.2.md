## Summary

Round 2 resolves review F1 to F6. Heartbeats are now node channel status messages, as D-0047 directs and as `task/T-0102` specifies in ARFC 0002 section 3.13. They are no longer a TLS API call. The node, its anchor, and the leader each have their timing, failover, results, and audit stated.
`cargo xtask ci` passes on `task/T-0103` after merging main.

## Changes

- F1 (block): `spec/arfc-0006-control-plane.md` 3.13 now carries a heartbeat as `NodeStatus` (`NodeMessage` number 16) on a home session (ARFC 0004 3.1.2). The node's anchor handles it when it holds `control` and otherwise sends it as `forwarded`. The heartbeat is authenticated by the mesh key the AL session authenticated. A new section 4.3 gives the proto (`NodeStatus`, `NodeStatusReply`, `StatusResult`), numbers 18 to 31 stay reserved, and it says what makes a message `INVALID`. 3.13 also says what changes in rung 3: nothing but the path. The heartbeat now also carries the running release write of ARFC 0017 3.11, which until now had no carriage for a node without `control`. 3.14, 2.5, 2.8, 7, 8 and the depends list follow.
- F2 (block): 3.12.2 now splits errors in two. Any code but `Unavailable` means no effect, at once or after any restart. `Unavailable`, or no answer, means the outcome is unknown, and an entry already durable is applied at the next start. This matches the clause 5.2 `fail_after` hooks.
- F3 (fix): 3.13 Path covers errors as well as silence. A node that gets an error moves to its other home. An anchor that gets `UNAVAILABLE`, or no reply within 1.5 s, moves to the next control node, tries at most 2 per request, and answers within 3 s. Failed control nodes stay passed over, so the anchor rotates through them. A non-leader control node answers `UNAVAILABLE` after 1 s without the leader. The clause states a 30 s guarantee for 4 or fewer control nodes.
- F4 (fix): 3.14 says a heartbeat that is dropped, `INVALID`, `REFUSED`, or `UNAVAILABLE` before any commit writes no audit record. A heartbeat writes records only for what it commits. It also bounds a deleted node: one heartbeat per 60 s once refused, and none after its record expires (24 h at most), when renewal gets `node_unknown`. `spec/arfc-0018-observability-and-audit.md` 3.3.1 now says a heartbeat is not an API authentication attempt. 3.3.7 covers the release write a heartbeat carries, gives the source address and digest of a node message, and leaves the `unreachable_since` commits unaudited.
- F5 (fix): 3.15 defines "last heard" as the later of the latest accepted heartbeat and, while `unreachable_since` is unset, the moment the leader began serving. The clause says this is what "heard from" means in ARFC 0002 section 2. Nodes that were `active` stay `active` across a leader change, and nodes that were `unreachable` stay `unreachable`. 2.6 adds the committed `unreachable_since`, which the 3.16 controller sets and clears within 5 s. Section 8 names that commit as the one unaudited mutation.
- F6 (note): `spec/arfc-0019-cli-and-console.md` 3.1.15 states the reference case behind the 94 columns. It gives how much each wider value adds, and the zone name length above which the list passes 100 columns.

## Decisions

- N: Heartbeats carry the running release write (`NodeStatus.release`), because the node channel is the only way a node without `control` reaches the control plane.
- N: Committed `unreachable_since`, written only when a node changes state, keeps a long-dead node from showing `active` for 30 s after each leader change.
- R: Heartbeat time limit 4 s. The delay after a failure is 1 s, doubling up to 4 s. 60 s after `REFUSED`. 1.5 s per control node at the anchor, at most 2 control nodes per request.
- R: A heartbeat whose `release` equals the stored running release commits nothing and writes no record.
