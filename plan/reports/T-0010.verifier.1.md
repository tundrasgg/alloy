## Summary

`tests/conformance/sim/` (crate `conformance-sim`) holds 139 tests, each named after the clause of ARFC 0005 sections 3.2 and 3.3 it checks, written only against the section 2.7 interface and the `alloy-rt` seams. The simulator's source was not read.
The suite has its own BLAKE3, checked against the `blake3` 1.8.7 crate. It rebuilds the trace from observer records and checks that the trace hash, event count, `run-end`, and record order match the summary on every passing run.
Compiled against a throwaway stub of the section 2.7 interface (never committed), the suite builds and is Clippy-clean under the CI flags. All 139 tests fail on the stub's panic, and the 2 BLAKE3 unit tests pass.
The acceptance command fails on this branch: `alloy-sim` exists only on T-0009's branch, so the workspace cannot load. The question below asks how the lead wants acceptance run.
Not done: the scope item "runtime seam suites from T-0008 run against `mem`", because T-0008 is queued and `tests/conformance/rt/` does not exist.

## Decisions

- The suite is one workspace crate, `conformance-sim`, at `tests/conformance/sim/`, the suite path that ARFC 0005 section 5 names. Its member line is added under the shared-workspace-files rule, although T-0010's `touches` does not list `Cargo.toml` (see Issues).
- The trace hash and digests are checked with the suite's own BLAKE3, not `alloy-crypto`. That crate does not exist yet, and an independent hash is what makes 3.2.5 testable.
- Tests drive host runtimes from the control task (binding sockets and opening files through `World::runtime`). Clause 3.2.7 step 3 and the `timer-fire` rule for the control task (task 0) allow this, and it keeps each scenario short.
- The 3.2.10 echo scenario is written into the suite from the clause text, because an example binary of `alloy-sim` cannot be called from another crate.

## Issues

- `process-issue`: T-0010 is a verify task paired with T-0009, but no `interface` task froze `alloy-sim` (ARFC 0005 section 2.7) on main first, as `agent/protocol/tasks.md` requires. Without it the acceptance command cannot succeed on `task/T-0010`, and the workspace on this branch does not load at all until `alloy-sim` is present. `task/T-0010` must not reach main before T-0009.
- `process-issue`: T-0010 adds a crate but its `touches` omits `Cargo.toml` and `Cargo.lock` (D-0006). The member line was added anyway. `Cargo.lock` is unchanged, because cargo cannot resolve without `alloy-sim`, so at merge it needs step 2 of the shared workspace rule (`cargo update --workspace`).
- `process-issue`: the suite is about 6,000 lines against a 400-line target. Sections 3.2 and 3.3 hold about 140 musts. Later verify tasks of this size should be split per clause group.
- `spec-issue`: clause 3.2.3's wall time bound cannot be a conformance test. `agent/eng/testing.md` forbids reading the wall clock in tests, and `clippy.toml` bans `std::time::Instant::now`. It needs a CI step that times a release run of the echo example. The CI test step also runs in debug, so the suite's echo test (3 runs of 100 hosts for 1 h) runs slower than release, by an amount that is unknown.
- `spec-issue`: clause 3.2.6 ("writes exactly one line to standard error") and the stderr lines of section 6 cannot be observed in-process, and `std::process::Command` is banned. The suite tests `RunSummary::line()` only. Comparing stderr belongs in the CI step that clause 3.2.6 already describes.
- `spec-issue`: clause 3.2.7 step 2 and section 4.1 (trace file contents, cap) cannot be read back, because `std::fs` is banned by `clippy.toml` in every crate. The suite checks only that a trace file leaves the run unchanged and that an unwritable one gives `fail`. Clause 3.2.7's "runs at once on different threads" is untested for the same reason (`std::thread::spawn`). Only sequential runs are checked.
- `spec-issue`: a `Partition` naming a host that does not exist is `Unknown` by clause 3.3.1 ("every method taking a `HostId` ... returns `Unknown`") but `Invalid` or `State` by clause 3.3.3. `s3_3_3_partition_arguments_are_checked` accepts `Unknown` or `Invalid`.
- `spec-issue`: `Restart` with `rng_replay: Some(s)` above the last start may be `Invalid` (a range, clause 3.3.8) or `State` (it depends on the host's starts). The test accepts either. `Some(0)` is asserted `Invalid`.
- `spec-issue`: clause 3.3.2 does not say whether the packet being serialized still counts as waiting bytes in the bandwidth queue. `s3_3_2_a_full_link_queue_drops_with_reason_4` assumes it does: 3 packets of 1,000 bytes into a 1,500-byte queue give 2 drops.
- `spec-issue`: clause 3.3.7 does not say whether a write that does not grow the total fails when the total is already above `capacity`. That case is not tested.
- `follow-up`: the scope item "the runtime seam suites from T-0008 run against the `mem` implementations" is not done. T-0008 is queued and `tests/conformance/rt/` does not exist. It needs a task once both T-0008 and T-0009 are merged.
- `follow-up`: `s3_2_7_poll_bound_ends_the_run_with_liveness` polls 100,000,000 times by design. Its time in a debug CI run is unknown.

## Question

Acceptance (`cargo test -p conformance-sim --no-run`) needs `alloy-sim`, which only T-0009 provides. How should T-0010's acceptance be run?

1. Recommended: merge `task/T-0010` into `task/T-0009` (step 3 of the build lifecycle) and run the command there as T-0010's acceptance. No more verifier work is needed unless tests fail for a spec reason.
2. Cut an `interface` task that freezes ARFC 0005 section 2.7 as `crates/alloy-sim` on main, then dispatch T-0010 round 2 to rerun acceptance on its own branch.
