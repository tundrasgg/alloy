## Summary

Round 2 resolves reviewer finding F1. The hook check (clause 3.2.9) no longer uses one run-wide flag plus a run-thread test. It now asks whether the calling thread is one of the threads running an observer of that world.
Both cases from the review are covered by new tests that make the call off the run's thread. Both tests fail on the round 1 source and pass on the fix.
`task/T-0075` has main merged in. `cargo test -p alloy-sim`, `cargo xtask ci` and `cargo xtask check-repo --base main` pass. T-0010 has not merged (`tests/` does not exist), so its suite was not run.

## Changes

- F1 (block), resolved:
  - `crates/alloy-sim/src/trace.rs`: adds `Hook`, the list of threads running an observer of one world, and a guard that adds the calling thread while observers run in `emit` and removes it afterwards. `write`, `emit` and `finish` take `&Hook` in place of `&AtomicBool`.
  - `crates/alloy-sim/src/world.rs`: `Shared::in_hook` is now `Hook::is_current`, true only on a thread that is running an observer of this world. The `run_thread` field is removed. The lock-order note is updated, because a hook call now takes the hook's own short lock and nothing else.
- `crates/alloy-sim/src/world.rs` (unit test): while the run thread is inside the hook, a draw from another thread advances the stream normally.
- `crates/alloy-sim/tests/runs.rs`: adds two tests, `world_calls_from_an_observer_off_the_run_thread_are_busy` (review attack 3) and `an_observer_on_another_thread_leaves_calls_on_the_run_thread_alone` (review attack 2). Each runs under a 10 s deadline, so a deadlock fails the test instead of hanging it. The file also uses `thread::scope` unqualified now.

## Decisions

- The hook holds a list of thread ids, not a single slot. Observers run under the trace lock, so today the list holds at most one thread. A later middlebox slice can run its hooks on other threads without changing this check. Routine.
- If an observer waits on another thread that makes a world call needing the trace lock (for example `note`), that thread blocks until the observer returns. That call is not made from inside `Observer::record`, so clause 3.2.9 does not apply to it. It waits as it would on any lock its own observer holds. Routine.
