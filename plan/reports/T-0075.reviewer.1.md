For the attacks I wrote a temporary integration test, `crates/alloy-sim/tests/review_attack.rs`, on the detached task tip. I ran it and then deleted it. It was not committed.

Attack 1: determinism, the cap, and fault injection over 1,000 seeds. For each seed 0..1000 the test sets a budget of `1 + seed % 200` ns and a trace cap of `16 + (seed * 37) % 600` bytes, with a trace file. On one seed in three, an observer panics at record `1 + seed % 40`. On one seed in seven, the control task returns `Err`. The control task polls 1 to 6 branches, each picked from the scenario's stream, and the branches interleave random 0 to 3 ns sleeps and notes. Each seed runs twice. The test asserts that both `RunSummary` values, both lines, and both observer record lists are equal. It rebuilds the trace bytes from the header plus the records the observer saw, then checks four things: BLAKE3 of those bytes equals `trace_hash`; the file is a prefix of the bytes that ends on a record boundary and stays within the cap; the next record would have passed the cap; and times never decrease, the last record is `run-end`, and `virtual_time` is at or below the budget.

Attack 3: a world call from an observer that runs off the run's thread. The observer calls `world.note("inner")` from `record` on every `note` record. The control task calls `note("outer")` from a spawned thread and joins it. The run itself executes on a helper thread, and the test waits 10 s for it to end.

```

test result: FAILED. 1 passed; 2 failed; 0 ignored; 0 measured; 0 filtered out; finished in 16.94s
```

Cause, by reading. `Shared::in_hook` (`crates/alloy-sim/src/world.rs:124-126`) is `hook.load() && thread::current().id() == self.run_thread`. `Trace::emit` (`crates/alloy-sim/src/trace.rs:311` and `:324`) sets and clears the one `hook` flag of the run on whichever thread writes the record. Two failures follow:

- In attack 3 the observer runs on the spawned thread, so `in_hook` is false there. `note` then passes `check` and calls `lock(&self.trace)` again on the thread that already holds it, at `world.rs:143`. That is a re-entrant lock of a `std::sync::Mutex`, which deadlocks or panics.
- In attack 2 the flag is set by the other thread, and `in_hook` is true on the run's thread although no observer runs there. The world call takes the clause 3.2.9 path.

## Issues

- `spec-issue`: `spec/arfc-0005-simulator-and-natlab.md` clause 3.2.7 step 4 is silent on one case: a `World::sleep_until(t)` with `t` above 2^63 - 1 ns, which can never complete. Is it an event pending after the budget, so that world time becomes `budget`, or is it no event, so that world time stays where it is? `crates/alloy-sim/src/world.rs:214-222` treats it as no event. So `sleep_until(2^63 - 1 ns)` ends at `budget`, while `sleep(Duration::MAX)` ends at the current time.
- `follow-up`: I confirm the developer's `follow-up` items. The task owner field (clause 3.2.7 step 3) and the record `digest` (clause 3.2.5) are absent, and later slices need both.
