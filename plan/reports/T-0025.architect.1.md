## Decisions

- A task whose scope edits an existing row of a shared index (for example an ARFC status change in `spec/README.md`) holds that file exclusively. Reason: only pure appends merge safely by keeping both sides; edits to the same row cannot be resolved mechanically.
- A conflict in a shared index that is not two sets of added rows is not resolved by the lead; the task's role is dispatched again with the next round. Reason: it means a task broke the append-only rule, and the lead does not produce content.
- Row placement is fixed as "the table where its id belongs, in ascending id order" so that the lead's conflict resolution is deterministic.
