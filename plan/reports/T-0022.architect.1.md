Size checks for the formats. Each string is `alyt_` or `alyc_` plus ceil(8n/5) base32 characters. A token is 62 fixed bytes plus 33 per anchor plus 9 or 21 per address. ## Decisions

- Private advertise addresses also include 100.64.0.0/10 (RFC 6598), beyond the brief's list. Reason: such addresses are not reachable from outside either, and principle 4 asks the CLI to say so.
- `init` on a machine without `/dev/kvm` leaves `compute` out of the first node's roles, although the brief gives it all four. `compute` from `--roles` or a token preset on such a machine is refused. Reason: ARFC 0011 section 3.6 allows `compute` there only after a cloud admin dedicates the node to one org.
- Clients generate join token secrets, login code secrets, and the access key secret sent in `ExchangeLoginCode`. The API receives these secrets only in requests and returns none of them. `--output json` or `yaml` on a command that prints a token or code is a usage error. Reason: I-22 forbids secrets in API responses, and PB-0001 forbids them in JSON output.
- The join exchange has two messages, version and then the request. The anchor's reply to the first message carries the cluster key and the anchor's own node record. Reason: the version must be checked before the secret is sent, and the cluster key must be checked against the token before the secret is sent.
- Accepted joiner releases are L and L+1, where L is the lowest minor release running in the cluster. Reason: this never makes three releases present (ARFC 0017 section 7), and it matches the brief's example of 0.1 and 0.2.
- Each token address entry carries the UDP mesh port and the `stream` TCP port. Anchors are listed by name and dropped once the string would exceed 512 characters. Reason: the old layout had no bound on addresses and could not meet the existing 512 character limit.
- Expired, revoked, and used up tokens and login codes are kept for 7 days after expiry, so that the reason for a refusal can still be given. All limits are stated in section 7 (I-21).
- A wrong secret for a known `code_id` spends the login code. Reason: this matches the token rule, and with checksums a wrong secret is never a typo.
- `node leave` refuses while the node hosts guests or has a disk in a pool. It fails with `Unavailable` when the control plane does not answer, unless `--force` is given. Reason: no data loss without an explicit choice.
- Machine checks: the host check runs first, a free space `warn` below 10 GiB and `fail` below 1 GiB, and all checks print before the command exits. `init` undoes every write when a step after the checks fails, and must take under 30 seconds.
- Section references use "section N" rather than the section sign, which matches the other ARFCs.

## Issues

- `follow-up`: T-0023 must let ARFC 0007 accept an access key created by `ExchangeLoginCode` with a client-generated secret (`spec/arfc-0002-identity-and-join.md` section 3.7). It must also say whether `sudo alloy login --issue-code` works with no context, which ARFC 0019 3.1.11 now answers with exit 4 (`spec/arfc-0019-cli-and-console.md`).
- `follow-up`: T-0024 must make ARFC 0008 section 3.8 present a chain that ends in the API CA certificate to clients that connect by address, even on a cluster with an ACME certificate, or login codes fail there. The default mesh port and the `stream` port that token address entries carry are T-0024's to fix (`spec/arfc-0008-native-api.md`).
- `spec-issue`: the API CA key is Ed25519 (`spec/arfc-0002-identity-and-join.md` section 2) and the console is served at the API endpoint (`spec/arfc-0019-cli-and-console.md` section 2). Unknown: whether current Chromium, Firefox, and Safari accept Ed25519 TLS certificates. This needs a research task.
- `spec-issue`: ARFC 0006 states no heartbeat interval, and ARFC 0002 section 2 now marks a node `unreachable` after 30 seconds without contact, so heartbeats must be more frequent (`spec/arfc-0006-control-plane.md`).
- `spec-issue`: ARFC 0017 does not define the next minor release across a major boundary (0.x to 1.0). The join version window in ARFC 0002 section 3.3 inherits this gap (`spec/arfc-0017-upgrades-and-versioning.md`).
- `follow-up`: a token carries no anchor names, so PB-0001's unreachable message ("Cannot reach anchor node1 at ...") can name only the address. After contact, the anchor's node record gives the name. PB-0001 also gives the generic text for a revoked token, while ARFC 0002 now returns `token_revoked` once the secret matches. Product chooses the wording (`product/briefs/PB-0001.md`).
- `follow-up`: `alloy node leave` refuses on the last control node, so Alloy has no command that removes a one-node cluster from its machine. This needs a product decision and then a spec change (`spec/arfc-0002-identity-and-join.md` section 3.9).
- `follow-up`: the proto definitions for `CreateLoginCode`, `ExchangeLoginCode`, `ApproveNode`, `RejectNode`, the `join_approval` setting, standing warnings in status, and the `Unauthenticated` error code belong in the first `alloy-proto` task (`spec/arfc-0008-native-api.md` section 3.6).
