## Summary

ARFC 0005 clause 3.1.14 now says the timer of `timeout` starts at the call, not at the first poll, with the reason, and `sleep` fixes its deadline the same way. This is the reading `alloy-rt` implements.
Clause 3.1.10 now says `RtPath::join` adds exactly one component, rejects a component that holds `/` with `InvalidPath`, and is the inverse of `parent` and `file_name`. This is also the `alloy-rt` reading.
Sections 2.1, 2.3, 2.4 and clause 3.1.13 give the exact `Debug` text of `Datagram`, `RecvSlot` and `IoBuf`, in the way ARFC 0001 clause 3.18 does.
Clause 3.1.9.1 gains pending ends, which settle T-0050 review 2 F1 and F2. Clauses 3.2.7 and 3.2.8 and section 6 settle F3.

## Changes

- `spec/arfc-0005-simulator-and-natlab.md` section 2.1: the `Debug` output of `Datagram`, `RecvSlot` and `IoBuf` with `{:?}` is exactly the text of each impl's doc comment, and `{:#?}` gives the same fields in Rust's standard multi-line layout.
- Same file, sections 2.3 and 2.4: doc-commented `Debug` impls. `Datagram { len: <payload.len()> }`, `RecvSlot { capacity: <buf.len()>, len: <len> }`, `IoBuf { len: <len()> }`. Doc comments on `RtPath::join`, `Runtime::sleep` and `Runtime::timeout`.
- Same file, clause 3.1.10: a `join` rule of its own, replacing "`join` applies the same rules".
- Same file, clause 3.1.13: points to the exact `IoBuf` text.
- Same file, clause 3.1.14: `sleep` and `timeout` read `now()` once, at the call. `timeout` polls `f` first, then the timer. It shows the outcome of a late first poll and of `Duration::ZERO`, and gives the reason for starting at the call.
- Same file, clause 3.1.9.1: a new "Pending ends" rule. "Abandoned setup", "Arrival" and "Reset" are changed to match it (F1, F2).
- Same file, clause 3.2.7 step 4, clause 3.2.8, section 6: what happens when an observer panics on the `run-end` record (F3).
- `plan/reports/T-0067.architect.1.md`: this report.

Rulings, with which side was right:

- Timer start (`spec-issue` in `plan/reports/T-0007.developer.1.md`). The spec was silent. The `alloy-rt` reading, a deadline fixed at the call, is confirmed. Reasons: the caller measures a limit from when it asks, so a future that is stored before it is awaited, or polled late by a busy scheduler, gets no extra time. `sleep` is already defined from `now()` at the call. Nothing in the spec argues against it.
- `RtPath::join` (same `spec-issue`). The spec was silent. The `alloy-rt` reading is confirmed: one component per call, and `/` gives `InvalidPath`. Reasons: `join` stays the exact inverse of `parent` and `file_name`, and `new` already builds a path of several components.
- `Debug` text (`spec-issue` in `plan/reports/T-0069.developer.1.md`). The spec was underspecified. The T-0069 reading is confirmed: lengths only, with no addresses and no `truncated`. That is the strict reading of "lengths only" in section 2.1. Main still has the T-0007 text, which also prints the addresses (`crates/alloy-rt/src/net.rs:187-233`), and T-0069 (in review) changes it to the text now specified. `IoBuf` on main already prints exactly `IoBuf { len: N }` (`crates/alloy-rt/src/disk.rs:450-455`).
- F1 (T-0050 review 2). The reviewer was right. The requesting host now has a pending end from `t + d` to `t + 2d`. A segment that arrives there is held. It arrives at the new live end when `connect` completes, so latency alone never loses it. A held byte is delivered less than 15 s after it was due, because the accepting end exists only from `t + d` and `d` is below 15 s, so the 60 s rule never fires on it. An arrival at the instant `t + 2d` has the same outcome in either seed order. A held reset makes the end reset at completion, and `connect` still returns the `Stream`. This restores ADR 0054's consequence "Latency alone never resets a stream", so no ADR is needed.
- F2 (T-0050 review 2). The reviewer was right. The pending end lasts until `t + 2d` even after the `connect` future is dropped. The abandoned setup reset discards what it holds and is the one reset of that direction. An arrival at `t + 2d` is either held and discarded with the rest, or finds no end and draws no second reset under the existing "unless a reset was already sent" rule. Both seed orders give one reset at `t + 2d`. The same rule also removes a second double-reset case: a segment that arrived after the future was dropped but before `t + 2d` used to draw a reset at once, and then the abandoned setup reset followed it.
- F3 (T-0050 review 2). The reviewer was right. An observer that panics on `run-end` is removed and no record follows. The result is fixed when `run-end` is written, so the summary always agrees with the result byte of the `run-end` record, which is part of the trace hash. Such a panic does not change the result or `failure`. Section 6 states the exception.
