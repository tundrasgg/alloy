## Summary

The API CA key is now ECDSA P-256 (option A of R-0006), and so is every API server certificate key. API CA signatures are `ecdsa-with-SHA256`, and every P-256 signature takes an RFC 6979 nonce. `api_ca_fp` is now a hash of the CA's 91-byte DER SubjectPublicKeyInfo, so the login code layout is unchanged. ARFC 0008 section 3.8 fixes the key, the `CertificateVerify` scheme, and the presented chain. `agent/eng/crypto.md` scopes P-256 to these two uses. ADR 0048 records the decision and is indexed.

## Changes

- `spec/arfc-0002-identity-and-join.md`: the section 2 key table names the API CA key as ECDSA P-256. A new rule list fixes the SubjectPublicKeyInfo encoding, `ecdsa-with-SHA256` signatures and RFC 6979 nonces. Section 3.7 redefines `api_ca_fp` over the DER SubjectPublicKeyInfo and the client pin check to match. ADR 0048 is added to Decisions.
- `spec/arfc-0008-native-api.md`: section 3.8 makes the API server certificate key P-256 from either source, sets `CertificateVerify` to `ecdsa_secp256r1_sha256`, and says the chain from the API CA is the leaf and then the CA certificate, all P-256. ADR 0048 is added to Decisions.
- `agent/eng/crypto.md`: adds an ECDSA P-256 primitives row scoped to the API CA key and API server certificate keys, plus a paragraph saying every other signing key stays Ed25519.
- `adr/0048-the-api-ca-and-api-server-certificates-use-ecdsa-p-256.md`: new ADR.
- `adr/README.md`: indexes ADR 0048 under Api.

## Decisions

- N: `api_ca_fp` hashes the DER SubjectPublicKeyInfo, not the raw point. The SubjectPublicKeyInfo is in every certificate, binds the algorithm and curve so no other key type can match, and keeps the field at 16 bytes.
- N: ECDSA nonces are deterministic by RFC 6979 section 3.2 with SHA-256. This meets `agent/eng/crypto.md` rule 5 and keeps signing off any random source outside `alloy-rt` (rule 4, ADR 0008). RFC 6979 also has P-256 test vectors for rule 9.
- N: the key of an ACME certificate is also P-256, so API endpoints use one key type from either source. Only the leaf key is Alloy's choice: the issuer's signatures are not specified.
- N: the crate cell of the new crypto row names the `rustls` provider still to be chosen, not a new crate. Choosing a crate needs research (`agent/eng/deps.md`), and the provider choice is already pending from R-0004.

## Issues

- `follow-up`: the `rustls` provider ADR (pending from `research/R-0004.md`) must confirm the provider signs ECDSA P-256 with RFC 6979 nonces, or name what supplies it. It must also name the crate that builds X.509 certificates for the API CA (`agent/eng/crypto.md`).
- `spec-issue`: `spec/arfc-0002-identity-and-join.md` states no lifetime or rotation procedure for the API CA key, and no validity for the certificates it issues. `agent/eng/crypto.md` rule 7 requires both before the key is used.
- `spec-issue`: the ingress ACME certificates in `spec/arfc-0010-public-addressing.md` clause 3.6 have no key type. The new crypto row covers API endpoints only, so ingress needs its own ruling.
- `follow-up`: the Safari handshake test and the real-browser checks listed as unknown in `research/R-0006.md` are still needed before ARFC 0002 section 2 freezes.
