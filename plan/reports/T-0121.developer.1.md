## Summary

`DataDir` creates the data directory `PrivateRoot`, adopts a Linux one at `0700`, and creates every file `Private`. `native` creates `log.redb` and `state.redb` through `disk-io` with `Private` before `redb` opens them, as clause 3.1.15 says. This closes T-0106 F3 and T-0107 F4. T-0114 F1 and F2 and T-0107 re-review F1 are folded in.
T-0106 F4 is not resolved: `disk-io` has no write-through rename, and `alloy-rt` is outside `touches`.
On a Windows host that is not elevated, `native` cannot build: the process may not name `Administrators` as owner, so `create_file` returns `PermissionDenied`, which clause 3.1.15 makes a build failure. That makes the `native` conformance suites fail there, so `cargo xtask ci` fails on this host. The question below asks how to settle this.

## Decisions

- N: `native` on a runtime without native paths (`mem`) now fails to build with `Failed`, because `rt_path` returns `Unsupported`. ADR 0064 already limits `native` to `os` runtimes.
- R: a `dir` outside the `disk-io` root is `Config(Invalid dir)`.
- R: the heartbeat race of F2 cannot happen on the simulator, which is single-threaded. The re-read guards against it on `os`, where it is not exercised by a test.

## Issues

- spec-issue: `spec/arfc-0002-identity-and-join.md` 3.14 requires `MoveFileExW` with `MOVEFILE_WRITE_THROUGH`, but ARFC 0005 3.1.10 and 3.1.15 give `disk-io` no write-through rename. `os` `rename` is `std::fs::rename` (`crates/alloy-rt/src/os/disk.rs:220`). T-0106 F4 needs a spec task and then an `alloy-rt` build.
- test-issue: `tests/conformance/log-store` and `tests/conformance/state-store`: under clause 3.1.15 the `native` harness cannot build on an unelevated Windows host. See the question.
- follow-up: `crates/alloy-id/src/store.rs`: nothing creates the `disks` directory yet. Whoever creates it must use `create_dir_protected(Private)`.

## Question

How should the `native` stores behave for a Windows process that may not name `Administrators` as owner?

1. (Recommended) Keep clause 3.1.15 as written: `native` fails with `Failed`, as `alloyd` always runs elevated. The verifier makes the Windows `native` conformance harnesses expect that failure when not elevated, as `crates/alloy-state/tests/native.rs` now does. Linux CI is unchanged.
2. Spec change to ARFC 0005 3.1.15: on `PermissionDenied`, `native` creates the file with `Protection::Default`. That gives the same inherited list, which is all clause 5.2 asks for on Windows, but the owner is the creating user. `alloyd` is unaffected, since it cannot reach the data directory unelevated.
3. Accept that `cargo xtask ci` passes on Windows only when elevated, and change nothing.
