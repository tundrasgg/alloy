Expression check for `.github/workflows/ci.yml:18`,
`github.event_name == 'pull_request' && format('ci-pr-{0}', ...) || format('ci-push-{0}', github.sha)`:

- Precedence: the Actions expression parser binds `&&` tighter than `||`. `logicalOr` calls `logicalAnd`, with the comment "&& is higher precedence than ||"
  (https://raw.githubusercontent.com/actions/languageservices/main/expressions/src/parser.ts, `logicalOr`, about line 85).
  The expression reads as `(is_pr && pr_group) || push_group`.
- `format(...)` always returns a non-empty string, which is truthy. A pull request run therefore never falls through to the push group.
- The triggers (lines 6-9) are `push` to `main` and `pull_request` only. Every push run is therefore a run on `main`, and the comment at lines 14-16 is accurate.

Attacks tried, no finding:

- A main run and a PR run in one group: the `ci-pr-` and `ci-push-` prefixes differ, so the two can never collide.
- Two main runs in one group: this needs the same SHA pushed to `main` twice. That takes a history rewrite of main, which `agent/eng/git.md` ("Never") forbids. A re-run of a finished run reuses its own group, which is empty by then.
- A main run cancelled while in progress: `cancel-in-progress` is false for pushes, and the group of a push run holds only that run.
- Concurrent cache saves from parallel main runs: `save-if` is unchanged. Both runs saving under one key is a cache-reservation warning, not a job failure. This behavior existed before the change and cannot change the verdict.
- Invariants (`agent/domain/invariants.md`): none can be reached by a CI concurrency setting.
- Banned list (`agent/core/4-evidence.md`): no Rust changed, so nothing applies.

Not observed on GitHub: no run was triggered, as was also the case for the developer. The behavior is established from the docs and the parser source cited above.
