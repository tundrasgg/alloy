It covers the namespace, files, and block devices (clauses 3.1.10, 3.1.11, 3.1.13), durability at a crash under `Lost`, `Seeded`, and `Torn` (3.1.12, 3.3.4), and capacity and read faults (3.3.7). ## Decisions

- Class N: every `mem` disk call completes at the call, at the current world instant, and writes its `disk-op` records then. The operations of a dropped `read_at` or `write_at` future have therefore always run, and `sync` has nothing pending to wait for.
- Class N: durability is per file. A completed `sync` of either kind, on any handle, makes every earlier data change and length change of the file durable. This follows clause 3.3.4 ("on any handle of it") rather than the "on the handle" wording of clause 3.1.11. Name changes become durable through `sync_dir` of their parent, or of both parents for a rename.
- Class N: the post-crash state is a replay of the log on the durable base, in completion order. Durable changes are always kept. `Lost` drops every unsynced change. `Seeded` makes one draw per unsynced change (keep on 1 of `below(2)`). `Torn` makes one draw per `block_size` unit of each unsynced write, aligned on the file. A change whose target the replay lacks is dropped: a write or truncate of a missing inode, a create in a missing directory, a rename whose source entry is not the same inode, or a remove of a non-empty directory. A rename is applied whole or not at all.
- Class N: draw streams. Read faults use `Stream(seed, "disk-read", [host])` and draw only when a rate is above 0. A crash uses `Stream(seed, "disk-crash", [host, start])`, one per start, since a start crashes at most once.
- Class N: readings where clause 3.1.10 is silent:
  - `remove` or `rename` of a block device, and `remove` of the root, return `PermissionDenied`. A device path is then fixed for the life of the host, which `DiskTarget::Device` relies on.
  - `rename` of the root, or of a directory to a place below itself, returns `InvalidInput`.
  - A directory renamed onto a file returns `NotDirectory`.
  - A parent component that is a file returns `NotDirectory`.
  - Directory `metadata` reports length 0.
- Class N: readings in clause 3.1.11:
  - A write whose end is past 2^63 - 1 fails alone with `InvalidInput`. That case is not in the whole-batch list.
  - An empty write does not extend a file.
  - Whole-batch checks run in this order: `BatchTooLarge`, `Unaligned`, `ReadOnly`, overlap, past the device's end.
  - `exclusive` is `Busy` only while another exclusive handle holds the device. Plain opens never block.
- Class N: capacity counts each regular file of the current tree, rounded up to `block_size`, including files whose name was removed while a handle holds them, until the last handle closes. A write or truncate fails with `NoSpace` only when it grows the count above the capacity, so an overwrite within the allocation still succeeds on a full disk. A crash replay may leave the count above the capacity, and nothing is refused for that.
- Class N: `Fault::Disk` and `Fault::Capacity` apply to a crashed host too, since both persist across crashes. Their `fault` record text is the fault's `Debug` form.
- Class N: `Ppm` lives in `fault.rs`, with the interface of section 2.7, for T-0077's `LinkConfig` to reuse.
- Routine: file and device bytes are stored in 4,096-byte chunks, created on first write. A 2^40-byte device, or a large sparse file, costs memory only for the chunks written.

## Issues

- `spec-issue`: clause 3.1.11 makes `sync` cover writes "on the handle", while clause 3.3.4 counts a sync "on any handle of it". `mem` follows 3.3.4. `spec/arfc-0005-simulator-and-natlab.md` clauses 3.1.11 and 3.3.4.
- `spec-issue`: the per-directory durable state of clause 3.3.4 can conflict with itself when name changes become durable out of completion order. Example: `rename /a/x /b/x`, then create `/a/x`, then `sync_dir /a` only. The create is durable, and the rename that freed its name is not. `mem` resolves this by replaying in completion order and dropping what no longer applies. The architect may want to state that rule. `spec/arfc-0005-simulator-and-natlab.md` clause 3.3.4.
- `spec-issue`: clause 3.1.10 does not cover these cases: `remove` or `rename` of the root or of a block device, a directory renamed below itself or onto a file, a non-directory parent component, and directory `metadata` length. `mem`'s readings are in Decisions. `spec/arfc-0005-simulator-and-natlab.md` clause 3.1.10.
- `spec-issue`: clause 3.3.7 does not say whether `Disk` and `Capacity` apply to a crashed host. `mem` allows both. `spec/arfc-0005-simulator-and-natlab.md` clause 3.3.7.
- `process-issue`: the task is at 2,393 changed lines against a 2,000 target. `disk.rs` is 1,262 lines without its tests. The model has many parts that could not be dropped: inode tree, durable base with log and replay, capacity, read faults, devices, handles, batch rules, and records. The tests add 520 more lines. An estimate for `alloy-sim` disk or network work should allow about 2,500 lines. `plan/reports/T-0076.developer.1.md`.
- `follow-up`: `tests/rt_mem.rs` now takes about 45 to 55 s in a debug build. Most of that time is the 1,048,577-entry `list` check of clause 3.1.10, which also holds roughly that many log entries in memory, since nothing syncs the directory. If CI time or memory becomes a concern, the `mem` harness could run that one check in a release-profile job. `crates/alloy-sim/tests/rt_mem.rs`.
