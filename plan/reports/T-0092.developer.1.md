## Summary

`packaging/` holds `install.sh`, `install.ps1`, `uninstall.sh`, `uninstall.ps1`, the unit `alloyd.service`, and the tools that set the version, gather license texts, assemble archives in the layout of clause 3.13, write the digests and `SHA256SUMS`, and check everything (`check.sh`, `check.ps1`).
`.github/workflows/release.yml` builds `alloy` and `alloyd` for linux-x86_64 (static musl) and windows-x86_64 on a `v0.0.PATCH-preview.N` tag, adds the pinned and Authenticode-checked Wintun DLL, stamps the scripts, attests every asset, and publishes a pre-release.
F3 is met by creating the manifest's directory and the manifest in one rename, with a marker that installs and uninstalls recognize. F4 is met by a quoted service image path that the install verifies.
All three acceptance commands pass. A dry run (84 checks) passes on Debian 13 and Ubuntu 22.04 containers. Windows ran only non-elevated here: see Issues.
The workflow cannot succeed until T-0091 creates the `alloy` and `alloyd` crates.

How the review findings are met:

- F3. A first install never creates the manifest's directory on its own. It builds the outermost missing directory of `/usr/local/share/alloy` (on Windows `%ProgramFiles%\Alloy`) under its temporary name `<dir>.alloy-new`, writes the pending manifest inside, and renames it into place in one step (`alloy_write_manifest`, `Write-AlloyPendingManifest`). Before that rename the only path written outside the temporary directory is that `.alloy-new` name, a temporary name of a manifest path. The uninstall removes the manifest's directory the same way, through `<dir>.alloy-old`. A directory under either name that holds only the directories down to the manifest and at most the manifest is a marker (`alloy_is_marker`, `Test-AlloyMarker`): step 4 does not count it as a conflict, step 6 removes it, and an uninstall with no manifest and no data directory removes it and exits 0 instead of saying Alloy is not installed. The dry run checks all three cases. Spec text needed: `spec-issue` below.
- F4. `install.ps1` creates the service `alloyd` with the image path in double quotes, `"C:\Program Files\Alloy\alloyd.exe"`, runs `sc.exe config` when an existing service differs, and exits 1 unless `Win32_Service.PathName` then equals the quoted path (`Set-AlloyService`). The host snapshot check is T-0093's.

## Decisions

- Class N: the release workflow refuses any tag that is not `v0.0.PATCH-preview.N`, since a release that is not a preview needs the release key of clause 3.14, which is out of scope.
- Class N: archives hold the executables that exist: `alloy` and `alloyd` (Linux), `alloy.exe`, `alloyd.exe`, `wintun.dll` (Windows). The list of packages is in the workflow's build steps.
- Class N: the Windows build links the C runtime statically (`-C target-feature=+crt-static`), so no Visual C++ redistributable is needed.
- Class N: the uninstall logic lives once per language, in a block shared byte for byte between each install script and its uninstall script; `check.sh` fails when they differ and `sync-shared.sh` copies it.
- Class N: the archive's `licenses/` holds Alloy's two license texts, the license files of every crate linked into the binaries (proc-macros and build dependencies left out), the Rust standard library notices, `wintun.txt` on Windows, and `README.txt`, the listing ADR 0062 asks for. A crate with no license file stops the release.
- Class N: the unit uses `Restart=on-failure` (any non-zero exit or signal counts as exiting abnormally), `KillMode=process` (stopping it stops `alloyd` alone), `Type=exec` (systemd 240 or later), `TimeoutStopSec=30`.
- Class N: the uninstall needs real root (exit 4 otherwise) in both forms; only the install goes through `sudo`, as clause 3.15 step 2 says.
- Class N: the install exits 1 when the manifest is not a regular file owned by root that only root can write, or its directory can be written by others, since an uninstall run as root deletes what the manifest lists.
- Class R: `--version` naming the script's own release runs this script instead of downloading itself again.
- Class R: with no manifest, a reserved object that a line of an Alloy data directory's host file matches is Alloy's own (clause 3.17.2) and not a conflict.
- Class R: on Windows, a machine `PATH` that already holds `%ProgramFiles%\Alloy` is left alone and the entry is not listed in the manifest ("appended ... when absent").
- Class R: `--purge` confirmation asks the user to type the data directory's path, the name of what is deleted.
- Class R: a host file `run` line counts only under `/run/alloy`, and `link`, `netns`, `nft`, and `adapter` lines only with reserved names, so a damaged host file cannot make an uninstall remove another product's object.

## Issues

- `spec-issue`: F3 needs text in `spec/arfc-0017-upgrades-and-versioning.md` clause 3.15 steps 4 and 6 and clause 3.16 step 2: the manifest's directory and the manifest are created together by renaming `<dir>.alloy-new` into place, removed through `<dir>.alloy-old`, and such a directory holding only the directories down to the manifest and at most the manifest is a marker that step 4 does not count as a conflict and an uninstall removes (with no manifest and no data directory, it removes the marker and exits 0).
- `spec-issue`: clause 3.15 step 4 cannot check the paths that only the archive names (license files, any further executable) before step 5 downloads it. The scripts check them after extraction and before step 6, with exit 5; the clause should say so.
- `spec-issue`: clause 3.13 says the Linux archives hold every executable of ARFC 0000 section 2.3 and the Windows archives `alloy-net.exe`; none of those but `alloyd` exists yet. A preview should be allowed to hold only the executables that exist, or the clause waits for them.
- `spec-issue`: clause 3.15 step 4 makes any non-Alloy directory at the data directory's path a conflict, including an empty root-owned directory that ARFC 0002 section 3.12 lets `init` and `join` adopt (a mount point).
- `spec-issue`: review finding F2 of T-0088 is still open: no command reports a non-default data directory, so the scripts use the default (`/var/lib/alloyd`, `%ProgramData%\Alloy`) for the preview rule, resuming, host objects, and `--purge`.
- `follow-up`: the release workflow builds `-p alloy -p alloyd`, which T-0091 creates; the first tag fails at `packaging/set-version.sh` until it merges. T-0091's `alloy version` and `alloyd version` must print exactly the crate version; the workflow checks it.
- `follow-up`: the elevated Windows install and uninstall were not run on this host, since they create the service `alloyd`, change the machine `PATH`, and write under `%ProgramFiles%`; only the non-elevated paths and the read-only steps ran. The service creation, the quoted image path (F4), the PATH entry, and the in-use rename are first exercised by the rung 1 check (T-0093) on the lead's Windows machine.
- `follow-up`: the Linux dry run used a stub `systemctl` (containers run no systemd); enabling, starting, and restarting `alloyd.service` on a real systemd host are first exercised by rung 1.
- `follow-up`: removing a Wintun adapter in uninstall step 6 uses `pnputil /remove-device`, which exists from Windows 10 2004 (build 19041); on builds 17763 to 19040 that step exits 1. Nothing creates an adapter yet (no ARFC defines how `alloy-net` opens it).

- `follow-up`: linux-aarch64 (an `ubuntu-24.04-arm` runner), windows-aarch64 (Wintun `arm64`), and macOS archives are not built; the matrices take another entry each.
- `process-issue`: `packaging/check.sh` on Git Bash for Windows spends minutes on its 2,386 `sh` prefix runs and hit "fork: retry: Resource temporarily unavailable" once under load; it is meant for Linux, where CI runs it in seconds.
- `process-issue`: the task is about 5,700 added lines, over the 2,000-line target of `agent/core/6-pace.md`; most of it is the two scripts in two languages, each with the full uninstall.
