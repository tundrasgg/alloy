## Summary

ARFC 0007 gains a recovery path for a `cloud-admin` user with no credential left: a fourth local admin action, `iam:RevokeUserAccessKeys`, revokes all of a user's keys and frees both key limits (new clause 3.9.13, table in 3.10.1).
ADR 0050 supersedes ADR 0041 for that action and restates ADR 0041's other decisions unchanged. ARFC 0020 is unchanged and holds.
The `NotFound` rule of 3.9.11 now covers only a call whose target is one access key. A `replaces` naming a key that is not kept is ignored (3.9.10). Authenticating with a revoked, deleted, or unknown key fails with `Unauthenticated` (new clause 3.9.12).
Section 7 states how re-logins through `replaces` consume kept keys and how the room is freed.

- F2 (fix): resolved. New clause 3.9.13: one call names a user and revokes every unrevoked access key of that user, each with the effects of 3.9.7. Since every ancestor and descendant of a user's key belongs to the same user (3.9.2, 3.9.5), this is a revocation with `descendants: true` of the whole lineage, and when it commits the user has no kept key (3.9.11), so both the 100 unrevoked and the 1,000 kept counts of section 7 are 0. Clause 3.10.1 gives the local admin this action for a `cloud-admin` user, the same limit as `iam:IssueLoginCode`. It voids no login code issued by a local admin, and an exchange refused at a limit does not spend the code, so the two calls work in either order. The cluster's only `cloud-admin` with a stolen only key therefore recovers: the local admin revokes all its keys, which ends the thief's keys, tokens, and codes, then issues a code the user exchanges. This also covers the reviewer's follow-up on the 100 unrevoked key limit. Check against ARFC 0020: no trusted party is added (2.2, the same socket and principal as ADR 0041); no adversary in 2.1 reaches it (no network listener, compute nodes refused under 3.10.4, so 3.3 holds); it only removes credentials that user id 0 on a control node can already remove by acting as the user (ADR 0041's facts); and it makes 3.4 ("a stolen credential ... until revoked") reachable when the user has no credential left. Section 8 states the path and its limits for users without `cloud-admin`.
- F1 (fix): resolved. Clause 3.9.11's `NotFound` rule now applies only to a call whose target is one access key given by its id (reading it, or revoking it with or without `descendants`), and says that an access key id anywhere else follows its own clause. Clause 3.9.10 lists what "anything else" covers, a key that is not kept included, and says the exchange's response and error are those of the same exchange without `replaces`, so a computer whose key was deleted elsewhere logs in again. New clause 3.9.12 gives authentication one outcome: a request signed with an id that names no unrevoked key (revoked and kept, deleted, or never issued), or with a bad signature, or carrying a token refused by 3.9.7, fails with `Unauthenticated`, the same code and message in every case, changes nothing, and is audited as an authentication attempt. The two conforming readings the reviewer found now have one answer each.
- F3 (note): resolved in section 7. It states that a re-login through `replaces` with a code issued by the replaced key, or by a key descending from it, directly or through a session token, keeps the replaced key and consumes one kept key per re-login, and that the user frees the room by ending every unrevoked key descending from the chain: revoking it, revoking all its keys (3.9.13), or logging the computer in again with a code from outside the chain. Section 8 points there.

## Decisions

- A fourth local admin action that revokes every access key of a `cloud-admin` user, rather than one that revokes a named key with `descendants: true`. Reason: a user with no credential cannot list its keys to find the stolen one, so a named-key action would need a fifth, listing, action; revoking all keys covers the same lineage and frees both limits.
- The same action, `iam:RevokeUserAccessKeys`, is open to every user on itself through every built-in org role and `cloud-admin`. Reason: one action name for the local admin and for users; it is the bulk form of revoking one's own keys, which those roles already allow (3.9.6).
- A login code from a local admin, from `alloy init`, or through a session token that derives from no access key survives the bulk revocation. Reason: 3.9.7 voids only codes issued through a revoked key, and the recovery code must survive in either call order.
- New error code `Unauthenticated` for a request whose access key, session token, or temporary key fails authentication, the same code and message for a revoked, deleted, or never issued key and a bad signature. Reason: one defined error, and a caller learns nothing about which ids exist, as PB-0001 does for join tokens.
- ADR 0041's status line is not set to `superseded by 0050`, and its row in `adr/README.md` is not changed: `adr/0041-*.md` is outside `touches`, and the index is append-only. See Issues.
