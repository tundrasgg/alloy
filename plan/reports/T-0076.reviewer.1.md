Every boot spawns workers that sleep on the host clock, yield, call `timeout`, and spawn, cancel, and join children. The control task applies or schedules 30 random faults: `Crash` with `after_polls` 0 to 3, `Restart` with and without `rng_replay`, `ClockRate`, `ClockStep`, and `Stall`. No `task-poll` comes between the n-th counted poll of an armed crash and its `host-crash`. Inside the tasks, the host clock never decreases, and a sleep never completes before its deadline.

Attack G (finding F1): one host whose boot records its start and its first 8-byte draw. The control task crashes it and restarts it four times, with `rng_replay` `Some(1)`, `Some(2)`, `None`, and `Some(3)`.

```
ATTACK G: Pass; (start, first draw) = [(1, 18319406404002883562), (2, 18319406404002883562), (3, 17500078643141557777), (4, 9603473062687356014), (5, 12593281085914616372)]
```

Start 2 replays start 1 and draws its stream, as required. Start 3 replays start 2, so it must draw start 2's stream, 18319406404002883562. It draws a stream no start drew. Start 5 replays start 3 and also draws a stream that start 3 did not draw. Cause, by reading: `Core::start` stores `replay.unwrap_or(start)` as the source (`crates/alloy-sim/src/host.rs:289`). It should store the source that start `s` used.

Attack B (finding F2): one host whose boot never completes. The control task applies `Stall` for 1,000 s, then `Crash`, then awaits a future that never completes. The same scenario without the stall is the baseline.

```
ATTACK B: without stall: Liveness at 0ns; stall then crash: Liveness at 1000s; failure = Some(Detail("nothing is runnable and no event is pending at world time 1000000000000 ns, before the budget of 3600000000000 ns"))
```

Clause 3.3.6 says a crash ends every stall in force, so after the crash nothing is pending. Under clause 3.2.7 step 4, world time stays at 0. Cause: `crash` clears `stall_until` (`host.rs:351`), but the `StallEnd` event that `stall` added (`host.rs:377`) stays among the world's events, and the run loop advances time to it.

Attack F (finding F3): a host task polls a host clock sleep with a waker whose `wake` spawns a task through the host's `Runtime`. That is what a wake-by-spawning executor adapter does. The run executes on a helper thread, and the test waits 10 s.

The module doc (`core.rs:5-13`) states that `core` is never held while task code runs. `touch_timer` also drops a replaced waker under `core` (`core.rs:506`).

## Issues

- `spec-issue`: section 7 states no bound on the starts of one host. Each start adds one entry to two per-host tables (`crates/alloy-sim/src/host.rs:130`, `host.rs:210`), and `start` is a `u32` (I-21). `spec/arfc-0005-simulator-and-natlab.md` section 7.
- `spec-issue`: clause 3.1.4 says host time saturates at `Instant::MAX` and also says `sleep_until(Instant::MAX)` never completes. With a positive offset the host clock reaches `Instant::MAX` within the world time limit, so a sleep to `Instant::MAX` polled after that moment completes. `spec/arfc-0005-simulator-and-natlab.md` clause 3.1.4.
- `process-issue`: `cargo xtask check-repo` does not check the banned item "comments that describe future work with no task id" (`agent/core/4-evidence.md`), so only review catches it (finding F5). `xtask/src/rules/code.rs`.
- `follow-up`: a `mem` `Net::interfaces(Some(g))` future pending at a crash never completes with `Closed` (`crates/alloy-sim/src/host.rs:748`). T-0077 replaces this list and can cover the case.
