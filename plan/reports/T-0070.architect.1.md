## Summary

ARFC 0007 clause 3.3 now states that user id 0 on a control node can read all tenant data of every org, names control plane state, access key secrets, and every kind of data a node it controls holds, and says the ARFC neither bounds nor lists the means.
Clause 3.3 states exactly what is audited: calls through the API, the local admin socket included, and nothing done outside it. It quotes ARFC 0018 clause 3.3.1 in full and rules how it reads (T-0065 review F3).
Clause 3.10.1 and section 8 drop every "one way", "only", and "two ways" limit on reach to tenant data. Section 8 keeps the API table as examples and adds a paragraph on what the chains record.
F2 and F4 are covered by the plain statement. F5 gets one sentence in clause 3.10.7.

T-0065 review findings:

- F1 (fix): resolved. Clause 3.3 states the whole reach, control plane state on the node's disks and access key secrets included, and no longer claims a count.
- F2 (fix): resolved. Clause 3.3 says the reach holds whether a node already holds the data, citing the `alloy init` node (ARFC 0002 section 3.1), or is made to hold it. Section 8 no longer says other cloud admins can see that a way was prepared; it says what user id 0 reads with no call is in no chain and raises no warning.
- F3 (fix): resolved. Clause 3.3 quotes ARFC 0018 clause 3.3.1 as written and rules that its "cloud admin action" is one that reaches the control plane through the API, since clause 3.3.3 commits each record in the transaction of the change. ARFC 0018 itself is outside `touches`; see Issues.
- F4 (note): resolved. Clause 3.3 names guests, volumes, objects, registry content, and VPC traffic, and cites ARFC 0012 section 1, clause 3.1.1, and section 6 alongside ARFC 0011 clause 3.4.1.
- F5 (note): resolved. Clause 3.10.7: when the target is an org, the org lies in no org, a policy attached to it is not on the side of the target, and a deny there must not refuse the recovered user's call.

## Decisions

- Clause 3.3 rules that "every cloud admin action" in ARFC 0018 clause 3.3.1 means an action that reaches the control plane through the API, because clause 3.3.3 commits each record in the transaction of the change and an action outside the API has none. Class N: it settles how two ARFCs read together. Clarification, no behavior change, so no ADR.
- Clause 3.10.7: a policy attached to an org is not on the side of the target for a call whose target is that org, which follows from the existing text that an org lies in no org. Class R, a clarification of the literal reading, and it keeps tenants from blocking cloud admin management of their own org (3.3).

## Issues

- `follow-up`: ARFC 0018 clause 3.3.1 should say itself that "every cloud admin action, including break glass access" means actions through the API, matching the ruling now in ARFC 0007 clause 3.3 (`spec/arfc-0018-observability-and-audit.md`).
- `follow-up`: ADR 0055, "Ruling on I-02" and "Consequences", still says the local admin "can come to tenant data in two ways only" and "can reach tenant data only by the two ways". Accepted ARFC 0007 now outranks it and says otherwise. A superseding ADR or an amendment should state the whole reach (`adr/0055-root-on-a-control-node-is-a-full-break-glass-administrator.md`).
