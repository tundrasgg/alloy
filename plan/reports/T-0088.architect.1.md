External facts the text relies on, with sources:

- GitHub's latest release is "the most recent non-prerelease, non-draft release": https://docs.github.com/en/rest/releases/releases#get-the-latest-release. This is why previews install from pinned URLs (clause 3.15).
- Artifact attestations are made by the `actions/attest` action and checked with `gh attestation verify <file> -R <owner>/<repo>`. Public repositories sign them through the Sigstore Public Good Instance: https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds and https://docs.github.com/en/actions/concepts/security/artifact-attestations.
- Wintun's signed DLLs may be shipped with other software, and the project calls that the only supported way to distribute it. Builds exist for AMD64, x86, ARM64, and ARM32, current version 0.14.1: https://www.wintun.net/. Its prebuilt license allows redistribution only with software that uses it through its published API, and forbids modification: https://git.zx2c4.com/wintun/plain/prebuilt-binaries-license.txt.

## Decisions

- Install, uninstall, and coexistence go in ARFC 0017 as clauses 3.13 to 3.17, because that ARFC already owns releases and artifacts.
- Preview integrity: each install script carries the SHA-256 of every archive of its own release, and checks a download against it before reading any entry. `SHA256SUMS` and GitHub artifact attestations exist for manual checks. A preview has no release key, its `alloyd` never replaces itself, and `alloy cluster upgrade` refuses while any node runs a preview. Previews make no compatibility promise, so a cluster runs exactly one preview release. The first stable release adds an Ed25519 release key and `SHA256SUMS.sig`, which `alloyd` verifies (clause 3.8). The install scripts keep checking digests only, because a key fetched together with the script proves nothing on a first install. This differs from PB-0001, whose transcript prints "release signature verified" (see Issues).
- A script installs the release it belongs to. `--version` re-runs the pinned script of that release. On Windows this means `irm | iex` needs no parameters.
- Uninstall is an `uninstall.sh` or `uninstall.ps1` shipped inside the archive, so the digest covers it, plus `--uninstall` on the install scripts. Node state is kept unless `--purge` is given. `--purge` runs `alloy node leave` first, and `--force` overrides a failed leave or running guests. Reinstalling over kept state restarts the node.
- An install manifest (section 4.1) lists every path, service, and `PATH` entry the install created. Uninstall works from it, so any release's uninstall removes any release's install.
- Ownership is by reserved names: interfaces `al<digit>` and `alv<digit>`, `nftables` tables `alloy` and `alloy_*`, units starting with `alloy`, and `alloy` users. Alloy creates no firewall state at all in this version, and adds addresses or routes only where they overlap nothing in use. `init` and `join` check both rules.
- Client node: `alloyd` and `alloy-net` only. It runs as the Windows service `alloyd` on Windows, and joins with `alloy join` (`--roles none` on Linux, always on Windows). Its infrastructure address sits on `al0` as a /64, and `al0` is a Wintun adapter on Windows. VPC routing for clients goes in ARFC 0009 clause 3.13, to be added by the rung 6 spec task.
- Minimum Windows for a client node is build 17763 (Windows 10 1809, Server 2019). This is a support choice, not a researched Wintun limit, and the rung 1 check confirms it on real hardware.
- No ADR other than 0062: the task allocated only that number. The preview integrity rule constrains future releases and may deserve its own ADR. Allocating one is the lead's call.
