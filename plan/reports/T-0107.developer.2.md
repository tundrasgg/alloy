Round 2 resolves review findings F1, F2, F3, and F5 on `task/T-0107` (682 lines added, 104 removed, all in `crates/alloy-state`). Every acceptance command passes.
F4 (`native` files at mode `0600` on Linux, clause 5.2) stays open. It cannot be fixed inside this task's `touches`: `redb` creates its files through `std::fs::OpenOptions` with the umask, `clippy.toml` forbids setting a mode outside `alloy-rt`, and the `alloy-rt` `disk-io` `OpenOptions` (ARFC 0005 clause 3.1.10) has no mode field. ## Changes

- F1 `crates/alloy-state/src/resource.rs`: `MAX_RESOURCE` (1 MiB, section 7), `check_command`, and `check_size`, which measures the encoded length without encoding. A unit test checks the measure against the encoding.
- F1 `crates/alloy-state/src/group.rs`: `write` checks the command before proposing it, so an oversized or invalid write returns `Invalid` and is never proposed. `decide` refuses over `MAX_RESOURCE`, the same limit, deterministically. `append_runs` splits one `openraft` append into store appends within `MAX_APPEND_BYTES`.
- F2 `crates/alloy-state/src/rt.rs`: `RtScope` (runtime plus `Tasks`). Every spawned task is registered and wrapped in `Abortable`. Its future drops before the task counts as ended. `Tasks::close` aborts every live task and refuses new ones, and `Tasks::ended` completes once none is live.
- F2 `crates/alloy-state/src/group.rs`: `shutdown` shuts `openraft` down, then closes the scope and waits, at most 60 s, until every task has ended, after a store failure too. `open` does the same on failure. `Drop` closes the scope without waiting.

That bounds the buffer at `MAX_BUFFERED`, 2 MiB plus one largest pair plus 2 KiB, whatever the store's size. A `debug_assert` checks the bound, and the unit test `a_snapshot_buffers_a_bounded_amount` exercises it.
- F3 `crates/alloy-state/src/mem.rs`, `crates/alloy-state/src/native.rs`: `Source::after` ends each batch with `batch_full`.
- F5 `crates/alloy-state/src/mem.rs`, `crates/alloy-state/src/native.rs`: in `read`, `scan`, and `StateInstall::finish`, the sticky `Io` check runs before every argument or format check. The `mem` unit test covers each of them after a failure.
- `crates/alloy-state/src/lib.rs`: re-exports `MAX_RESOURCE`.
- `crates/alloy-state/tests/group.rs`: the original scenario on seeds 0 to 999; write-stop-rebuild-at-once-read on seeds 0 to 999; store failure (`fail_after` 3 to 62), then stop, rebuild, and check every acknowledged write, on seeds 0 to 999; 1 MiB and 70 MB creates and an oversized update refused while the group serves on.

## Decisions

- N: the 1 MiB resource limit of section 7 is measured on this crate's encoding of the resource (`MAX_RESOURCE`), checked before proposing and again when applied.
- N: `Group` tracks the tasks `openraft` spawns and aborts any that remain after `Raft::shutdown`. `openraft` leaves some tasks (timers, workers) running for up to about 120 s of virtual time after shutdown.
- R: one `openraft` append may become several store appends. A stop between them leaves a prefix of the entries, which Raft allows, because the entries are reported durable only once every run is.

## Issues

- spec-issue: ARFC 0006 clause 5.2 requires `0600` files, but ARFC 0005 `disk-io` has no file mode and ADR 0064 has `redb` open its own files. The same gap meets ARFC 0002 line 606 (node key file `0600`). See `crates/alloy-state/src/native.rs:69`.
- follow-up: no test of `native`'s sticky `Io` (F5), because a real I/O error cannot be injected into `redb` on the CI host. The fix was checked by reading `native.rs` `read`, `scan`, and `finish`.

## Question

How is F4, the `0600` mode of `log.redb` and `state.redb` on Linux, to be resolved?

1. Recommended. Merge T-0107 with F4 open, and cut a `spec` task that adds a create mode to the ARFC 0005 `disk-io` `OpenOptions`, followed by a `build` task on `alloy-rt` and `alloy-state`: `native` creates each file through `disk-io` with mode `0600` before `redb` opens it, since `redb` keeps an existing file's mode. One mechanism then also serves the ARFC 0002 node key file.
2. Amend ARFC 0006 clause 5.2 by a spec change to "readable only as the data directory is" (section 8 already says this), so the directory's mode protects the files. No code change.
