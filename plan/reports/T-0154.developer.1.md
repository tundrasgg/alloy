## Summary

The socket behind the rule is the UDP wildcard bind of the ports check, `busy_ports` in
`crates/alloy/src/setup/probe.rs`: `bind_udp` on `0.0.0.0:7476` and `[::]:7476`. Neither
seam can check a UDP port on Windows without that bind, so per the task's scope I raise a
`spec-issue` and stop. No product code changed. No acceptance command was run.

## How the socket was found

- On Windows the host check passes only for `join` of a client node
  (`setup/checks.rs:301-307`). `init` stops there (`checks.rs` `run`), so its TCP `listen`
  never runs on Windows. A client never serves the API (`Kind::serves_api`), so the TCP
  branch of `busy_ports` is skipped too. That leaves the two UDP binds.
- No other code in `crates/alloy/src` binds or listens. `login.rs:356` and the API client only `connect`.
- Windows writes the rule when the prompt is raised, as TCP or as a TCP and UDP pair, and
  turns it to Allow only if someone answers it. The rule says which program, not which socket.

## Why the existing seams fall short

Source: https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse,
the Windows Server 2003 and later tables.

- A wildcard `bind_udp` is the socket that raises the prompt (above), so it must not run.
- A UDP bind on `127.0.0.1` or `::1` raises no prompt. But when the same account already holds
  the wildcard, that bind succeeds: "Default Wildcard" row, "Default Specific" and
  "SO_EXCLUSIVEADDRUSE Specific" columns, both Success. So the check would call a taken port free.
- `net` has no TCP bind without `listen` and no exclusive-bind option. `host` has no port table.
  Neither seam can read `GetExtendedUdpTable` or `GetExtendedTcpTable`.

## Issues

- `spec-issue`: ARFC 0005 clause 3.1.18 (`host` seam) has no read-only way to tell who holds a TCP or UDP port, so ARFC 0002 section 3.8's ports check can only bind wildcard, which raises a Windows Firewall prompt (`crates/alloy/src/setup/probe.rs` `busy_ports`).
- `follow-up`: the ports check never names "the process and pid holding it" (ARFC 0002 section 3.8). A port-table seam would also fix that.
- `follow-up`: the `os` net tests in `alloyd` and `alloy` listen on wildcard addresses on Windows and leave Query User rules (firewall log above). Out of scope here.

## Question

How should the ports check learn that a port is taken on Windows without a wildcard bind?

1. (Recommended) Have a spec task add a read-only `host` seam call returning the holders of a TCP or
   UDP port with their pids: Windows `GetExtendedTcpTable`/`GetExtendedUdpTable`, Linux
   `/proc/net/{tcp,udp}{,6}`. Then an `alloy-rt` build, then T-0154 again. It is accurate and opens no socket.
2. Use today's seams: on Windows, bind UDP on loopback only. It misses a port the same account
   holds on the wildcard (Microsoft table above), so it does not fully meet ARFC 0002 section 3.8.
3. Change the spec so the ports check does not run on Windows clients, and let `alloyd`'s own
   bind failure report a taken mesh port.
