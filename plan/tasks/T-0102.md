## Goal

M11 rung 2 can be built from the specs. Concretely:

- `alloy init` on a Linux node creates a cluster.
- `alloy join <token>` makes a second Linux node and a Windows client node members of it.
- `alloy node list` run on any of them shows all three.

T-0103 specifies the control-plane half (state store, heartbeats, health, the list). This task specifies identity, join, the API transport, and ports, and resolves the open rulings that block the first TLS and API code.

## Scope

- Default ports, absorbing T-0024 (cancelled):
  - the mesh UDP port and the API TCP port;
  - how the API shares or avoids TCP 443.
  On the pilot's nodes 443 is free; Proxmox VE uses 8006 and 3128. Fold in the T-0088 issue that ARFC 0004 does not exclude Alloy's own `al*` addresses from candidates, and findings F1 (an ADR superseding ADR 0061 for the T-0090 changes; this task holds ADR 0063 for it if needed) and F2 of `plan/reports/T-0090.reviewer.2.md`.
- The API transport ruling: what `alloy-proto` and `alloy-api` use on the wire for M11 (R-0007: `prost` with `tonic`, connect-rust, or another). Keep within `agent/eng/deps.md` standing choices unless an ADR changes one. Specify the JSON over HTTP surface only as far as rung 2 needs.
- The TLS randomness ruling recorded on the board (from T-0049): `rustls` providers draw key shares and randoms from their own generator, against `agent/eng/crypto.md` rule 4 and I-20. Decide it in `agent/eng/crypto.md` and an ADR (0042 is allocated here):
  - an exception for TLS under `os`, with how the simulator handles TLS;
  - or a provider fed from `alloy-rt`.
- Join over the underlay for rung 2: what `init` and `join` do step by step, with the exact data each side stores:
  - identity keys and the cluster key;
  - the API CA (P-256, ADR 0053) and its fingerprint pinning;
  - join tokens and node records;
  - client nodes (section 3.11, Windows, roles none).
  Close any gap that would stop a developer, including the open T-0088 re-review items F1 (Windows data directory ancestors) and F2 (recording a non-default data directory). Say which traffic in rung 2 uses the underlay, and which waits for the mesh in rung 3.
- How the CLI on each machine reaches the API in rung 2:
  - on a node, as root, through the local admin path (ADR 0055);
  - on the Windows client, through a context made at join, or by `alloy login`.
  Say which, so `alloy node list` works on all three.
- Fold the ARFC 0008 issues from `plan/reports/T-0087.product.1.md` that rung 2 needs: names, errors, pagination for `node list`. Leave the rest listed.

## Out of scope

- The state store, consensus, heartbeats, health, and the node list output (T-0103).
- Mesh sessions and paths (rung 3).
- VMs.
