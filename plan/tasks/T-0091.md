## Goal

The binaries `alloy` (CLI) and `alloyd` (daemon) exist and build for Linux and Windows, so M11 rung 1 has something to install. `alloyd` runs as a systemd service on Linux and as the Windows service `alloyd` on Windows, on `alloy-rt`'s `OsHost`.

## Scope

- `crates/alloy`: the CLI skeleton of ARFC 0019 clause 3.1: command parsing for `alloy <noun> <verb>` and the top-level commands, with `alloy version` implemented. It prints the version of ARFC 0017 clause 3.13 and nothing else on standard output, so the install check of clause 3.15 step 8 can compare it. Output follows `product/principles.md` T rules where they apply to `version` and to usage errors. Commands that later tasks implement are not registered yet; an unknown command is a usage error.
- `crates/alloyd`: the daemon entry:
  - `alloyd version` prints the same version.
  - Run with no command, it starts an `OsHost`, logs that it started and which data directory it would use (ARFC 0002 section 3.3 default), and keeps running until it is told to stop: SIGTERM or SIGINT on Linux, and a stop request from the Windows service control manager on Windows. It then shuts the host down within the 30 s of ARFC 0017 clause 3.16 step 5 and exits 0.
  - With no local join state, it also states in its log that the node is not initialized and names `alloy init` and `alloy join`. Joining is a later rung.
- The version string comes from the package version at build time. The release workflow (T-0092) sets it for previews.
- Exit codes: this task needs only 0 and 1. If `check-repo` still forbids `std::process::ExitCode` when you start, return `Result` from `main`, and leave the code mapping to the task after T-0089.
- Add the dependencies this needs, for example a Windows service crate and an argument parser, to `deny.toml`, giving each license in the report. Record each crate in `plan/workspace.md` only if it is a new workspace crate (both binaries are, per its table).
- Tests: argument parsing; `version` output; on Linux and Windows, a start-and-stop test of `alloyd`'s run loop through its library entry. The Windows service registration itself is checked by the rung 1 e2e script (T-0093).

## Out of scope

- `init`, `join`, `login`, the API, the mesh, and the install scripts (T-0092).

## Acceptance

```
cargo build --release -p alloy -p alloyd --locked    # expected: builds
cargo test -p alloy -p alloyd --locked               # expected: passes
cargo run -q -p alloy -- version                     # expected: prints the version only
cargo xtask ci                                       # expected: exits 0
```
