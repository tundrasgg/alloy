## Goal

Main is red in CI: `clippy_fixture::clippy_fixture_other_crates_fail` fails on every push since the T-0068 merge, because CI sets `CARGO_TERM_COLOR=always`. Every Cargo or Clippy run whose output `xtask` parses gives the same result whatever the caller's color settings are, and main is green again.

## Scope

- Find every place in `xtask` (gate steps and tests) that runs Cargo, Clippy, or rustc and reads its output. Make each run immune to the caller's color settings, for example by passing `--color never` or by setting `CARGO_TERM_COLOR=never` on the child process. Gate steps count as much as tests: a gate step that misreads colored output can pass code it should reject.
- A test that runs the affected parsing with `CARGO_TERM_COLOR=always` set in the environment and checks that the result is the same as without it.

## Out of scope

- Any other change to the Clippy fixture, `clippy.toml`, or the workflow (T-0079 owns those).

## Acceptance

```
CARGO_TERM_COLOR=always cargo test -p xtask --locked   # expected: passes, including clippy_fixture_other_crates_fail
cargo test -p xtask --locked                           # expected: passes
cargo xtask ci                                         # expected: exits 0
```

## Notes

Evidence for the cause, from a Linux machine on main b082cc3: `cargo test -p xtask --locked clippy_fixture_other` passes; the same command with `CARGO_TERM_COLOR=always` fails. In the failing CI run, the set of lines the test found lacks every `crates/switches` line (the `allow(clippy::...)` and `expect(clippy::...)` lines that the forbid step reports), while every `crates/demo` line is present. The CI log shows ANSI color codes in the compiler messages. Under 100 changed lines in `xtask/` with the lead running acceptance on Linux, this task needs no review (T-0073).
