## Goal

`alloyd join` makes a Linux node or a Windows client node a member of a cluster that `init` made, as ARFC 0002 section 3.3 and section 3.15 state for rung 2. Every member heartbeats over the node channel, and the control node keeps node state. Three `alloyd` instances then form a cluster in which every node is `healthy`.

## Scope

- Read only the named sections.
- The joiner's steps 1, 2, and 4 to 8 with no reflection:
  - the anchor's join service, using T-0127's accept-unknown mode, and the section 3.15 endpoint rule;
  - control node handling of join requests, renewals, and status messages;
  - client nodes (section 3.11, Windows, roles none).
- Heartbeats every 5 s, node state by ARFC 0006 clauses 3.13 to 3.15, and the node lifecycle controller.
- The interface the CLI calls to run `join`; state it in the report for T-0112.
- Tests:
  - three `alloyd` instances on loopback (one `init`, one Linux `join`, one client `join`) reach `healthy` for all three in `ListNodes`;
  - a control node restart leaves all three healthy again within the spec's bound;
  - a joiner with a wrong token is refused.

## Out of scope

- `al0`, paths, relays (rung 3), and leave (section 3.15 leaves it out).

## Acceptance

```
cargo test -p alloyd --locked   # expected: passes, including the three-node loopback and restart tests
```
