## Goal

`alloy-rt` exports `OsHost` and `register_os` (ARFC 0005 section 2.6), and its `os` implementations of `clock`, `rng`, `spawn`, `net`, and `disk-io` meet section 3.1 on a real operating system. Every real Alloy binary will run on this runtime.

## Scope

- `OsHost` on one `tokio` multi-thread runtime with time and I/O drivers, and `register_os` for the five kinds, with the version 1 configurations of section 4.2 (the `OsDiskIoConfig.root` rules included).
- The `os` behavior of every clause of section 3.1 that names `os`: the monotonic clock, the platform's secure generator for `rng`, `spawn` returning `ShuttingDown` after `shutdown`, UDP and streams in `net` (batched UDP I/O with segmentation offload where the platform has it, clause 3.1.2), and `disk-io` mapped below its root.
- Linux is the target platform. The crate must still build and pass its tests on Windows and macOS. Where the platform lacks a feature, return the error the ARFC names for that case, never a silent success.
- Add `tokio` (the standing choice in `agent/eng/deps.md`) and any crate the platform generator or socket options need to `deny.toml`. The report gives each one's license.
- Unit tests for each kind on the host OS. Do not write conformance tests; T-0084 does that.

## Out of scope

- `mem` implementations (`alloy-sim`), and any new trait or method not in ARFC 0005.

## Acceptance

```
cargo test -p alloy-rt --locked   # expected: passes, with tests for each of the five os kinds
cargo deny check                  # expected: exits 0
cargo xtask ci                    # expected: exits 0
```

## Notes

The `os` implementations are the only place outside `alloy-sim` where `std::time`, `std::net`, `std::fs`, `std::thread`, and `tokio` may be called; `clippy.toml` already lets `alloy-rt` use them.
