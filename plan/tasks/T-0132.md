## Goal

`alloyd init` on a Linux node creates a cluster as ARFC 0002 sections 3.1 and 3.15 state for rung 2:
- keys, certificates, and stored data;
- the single-voter state group;
- the node, the `default` organization, the `admin` user, the join token, and the login code;
- the API port and the local admin socket, serving.

After a restart, the node serves again from its stored state.

## Scope

- Read only the named sections.
- Every `init` step that section 3.15 keeps, through `alloy-id`, `alloy-state`, and `alloy-api`. The interface the CLI calls to run `init` is the local admin path or what the spec names; state it in the report for T-0112.
- The anchor side of the node channel's listener, up to accepting a session (T-0127's accept-unknown mode is merged or merging; if not, stop there and report).
- Fix `alloy_id::proto::JoinRequest` to the section 3.3 step 6 layout (T-0111 report).
- Fold T-0111 review F1 (`decode` drops messages section 4.3 says must be answered) and F2 (`Requester::receive` takes a late reply), and the notes F3 to F5.
- Tests: `init` on a fresh data directory, then `ListNodes` on both listeners shows one healthy node; a restart preserves it; a second `init` refuses.

## Out of scope

- Join, heartbeats from other nodes, and the lifecycle controller (T-0133).
