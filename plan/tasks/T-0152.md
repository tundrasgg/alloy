## Goal

`ConvertFrom-NodeListJson` in `tests/e2e/e2e-lib.ps1` reads `alloy node list --output json` as the CLI prints it, so `rung2.ps1` compares states and roles correctly.

## Problem

`--output json` gives the API representation unchanged (ARFC 0019 clause 3.1.4). That's the protobuf JSON mapping (ARFC 0008), which writes enums by name: `"state": "NODE_STATE_ACTIVE"` and `"roles": ["ROLE_ANCHOR", ...]`. The parser keeps those strings, and `rung2.ps1` compares them to `active` and `anchor`. On the third rung 2 hardware run (preview.5), every node was `NODE_STATE_ACTIVE` with the right roles, and the run still failed with: "want roles 'anchor,control,compute,storage', found 'ROLE_ANCHOR,ROLE_CONTROL,ROLE_COMPUTE,ROLE_STORAGE'" and "not active: ... state=NODE_STATE_ACTIVE".

## Scope

- In the parser, map a state `NODE_STATE_<X>` to the lowercase `<x>`, and a role `ROLE_<X>` to `<x>`. Those are the table spellings of clause 3.1.15. Treat a value of any other form, a number included, as a parse problem that names the value, so a later change in the mapping fails loudly.
- Leave every check in `rung2.ps1` as it is.

## Out of scope

- The CLI. Its JSON output is correct.

## Acceptance

From Windows PowerShell 5.1, dot-sourcing `e2e-lib.ps1`:

```
ConvertFrom-NodeListJson '[{"metadata":{"name":"nodes/a"},"spec":{"roles":["ROLE_ANCHOR","ROLE_CONTROL"]},"status":{"state":"NODE_STATE_ACTIVE"}}]'   # expected: Name a, State active, Roles anchor control
ConvertFrom-NodeListJson '[{"metadata":{"name":"nodes/a"},"status":{"state":2}}]'                                                              # expected: Ok false, an error naming the value
cargo xtask ci                                                                                                                                  # expected: exits 0
```
