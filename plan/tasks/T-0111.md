## Goal

`alloyd` becomes a node:
- On `init` it creates a cluster and serves as its anchor and control node.
- On `join` it becomes a member, as a Linux node or a Windows client node.
- It sends heartbeats over the node channel.
- The control node serves `Node` list and get through `alloy-api`.

After this, M11 rung 2 can run on real machines.

## Scope

- Read only the named spec sections.
- The node channel of ARFC 0002 section 3.13:
  - built on `alloy-link` sessions over the `os` UDP seam on the mesh port;
  - join, renewal, leave, and status messages, with node to control-node traffic direct.
  - Forwarding by an anchor without `control` is not built. Every M11 anchor holds `control`, and T-0110 is still settling its rules (D-0050). A join that would need it fails with the error the spec gives for an unreachable control node.
- `init` and `join` inside `alloyd`, step by step as ARFC 0002 sections 3.1 and 3.3 state:
  - keys, records, the API CA, and stored data through `alloy-id`;
  - the state group through `alloy-state`;
  - client nodes (section 3.11).
  Fold T-0091 review findings F1 (data directory checks before reading join state) and F3 (escape control characters in logged arguments).
- Heartbeats and node state (ARFC 0006 clauses 3.13 to 3.15, section 4.3), and the node lifecycle controller.
- The API server on the control node through `alloy-api`, with the local admin path (ADR 0055) for root on the node.
- The interface the CLI (T-0112) uses to ask the local `alloyd` to run `init` and `join` (the local admin path, or what ARFC 0002 names). State it in the report.
- Tests:
  - an in-process cluster of three `alloyd` instances on loopback (one init, one Linux join, one client join), with heartbeats making all three `healthy`;
  - restart of the control node, with state surviving.

## Out of scope

- The CLI front end (T-0112), forwarding by anchors without `control`, the mesh interface `al0`, and paths (rung 3).
