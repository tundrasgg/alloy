## Goal

The native API exists for M11 rung 2:
- `proto/alloy/` definitions with `alloy-proto`'s generated code;
- `alloy-api`, a gRPC server over TLS 1.3 that serves `Node` list and get, with errors as ARFC 0008 defines;
- the generated client the CLI will use.

## Scope

- Read only these sections:
  - ARFC 0008 sections 2 and 3;
  - ARFC 0019 clause 3.1;
  - ARFC 0002 sections 3.7 (login code) and 3.13 (only what the API needs);
  - ARFC 0006 section 2.6 (the `Node` kind);
  - `agent/eng/crypto.md` rule 4 and the TLS row.
- `proto/alloy/common/errors.proto`, and the `cluster` service at `v1alpha1` with `Node` and the methods rung 2 needs (`ListNodes`, `GetNode`), every item documented (clause 3.11). Fold the board note on `Unauthenticated` in errors.
- `alloy-proto`: `prost` and `tonic` generation at build time, with no network access at build.
- `alloy-api`:
  - a `tonic` server on `rustls` with the provider and randomness ruling of crypto rule 4 and ADR 0042;
  - ALPN sharing of TCP 443 as T-0102 specified, to the extent rung 2 needs;
  - pagination (clause 3.4) and errors (clause 3.6);
  - authentication by a session token or the local admin path, as ARFC 0002 and 0019 require for rung 2.
  The resource store is a trait argument, so `alloy-state` plugs in when it merges.
- A generated client wrapper with the helpers clause 3.10 asks for, as far as rung 2 needs.
- Add `tonic`, `prost`, `rustls`, and the provider to `deny.toml`, giving licenses in the report. If the `aws-lc-rs` provider cannot build for `x86_64-unknown-linux-musl` or Windows MSVC in CI, report it as a `spec-issue` with the error, and propose the alternative crypto rule 4 allows.
- Tests: an in-process client and server over TLS; list and get with pagination; error codes; a rejected unauthenticated call.

## Out of scope

- Other services and kinds, the console, JSON over HTTP beyond what rung 2 needs, and SigV4.
