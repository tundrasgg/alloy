- Specs affected: arfc-0002, arfc-0019, arfc-0008, arfc-0007

## Who and why

A cloud admin setting up Alloy for the first time, on one spare machine or a few,
at home, in a lab, or in a server room. They want a working cluster they can reach
from their own computer, with as few decisions as possible, and they want to be
told plainly what is still fragile and the one command that fixes it.

## Behavior

**Install**

- The installer detects the operating system and architecture, downloads the
  matching release, verifies its signature against the release key (ARFC 0017
  §3.8), and installs into `/usr/local/bin`. It changes nothing else except the
  service file, and starts nothing.
- On Linux 6.1 or later on x86_64 or aarch64 it installs `alloy` and `alloyd`
  and a disabled `alloyd` service. Anywhere else it installs only `alloy`. On
  Windows the same installer is `install.ps1`, run with
  `irm https://<download-host>/install.ps1 | iex`.
- `--version <x.y.z>` installs a specific release. The last line always names the
  next command.

**`alloy init`**

- Must run as root on Linux. It checks the machine, picks an advertise address,
  creates the cluster as ARFC 0002 §3.1 says, enables and starts `alloyd`, and
  waits until the node is `active` and the API answers.
- Each check prints `ok`, `warn`, or `fail`. Any `fail` stops before anything is
  written, so a fixed rerun starts clean.
- The advertise address is printed with where it came from. When it is a private
  address (RFC 1918, RFC 4193, or link-local), the next line says so, because a
  machine outside that network cannot join through it.
- It creates organization `default`, project `default`, user `admin` (cluster role
  `cloud-admin`, org role `owner` of `default`), pool `default` with one copy on
  one `file` disk under the data directory, and node `node1` with all four roles.
- It prints one join token and one login code, each once, then the standing
  warnings that apply: one anchor always, one copy of data when the pool is
  unprotected, no hardware virtualization when it applies.
- `sudo alloy init` on a machine that is already a node changes nothing and fails
  (see Errors).

**`alloy join <join token>`**

- Must run as root on Linux. It runs the same machine checks as `init`, then
  ARFC 0002 §3.3. It checks the token's checksum before contacting anyone, so a
  mistyped token fails at once and is not counted as a use.
- It prints the anchor it contacts, confirms the cluster key against the token
  before anything else, then prints the roles it joins with.
- Roles: the token's preset roles if it has them, otherwise `--roles`, otherwise
  `compute,storage`. `compute` is left out, with a warning, on a machine without
  hardware virtualization.
- It waits until the node is `active` and prints the time taken. With approval
  required (a cluster setting, off by default), it waits in `pending` and prints
  the approve command for a cloud admin. Ctrl-C stops the waiting, not the join:
  `alloyd` keeps the request open until it is approved, rejected, or the token
  expires. Running the same `alloy join` again resumes the wait.
- After join, the node's storage disk is added to the existing pool `default`.
  Copies are not changed.
- `--no-wait` returns once `alloyd` has the request, exit code 0, and prints the
  command that shows progress: `alloy node get node2`.

**`alloy login`**

- `alloy login <login code>` works on any computer. The code carries the API
  addresses and the API certificate authority's fingerprint, so the CLI pins the
  certificate (ARFC 0019 §8) with no question to answer.
- The code is exchanged once for a new access key belonging to `admin`, named
  after this computer's hostname. The key goes into the operating system keychain,
  or a file readable only by the user where no keychain exists (ARFC 0019
  §3.1.9). The code is then spent.
- It creates or updates a context. A context is named after the API host unless
  `--context <name>` is given, and becomes the current context.
- `alloy login <address>` with a context whose pinned certificate authority
  matches the cluster found at that address updates that context's API address
  and keeps its access key. This is how a computer follows a cluster whose address
  changed.
- `sudo alloy login --issue-code`, run on a control node, prints a new login code
  for `admin`. It works with no context, through the local `alloyd`, because root
  on a control node already holds the cluster key. The action is audit-logged as
  `root@<node>`. Run on a logged-in computer, without `sudo`, it prints a login
  code for the current user.
- Password login for other users is not part of this brief.

**`alloy token`**

- `alloy token create` prints one join token and how long it is valid. Flags:
  `--expires <duration>`, `--uses <n>`, `--roles <list>`, `--zone <name>`.

  ```
  $ alloy token create
  sudo alloy join alyt_hd7rpe…q2na
  This join token works for 24 hours, any number of times. Anyone who has it can
  add a machine to this cluster.
  ```

- `alloy token list` shows `ID`, `EXPIRES IN`, `USES`, `ROLES`, `ZONE`, never the
  secret. `alloy token revoke <id>` asks for the id on a terminal, as any
  destructive command does (ARFC 0019 §3.1.6).

**`alloy node`**

- `alloy node list` columns: `NAME`, `ROLES`, `ZONE`, `STATE`, `MESH`, `VERSION`.
  `STATE` is `joining`, `pending`, `active`, or `unreachable`. `MESH` is `direct`
  or `relay-only` (ARFC 0004 §3.7).
- Standing warnings that concern nodes (one anchor, relay-only nodes, an anchor
  whose advertise address is gone, nodes on two versions) follow the table on
  stderr, each with a `Try:` line. They never appear in `--output json` or `yaml`
  on stdout.
- `alloy node update <name> --roles <list>` and `--advertise <addr>` change a
  node's roles and anchor addresses. `alloy node approve <name>` and
  `alloy node reject <name>` decide a pending join.
- `sudo alloy node leave`, run on the node itself, asks the control plane to
  delete the node's record when it can reach it, stops `alloyd`, and removes the
  node's cluster state and keys. Guests and data on the node must have been moved
  first. It refuses on the last control node.

**All commands**

- Output follows ARFC 0019 §3.1.4: tables and progress on a terminal, plain lines
  and no color on a pipe, and the API representation with `--output json`.
- Errors print the API error's message, then `Try:` with the next command when one
  exists (ARFC 0019 §3.1.8). Warnings use the same form, starting `Warning:`.
- Join tokens, login codes, and access key secrets never appear in logs, in
  `--output json`, or in error messages (I-22).

## Defaults

| Input | Default | Why |
|---|---|---|
| `init --advertise` | The address of the interface holding the default IPv4 route, else the default IPv6 route | It is the address other machines on the same network most likely reach |
| `join --advertise` | As for `init`. Used only when the node holds `anchor` | An anchor needs an address in tokens; other nodes are found by the path manager (ARFC 0004) |
| `init --mesh-port`, `join --mesh-port` | UDP 7270 | One fixed port is easy to open in a firewall |
| `init --api-port` | TCP 443 | ARFC 0008 §3.8. Shared with the anchor's TCP fallback (ARFC 0004 §3.6) |
| `init --name`, `join --name` | The hostname, lower case, cut at the first dot, with characters outside `[a-z0-9-]` replaced by `-`, prefixed `node-` if it does not start with a letter. A name already in use gets `-2`, `-3`, ... | People already know their machines by hostname |
| `init --data-dir`, `join --data-dir` | `/var/lib/alloy` | Standard location for service state |
| Disk contributed | One `file` disk at `<data-dir>/disks/0` | Works on any machine with no spare device (principle 3) |
| `join --roles` | Token preset, else `compute,storage`, without `compute` when there is no hardware virtualization | A new machine adds capacity. Anchors and control nodes are a choice about reachability and quorum |
| `join --zone` | Token preset, else `default` | A new cluster has one zone |
| Join token from `init` and `token create` | 24 hours, any number of uses, no preset roles or zone | ARFC 0002 §3.2 |
| Login code | 24 hours, one use | It grants cluster admin, so it should not outlive its first use |
| Approval for joins | Off | Holding a valid token is the authorization. A cloud admin can require approval |
| `login --context` | The API host from the code | Unique per cluster in practice, and readable |
| Org and project of a new context | `default` and `default` | The ones `init` creates |
| Where the access key is kept | Operating system keychain, else a mode `0600` file in the config directory | ARFC 0019 §3.1.9 |
| Waiting | `init`, `join`, and `login` wait for completion and show progress. `--no-wait` returns early | ARFC 0019 §3.1.5 |
| `--output` | `table` | ARFC 0019 §3.1.4 |

## Errors

The ten most likely failures. Each message is printed as shown, then the `Try:`
line. Exit codes follow ARFC 0019 §3.1.7.

| Situation | Message | Next step shown |
|---|---|---|
| Unreachable address: `join` gets no reply from any anchor in the token | `Cannot reach anchor node1 at 192.168.1.10: no reply on UDP 7270 or TCP 443 after 10 s. A firewall may block these ports, or this machine may not be able to route to that network.` Exit 6. `login` prints the same for the API address on TCP 443. | `Try: open UDP 7270 and TCP 443 on node1, then run the same command again.` If the anchor's address changed, the line names the next row's fix instead |
| Expired token | `This join token expired 3 hours ago. Join tokens work for 24 hours unless created with --expires.` Exit 4. Only shown once the secret matched; otherwise the wrong token message is shown | `Try: alloy token create` (on a logged-in computer, or with `sudo` on a control node), then join with the new token |
| Wrong token: mistyped | `This is not a valid join token: its checksum does not match. It may have been cut off or mistyped.` Exit 2. Nothing is sent | `Try: copy the whole token again. It starts with alyt_ and has no spaces.` |
| Wrong token: revoked, unknown, or wrong secret | `The cluster did not accept this join token. It may have been revoked, or replaced by a newer one.` Exit 4. The attempt counts as a use and is audit-logged (ARFC 0002 §6) | `Try: alloy token create` (on a logged-in computer) |
| Wrong token: something answers at the anchor's address but cannot prove it holds the anchor's mesh key, or its cluster key does not match the token | `The machine at 192.168.1.10 could not prove it is the anchor named in this join token. Nothing was sent to it. The address may now belong to another machine.` Exit 1 | `Try: alloy token create` (on a logged-in computer) for a token with the anchor's current address |

## Requested design changes

ARFC 0002:

- §3.1: make `--advertise` optional, defaulting as in Defaults. `init` reports
  the chosen address and whether it is private.
- §3.1: `init` also creates project `default`, user `admin` with `cloud-admin`
  and `owner` of `default`, and pool `default` on one `file` disk. The "initial
  admin credential" is a login code, defined below, not a raw secret.
- New section: the login code. `alyc_` plus unpadded lower case base32 of version,
  `cluster_id`, the API CA fingerprint, a code id, a 16 byte secret, the API
  endpoints, and a checksum. One use, 24 hours, stored as `BLAKE3(secret)`.
  Exchanged once for an access key.
- §3.2: add a checksum to the join token (for example the first 4 bytes of
  `BLAKE3` over the other fields) so a mistyped token is rejected locally and does
  not count as a use.
- §3.3: default roles for a joiner without preset roles are `compute,storage`,
  minus `compute` without hardware virtualization. Default node name from the
  hostname. Flags `--roles`, `--zone`, `--name`, `--advertise`, `--mesh-port`,
  `--data-dir`, `--no-wait`.
- §3.3: the joiner sends its release version before the token secret. The anchor
  refuses a joiner outside the cluster's version window (ARFC 0017 §3.1) without
  checking the token, and says which releases it accepts.
- §3.3: the reason a token was refused (expired, revoked, used up) is returned
  only after the secret matches. Otherwise the joiner gets one generic refusal.
- §3.3: approval. `pending` lasts until approved, rejected, or token expiry.
  Commands `alloy node approve` and `alloy node reject`. The joiner's `alloyd`
  holds the request, so the CLI may stop waiting.
- §3.3: `join` on a machine that holds a node record, and `init` on one, fail with
  `Conflict` and change nothing. New command `alloy node leave` returns a machine
  to the unjoined state.
- New: a default mesh port, proposed UDP 7270, configurable with `--mesh-port`.
  The architect confirms the number is unassigned before it is fixed.
- New: `alloyd` records which advertise addresses were on its own interfaces, and
  raises a standing warning when one of them disappears. It does not change the
  address on its own, since tokens and contexts depend on it.
- New: root on a control node can act as a built-in local admin through the local
  `alloyd`, audit-logged as `root@<node>`. Used by `sudo alloy login
  --issue-code`, by `sudo alloy token create`, and by `sudo alloy node update` on
  the node itself. Needs an ARFC 0020 check: root on a control node already holds
  the cluster key, which §2.2 trusts, so this adds no new trusted party.

ARFC 0019:

- §3.1.2: `login` takes a login code or an address, and `--issue-code`,
  `--context`. A login with an address whose CA matches a pinned context updates
  that context's address.
- §3.1.8: warnings use the same form as errors, `Warning:` then `Try:`, on stderr,
  so `--output json` on stdout stays clean.
- §3.2.5: the CLI shows standing warnings that concern nodes after `alloy node
  list`, and all standing warnings after `init` and `join`.
- `alloy node list` columns as in Behavior.

ARFC 0008:

- §3.8: the API port defaults to 443 and is configurable with `--api-port`. On a
  node that is both anchor and control, the API and the stream underlay share TCP
  443, separated by ALPN.

ARFC 0007:

- §2.2 and §2.3: a user may hold access keys created by `alloy login` with a login
  code, one per computer, named after it, revocable like any access key. Password
  and second factor remain the way users log in without a code.

Not an ARFC change, but needed before this brief can ship:

- The download host in `https://<download-host>/install.sh` is a public name and is
  costly to change. The lead asks the pilot (class P).
- `alloy pool update default --copies 2` is a placeholder until the pool brief
  fixes its wording.

## Principles check

1. One command to start, one to join: `alloy init` and `alloy join` are one command
   each with no flags, and every output names its next command. The installer is a
   separate first command; the 60 second measure counts installer plus `init`.
2. Defaults produce something that works: every flag above has a default. The only
   arguments that cannot have one are the join token and login code, which are the
   authorization itself.
3. It works on one machine: `init` alone gives a full cluster with a `file` disk.
   Nothing asks for a second machine, disk, or external service.
4. Say what is true: one anchor, one copy of data, no hardware virtualization,
   private advertise address, relay-only, and a vanished advertise address are all
   printed where the user looks, each with the command that removes the risk.
5. Errors lead somewhere: every row in Errors has a next step. The one exception,
   a certificate mismatch, says why no command is offered.
6. One name per thing: join token, login code, context, access key, advertise
   address, anchor, and standing warning are glossary terms.
7. CLI, console, and API can do the same: every command here is a native API call,
   except the local admin path, which is reachable only by root on a control node.
   The console's first login screen is a later brief.
8. Compatibility is exact: not affected.
9. Tenants are strangers: join and login errors reveal nothing about organizations.
   A wrong token gets one generic refusal.
10. Fast enough to feel local: `init`, `join`, and `login` show progress, and
    `join` targets under 10 seconds (ARFC 0002 §3.3).
