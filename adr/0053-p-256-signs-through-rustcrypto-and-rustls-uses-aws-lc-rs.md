# ADR 0053: P-256 signs through RustCrypto, and rustls uses aws-lc-rs

- Status: accepted
- Subject: api
- Specs: arfc-0002, arfc-0008

## Context

ADR 0048 requires RFC 6979 nonces and keys from `alloy-rt` for every ECDSA P-256 signature and left the source to the `rustls` provider ADR. No provider (`ring`, `aws-lc-rs`, `graviola`, `rustls-rustcrypto`) meets that: each draws the nonce from its own generator (R-0008). `rustls` takes any key through its `SigningKey` trait, so signer and provider are separate choices. ACME (ARFC 0008 clause 3.8) adds a PKCS#10 CSR signed by the certificate key and JWS requests signed by an account key, and RFC 8555 section 6.2 makes `ES256` the only algorithm every ACME server must implement.

## Decision

- Every ECDSA P-256 key Alloy holds is generated by `p256` and `ecdsa` from the `alloy-rt` randomness trait, and every P-256 signature it makes comes from their plain RFC 6979 signer (`Signer::sign`, `rfc6979`, SHA-256, no additional data). No randomized or hedged signer is used.
- `rcgen`, with default features off, builds certificates and CSRs, signing through that key. `rcgen`'s own `KeyPair` never holds an Alloy key.
- `rustls` uses the `aws-lc-rs` provider. Alloy's P-256 keys reach `rustls` only as `rustls::sign::SigningKey` values, never through the provider's `key_provider`, so the provider verifies P-256 and never signs with an Alloy key.
- Three keys are P-256: the API CA key, every API server certificate key (TLS 1.3 `CertificateVerify`, and the CSR of an ACME order), and the ACME account key. The account key signs every ACME JWS as `ES256`, a 64-byte signature of R then S (RFC 7518 section 3.4), under the same rules.
- The ACME account key is the one exception to ADR 0048's "every other signing key stays Ed25519". The rest of ADR 0048 stands.

## Consequences

- `alloy-crypto` gains `p256`, `ecdsa`, `rfc6979`, `rcgen` and `rustls` with `aws-lc-rs`; the lead adds them under `agent/eng/deps.md`.
- Building `aws-lc-sys` needs a C compiler for every target. Moving to another provider later changes one `CryptoProvider` value, not the signing code.
- The binary holds two P-256 implementations: RustCrypto signs, `aws-lc-rs` verifies.
- `rcgen` without its `crypto` feature needs an explicit serial number and key identifier on every certificate.
- The provider draws TLS ephemeral key shares and hello randoms from its own generator, not from `alloy-rt`. `agent/eng/crypto.md` rule 4 needs a ruling on that before the first task that builds TLS.
- Tests: the RFC 6979 appendix A.2.5 P-256 vector, identical bytes for the same key and message, and a 64-byte `ES256` JWS signature.

## Alternatives rejected

- A provider's own ECDSA signer: its hedged random nonce breaks ARFC 0002 section 2 and ADR 0048 (R-0008).
- `rustls-rustcrypto`: pre-release, its README says not for production, and `paste` fails the `cargo deny` advisories check.
- `ring`: no release in over a year, and its `getrandom` 0.2 beside RustCrypto's 0.4 risks `multiple-versions = "deny"`.
- `graviola`: x86_64 and aarch64 only, with CPU features that exclude Raspberry Pi 4 and older boards.
- A custom `CryptoProvider` from `alloy-crypto` primitives: new cryptographic glue that `agent/eng/crypto.md` rules 1 and 2 discourage.
- An Ed25519 ACME account key: RFC 8555 section 6.2 makes EdDSA only a SHOULD, so an ACME server may refuse it.
