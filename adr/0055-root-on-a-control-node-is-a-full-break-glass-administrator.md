# ADR 0055: Root on a control node is a full break-glass administrator

- Status: accepted
- Subject: tenancy
- Specs: arfc-0007, arfc-0020

## Context

This ADR supersedes ADR 0050, which gave the local admin four fixed actions and kept one enabled `cloud-admin` user by refusing calls with `Conflict`. Review showed that every narrow list leaves a dead end: a thief holding the only `cloud-admin` key can move that role to a user the local admin cannot name, or attach a deny that still binds the recovered user after it logs in. The pilot chose a full break-glass administrator over a longer action list and over no local admin (D-0020).
The facts of ADR 0041 and ADR 0050 still hold. ARFC 0020 section 2.2 trusts the hardware and kernel of each node, section 2.1 names a compromised compute node as an adversary but no compromised control node, and section 2.3 has no boundary between user id 0 and `alloyd`. Every control node serves the API (ARFC 0006 section 3.4) and authenticates each call (ARFC 0008 section 3.7), which for SigV4 needs the access key secret (ARFC 0007 section 3.8), kept at rest under a node key file of mode `0600` (ARFC 0020 section 3.7).

## Decision

- Kept from ADR 0050: a user may hold access keys. A user access key is created only by exchanging a login code issued for that user, by that user, by `alloy init`, or by a local admin. It is named after the computer, records `issued_by`, and is listed and revoked like any access key, within 5 seconds. A login code is neither issued for nor exchanged into a disabled user or a user of a disabled org.
- Kept: one key per computer. The exchange takes `replaces`, the id of the key the computer holds for that context, and revokes it in the same transaction. The CLI always sends it when it holds one. Without `replaces` an exchange never touches an existing key, and a taken name gets `-2`, `-3`, and so on. A session token or temporary key obtained with an access key derives from that key, and a login code issued through such a session token is recorded as issued by the key. A temporary key cannot issue a login code.
- Kept: revoking a key voids the unspent login codes issued by it or through it, ends the session tokens and temporary keys that derive from it within 5 seconds, and reports how many keys descend from it. `descendants: true` revokes them too, and they are not revoked by default. Issuing a login code is refused when, in the committed state, the key it is issued through is revoked. Action `iam:RevokeUserAccessKeys` revokes every access key of one user, and every built-in org role and the cluster role `cloud-admin` allow it on the holder's own user.
- Kept: each control node has a built-in principal `root@<node name>`, the local admin, reached only through a Unix socket of mode `0600` owned by user id 0, and only by a peer with user id 0. The control plane derives the node from the socket or the AL session's node record, never from the request, and refuses a node without the `control` role. Calls go through authorization, consensus, and the audit log. No deny binds the local admin.
- New: the local admin's fixed policy allows every action the cluster role `cloud-admin` allows, and every action of the `iam` service on every resource in every org. So it can list orgs, users, roles, and policies, create or enable a user, grant `cloud-admin`, detach or delete any policy, revoke any key, and issue a login code for any enabled user. Its policy allows no action on the contents of an org's resources, and it cannot create a user access key except through a login code. No API method changes what a built-in role allows, so no call narrows this policy.
- New: every local admin call, a read included, is recorded in the cluster chain as `root@<node name>`, and in the chain of each org it reads or changes. A local admin read therefore needs quorum. Every successful local admin write raises the standing warning `local-admin-used` on the cluster until 7 days after the latest one. No call clears it or shortens it.
- Removed: the rule that keeps one enabled `cloud-admin` user. The cluster may hold none, because a local admin can always make one.
- Ruling against ARFC 0020: no change weakens it, and ARFC 0020 is unchanged. The local admin adds no trusted party (section 2.2), and no adversary in section 2.1 gains from it: by the facts in Context, user id 0 on one control node can already act as any principal that holds an access key, and where that node holds the cluster key it holds that too. The ruling does not rest on the cluster key, whose custody across control nodes is open (ARFC 0002 section 9). A stolen key still grants its principal's policies until revoked (section 3.4), and can no longer stop its own revocation.
- Ruling on I-02: consistent. The local admin is on the cluster side of the org boundary, as ARFC 0007 clause 3.3 has cloud admins. No principal of any org gains reach through it, and its policy allows no action on tenant data. It can come to tenant data in two ways only, each a write to that org's identity state: changing who has access (a role, a policy, group membership), or making a credential of a principal that already has access (a login code for a user such as an org `owner`, an access key for a service account, or another `iam` action that sets how a principal authenticates). Each is a break-glass action under ARFC 0007 clause 3.3: that org's own chain records it as `root@<node name>`, as it records every local admin call that touches the org, and it raises the warning.

## Consequences

- A cluster can always be given a working `cloud-admin` from root on a control node, whatever any credential changed: removed roles, disabled users or orgs, attached denies, full key limits. A cloud admin can remove its own role and leave none, and nothing refuses that.
- Administering a cluster and holding root on one of its control nodes are formally the same power. The audit log shows each use as `root@<node name>`, and the warning shows other administrators for 7 days that it was used. Routine `sudo alloy token create` and `sudo alloy node update` on a control node raise it too.
- The local admin can change identity state in an org whose admins hold no access key, which root could not reach through a key before. Each such call is in that org's chain. It can reach tenant data only by the two ways in the ruling on I-02, a grant or a credential of a principal that has access, and that chain records both.
- A user access key bypasses password and second factor. An org that does not want that attaches a deny on `iam:IssueLoginCode`. The deny does not void login codes issued before it and does not bind a local admin. A computer that lost its key store cannot send `replaces`: its old key stays until someone revokes it, and its next login gets a numbered name.
- One revocation with `descendants: true` removes every key, login code, session token, and temporary key of that user that exists because of a stolen key. It does not undo other uses of the user's policies, such as a service account's access key made in the 5 seconds before the revocation binds. The audit log lists those and a local admin can undo them. A key whose `issued_by` is `session` descends from no key and is found through the audit log.
- The local admin must be removed or made to need a quorum, by a new ADR, if a single control node can no longer authenticate API calls or recover access key secrets by itself, a hostile control node becomes an adversary in ARFC 0020 section 2.1, or ARFC 0020 gains a boundary between user id 0 and `alloyd`. A node without the `control` role has no local admin, and removing that role is the only way to revoke one.

## Alternatives rejected

- Keep the narrow local admin and add actions (ADR 0050): five review rounds showed that each list leaves a state a stolen `cloud-admin` key can reach and the list cannot undo.
- No local admin, recovery by editing state offline, or one that a setting disables: the same trust with no audit record, and no stop to user id 0, who can read the node key file.
- Local admin with `cloud-admin` only, without `iam` in every org: a deny attached to an org binds its users, `cloud-admin` included, so only a caller no deny binds can detach it.
- A warning that a cloud admin can acknowledge and clear: a stolen `cloud-admin` key, or the root that used break-glass, would clear it. Reads raise no warning: they change nothing, and the audit log has them.
- Replace an existing key of the same name on exchange, or always revoke descendants: hostnames collide, and logging in again on one computer would log out every computer set up from it.
- Refuse at commit every write through a revoked key: it reaches every service's write path, and ARFC 0020 section 3.4 allows the 5 seconds.
